# 能力资产资料收集清单

## 1. 目的

本文用于指导 AgentArbor 开发前期的资料收集。

当前要解决的问题不是“临时接一个模型”或“临时找一个工具”，而是为 AgentArbor 沉淀一套可版本化、可选择、可验证、可快照的能力资产体系。

后续 AgentArbor 在孕育 AgentApp 时，应优先从本项目已经沉淀的资产中选择能力，而不是每次生成 Agent 时临时查找模型协议、工具协议、MCP、Skill 或插件资料。

## 2. 收集原则

### 2.1 优先官方来源

优先收集：

* 官方文档。
* 官方 API reference。
* 官方 SDK 示例。
* 官方协议规范。
* 官方 GitHub 仓库。
* 官方 changelog / release notes。

社区文章、博客、教程可以作为理解材料，但不能作为最终协议事实源。

### 2.2 记录来源和日期

每条资料都要记录：

```text
名称：
官方链接：
访问日期：
版本号：
适用范围：
是否稳定：
备注：
```

如果资料没有明确版本号，需要记录访问日期。

### 2.3 区分事实、推断和建议

记录时要区分：

```text
事实：官方文档明确写出的能力和字段。
推断：根据示例或行为推出来的结论。
建议：我们准备在 AgentArbor 中如何抽象。
```

不要把推断直接写成事实。

### 2.4 不收集大段原文

不要把官方文档整篇复制到项目里。

应沉淀为：

* 链接。
* 关键字段。
* 协议差异。
* 能力矩阵。
* 风险和限制。
* AgentArbor 的抽象建议。

## 3. 资料最终要沉淀成什么

这些资料最终不是普通笔记，而是要沉淀为 AgentArbor 的固定资产。

目标资产包括：

```text
Provider Protocol Pack
Protocol Pack
Capability Spec
Tool Spec
MCP Connector Spec
Skill Spec
Plugin Spec
Runtime Profile
Sandbox Profile
Evaluation Spec
```

第一版不一定全部实现，但资料收集时要按这些资产类型整理。

### 4.3 重点比较项

模型供应商之间重点比较：

* Tool calling 的字段格式是否一致。
* 工具调用结果如何回传。
* Structured output 是否强约束。
* Streaming 中如何传递 tool call delta。
* 错误码是否可分类为 retryable / non-retryable。
* 是否兼容 OpenAI 风格接口。
* 是否需要特殊 header。
* 是否支持本地部署或私有化。


### 5.2 需要特别关注

MCP 对 AgentArbor 的价值不是“多一个工具接入方式”，而是可以成为外部能力发现和调用协议。

需要重点判断：

* AgentArbor 是否自己实现 MCP Client。
* AgentApp 是否允许直接连接 MCP Server。
* MCP Server 的工具是否需要转成 AgentArbor Capability。
* MCP 的权限是否能映射到 AgentArbor 的 PermissionPolicy。
* MCP Server 的版本和工具清单是否需要快照进 AgentApp。

## 6. Tool 资料

### 6.1 Tool 的定义边界

在 AgentArbor 内部，Tool 应定义为：

> 一个可被 Agent 调用的具体动作。

例如：

```text

web.search
```

## 7. Skill 资料

### 7.1 Skill 的定义边界

Skill 不等同于 Tool。

Skill 应定义为：

> 面向某类任务的方法包，包含流程、提示词、输入输出约束、验收规则和可能使用的工具。

例如：

```text

research-report
paper-reading
file-organize
docx-edit
pdf-extract
spreadsheet-analysis
browser-research
```
