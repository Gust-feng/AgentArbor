# 系统总览

## 产品结构

```text
用户任务 / 文件 / 项目 / 网页
  -> Workbench Shell
       ├─ Ordinary Agent Feature（默认）
       │    └─ Sub-Agent Tool Feature（按需）
       └─ Multi-Agent Feature（显式深入协作）
  -> 结果与活动展示
```

Workbench Shell 是唯一产品壳，负责输入、工作区上下文、导航、历史和结果展示。它不拥有 Agent run 状态，也不从前端事件或文案推导完成、阻塞、确认、child 或 synthesis 事实。

Ordinary 与 Multi-Agent 是两个独立业务 feature，不是两个产品：

- Ordinary 负责线性 conversation、模型-工具循环、确认、取消、失败、恢复和普通 read-model。
- Multi-Agent 负责 intake、manager 决策、TaskBoard、scheduler、child、纠正/停止/继续、parent synthesis 和 Deep read-model。
- Sub-Agent 是 Ordinary 的 SDK AgentTool 贡献，负责专家定义、输入解析和权限收窄；执行、确认与结果进入父 Ordinary run，不拥有独立入口、runner、trace 或 read-model。

## 中性能力与 Host

```text
Desktop / HTTP / Panel adapter
  -> Composition Root
       ├─ Ordinary Agent Feature
       ├─ Multi-Agent Feature
       ├─ Sub-Agent contribution
       └─ neutral capabilities + system adapters
```

中性能力包括 provider/channel、工具执行机械原语、确认、tokenizer、消息完整性、压缩执行、配置和系统协议适配。它们只返回技术事实，不保存业务状态，也不决定模式、工具路径、完成或综合语义。

`createPanelRuntime()` 是当前唯一后端 Composition Root。只有它可以同时创建多个 feature 和具体 adapter。HTTP/SSE route 只解析协议、调用 feature command/query/event facade，并映射响应；不得创建 store、provider、ToolCenter、continuation registry 或隐藏 runtime。

## 状态与事件

每个 feature 拥有自己的事实链：

```text
command -> feature execution -> feature event -> feature state/store -> feature read-model
                                                            └-> UI projection
```

- 业务事件不经过另一个 feature 再解释。
- read-model 不写回业务状态。
- SSE 可以通知变化，但前端不能以 SSE 重建后端权威状态。
- 工具执行以 `ToolCallResult` 为唯一事实，模型、事件和 UI 单向派生。
- Workbench 统一历史只组合判别后的 summary，不合并 Ordinary 与 Multi-Agent 的 conversation/store。

## 依赖方向

- feature 可以依赖中性能力端口。
- adapter 可以依赖中性契约。
- Host / Composition Root 可以依赖 feature factory 和 adapter。
- neutral capability 不能依赖 feature。
- Multi-Agent 不能依赖 Ordinary/Desktop 实现。
- feature 不能依赖 Panel server、Panel UI 或展示类型。
- 不创建 universal Run runtime、全局业务状态、统一工作流引擎或 `RuntimeServices` 属性包。

## 当前实现差异

架构目标已经确定，入口仍在迁移：

- 启动后默认进入普通 Agent。
- Multi-Agent 仍需在设置中开启 beta，并从侧栏 `Agent 集群` 按钮进入。
- 后端仍使用 `/api/deep/*`、Deep DTO 和独立 Deep 数据目录。
- Ordinary 与 Deep 当前拥有各自的 SSE/poll、history 和 view。

这些事实必须在迁移期间保持可用，不能提前写成已经合并。目标是把 Multi-Agent 收口为 Workbench 内的单次显式功能入口，同时继续隔离两类业务状态。

## 长期能力

Task Soil、Underground、Plan、Aboveground、Fruits、Governance 和 Global Soil 作为可选纵向能力保留：普通任务可以不经过它们；Multi-Agent 可以只产出综合结论；只有真实存在计划交接、候选经验和治理需求时，相关模块才通过明确端口出生。

开发时不能把长期能力预装进一个固定全局流程，也不能把普通文件编辑、helper、adapter 或状态更新包装成 Plan、Handoff、Agent 或 atomic mutation。
