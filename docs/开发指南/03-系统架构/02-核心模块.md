# 核心模块

## Workbench Shell

统一产品壳，负责：

- 任务输入与工作区上下文选择。
- Ordinary / Multi-Agent surface 导航。
- 两类历史的判别联合、排序和恢复入口。
- 结果、活动、确认和详情的布局组合。

Workbench Shell 不拥有 conversation、run、child、synthesis、confirmation 或完成状态。公共 `ActiveWorkbenchSurface` 与 `WorkbenchItemSummary` 只服务导航和展示，不进入后端业务状态或持久化。

## Ordinary Agent Feature

默认工作方式，拥有完整 Ordinary 闭环：

- conversation 与 run lifecycle。
- Context Ledger / Context Pack。
- 模型-工具-模型循环。
- 工具可见性、确认、取消、失败和恢复的业务映射。
- Ordinary event、仓储和 read-model。
- Skills 与 Sub-Agent 工具贡献的装配入口。

普通运行不维护 DeepTaskBoard、child run tree 或 Plan 交接。它只能通过中性端口使用模型、工具、确认和系统能力。

## Multi-Agent Feature

显式深入协作功能，内部实现当前沿用 `deep` / `DeepRuntime` 命名。它拥有：

- Deep intake 与 conversation。
- manager 自由决策循环。
- DeepTaskBoard、DeepChildScheduler 与一层 child。
- child 追加、确认恢复、纠正、停止和重新综合。
- parent synthesis、Deep event、store 与 read-model。
- control/continuation registry、active run tracking 和自身资源释放。

Multi-Agent 不读取 Ordinary conversation、store、read-model 或完成语义。它可以使用与 Ordinary 相同的模型、工具和确认机械能力，但必须自行映射 Deep outcome。

## Sub-Agent Feature

Sub-Agent 是 Ordinary 的工具能力，拥有：

- builtin/user/project 定义发现。
- `call_sub_agent`、`call_sub_agents`、`spawn_sub_agent` 工具贡献。
- 父 run 权限上限内的工具收敛。
- 禁止递归派生。
- 子运行、确认冒泡、完整模型可用输出和 trace。

Sub-Agent 不拥有独立产品入口、全局 mode、Deep run tree 或独立任务生命周期。父 Ordinary Agent 对它的输出负责综合和最终回答。

## Neutral Model Capability

负责 provider/channel 创建、协议能力、模型请求/响应与失败归一化。它不能：

- 导入 Ordinary、Multi-Agent、Sub-Agent 或 Panel。
- 创建 feature ToolCenter 或 Skill Context。
- 硬编码 Ordinary 的 `finish_task` 或 Deep outcome。
- 保存 run、conversation 或 child 业务事实。

## Neutral Tool Capability

负责工具定义、执行机械边界、权限/确认原语、取消和 `ToolCallResult` 事实。Host 按当前 feature 装配基础文件、命令、浏览器、HTTP、研究、MCP、Skills 和 Sub-Agent 工具贡献。

ToolCenter 不拥有 Agent loop 预算、业务完成语义、UI display 或持久化 read-model。模型、事件和 UI 分别从同一工具事实单向派生。

## Neutral Context Capability

只提供 tokenizer、消息完整性、上下文窗口计算、压缩执行和 continuation 所需的机械算法。Ordinary 与 Multi-Agent 分别拥有自己的上下文策略、触发条件、事件与业务结果；Deep 不能依赖 Ordinary 专用 compaction facade。

## Confirmation Capability

提供确认请求、决定和技术恢复句柄。是否进入 pending、如何向用户展示、确认后恢复哪个业务流程，由调用 feature 拥有。Sub-Agent 的确认必须冒泡到父 Ordinary run；Multi-Agent child 确认留在 Deep 业务闭环。

## System Adapters

负责外部格式与系统能力接入，包括：

- 模型供应商协议。
- MCP、浏览器、文件、命令和 HTTP。
- 本地路径、secret、进程和桌面环境。
- 文件系统或未来数据库实现。

adapter 只实现中性 contract，不能定义 feature 业务模型或导入 Panel UI 类型。

## Composition Root

`createPanelRuntime()` 是生产后端的唯一 Composition Root。它解析 Host 配置，创建 adapter，装配 Ordinary 与 Multi-Agent feature，并统一关闭资源。

route、controller、feature helper 和测试 fixture 不能形成第二个生产组合根。禁止以 `MinimalRuntime`、`RuntimeServices`、全局 singleton 或 route `WeakMap` 隐藏装配与生命周期。

## Feature Stores 与 Read-Models

- Ordinary store 只保存 Ordinary conversation/run 事实。
- Multi-Agent store 只保存 Deep conversation/run/child/synthesis 事实。
- Sub-Agent trace 保存子运行复盘事实，不能成为 Deep 或 Ordinary 主状态。
- Workbench history summary 只保存或临时组合 `{kind, id, title, updatedAt, status}` 一类展示字段。

不提前抽象统一 repository、blob、journal 或 transaction。只有出现两个稳定消费者且机械语义完全相同时才提取。

## 长期能力模块

Task Soil、Plan、Aboveground、Fruits、Governance、Global Soil 和 Lineage 继续保留独立所有权。它们只能在真实业务契约与消费者出生后通过公开端口接入 Workbench feature，不得预先组成固定的请求流水线。
