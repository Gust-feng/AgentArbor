# 主干审查报告

## 审查结论

截至 2026-06-07，默认普通 Agent 已经从零散面板流程收敛成一条可以继续建设的主干，但还不能视为最终优秀状态。

当前主干已经具备四个关键事实：

1. 默认桌面入口以普通 `agent` 为唯一默认运行模式。
2. 普通 run 在创建时冻结 `AgentDefinition` 引用、能力快照、模型配置、信息访问和工具可见事实。
3. 模型工具循环以 `allowedTools` 作为模型可见和执行前校验的共同边界。
4. 前端主路径消费后端 `workView` / run view，不再自行重建普通 Agent 运行事实。

这说明主干方向已经进入代码，而不只是文档口径。后续优化应继续削弱兼容残留和显示噪音，而不是继续添加新概念。

## 当前主干路径

当前普通 Agent 的真实路径应按下面顺序理解：

```text
conversation route / desktop run route
  -> runExecutor.start
  -> PanelRunJobStore creates birth facts
  -> AgentDefinition ref + capabilitySnapshot freeze
  -> BasicAgentRunExecutor
  -> runOrdinaryDesktopForPanel
  -> runDesktopAgentSession
  -> AgentTurnRuntime / executeToolUseLoop
  -> ToolCenter execution and confirmation
  -> backend run response / run view
  -> persistence
  -> frontend read-model display
```

后续普通入口只能复用这条链路。新增入口不得绕过 `runExecutor.start` 直接调用 `runForPanel`、`runOrdinaryDesktopForPanel` 或 `runDesktopAgentSession`，否则会破坏 run 出生事实和恢复边界。

## 已经可信的边界

### 默认运行模式

可信事实：

- `CURRENT_RUNTIME_MODE.md` 已明确当前默认运行方式。
- `run-mode-policy` 约束 desktop 只能跑普通 `agent`，underground 兼容入口固定为 `deep`。
- `panel-server/run-execution` 在路由层之后仍会拒绝错误的 run kind / run mode 组合。

剩余注意点：

- `/api/underground/*` 仍作为显式 deep 兼容路径存在。它不应被前端普通入口、默认菜单或自动路由重新激活。

### AgentDefinition

可信事实：

- `createRuntimeAgentDefinitionCatalog` 拥有默认 desktop AgentDefinition。
- 默认 desktop AgentDefinition 必须声明普通 `agent` 模式。
- `AgentDefinitionRegistry` 以安全 run ref 解析定义，并拒绝带 hash 的语义漂移。
- run response、run persistence 和 UI contract 暴露的是 `RunAgentDefinitionRef`，不是完整 prompt 正文。

剩余注意点：

- AgentDefinition 资产已经存在，但未来新增 Agent 时仍要先定义 prompt、turn policy、output contract 和 tool visibility profile，再接入运行时。
- 历史 prompt 版本必须可解析，不能为了清理文件删除旧 run 所需定义。

### 工具暴露与执行

可信事实：

- `capability-policy` 从 run 创建时冻结的 `capabilitySnapshot` 和 `AgentDefinition.toolVisibilityProfile` 推导工具可见集合。
- `desktop-agent-session` 在有工具调用能力时要求先有 `capabilitySnapshot`，再向模型暴露工具。
- `tool-use-loop-execution` 在调用 broker 前检查 `allowedTools`。
- `ToolCenter` 执行时再次检查 run permission。
- 未授权工具调用返回标准失败结果，而不是交给 adapter 执行。
- read-only batch 也会在执行前检查授权，不能因为并行优化绕过边界。

剩余注意点：

- MCP 当前只能作为配置目录、能力快照和能力草案投影，不进入默认普通 Agent 工具循环。
- 后续接入 MCP 执行前，必须先补齐确认、安全投影、模型可见描述和行为测试。

### 后端 run facts 与用户视图

可信事实：

- `resolveCompatibleRunFacts` 会保留 run 创建时冻结的事实，防止 terminal payload 覆盖模型、工具和 AgentDefinition 事实。
- live run view 优先使用匹配当前状态的 payload，不让 stale completed payload 覆盖 failed / cancelled 状态。
- persisted run response 使用 snapshot 中的 run facts，而不是当前全局配置。
- run persistence 不再用当前 workspace config 发明历史 workspace 事实。
- 前端 contracts 把 `workSession` 从普通 UI contract 中移除，普通主路径读取 `workView`。

剩余注意点：

- 后端仍保留 `workSession` 兼容别名和旧 endpoint。它们可以保留给历史调用方，但新增普通 UI 和普通后端路径必须使用 `workView`。
- 旧 canvas 中的 `work_session_canvas` 仍然是历史数据形态，不能把它重新解释成新的产品语义。

## 仍然薄弱的地方

### 1. 兼容路径还容易误导新开发

`workSession`、`underground_deep_canvas`、`direction_handoff`、`agent.child.*` 等兼容处理仍在代码中存在。这些不是默认普通 Agent 主线，但搜索代码时会干扰判断。

改进方向：

- 为兼容路径保留明确命名，例如 `legacy`、`compat`、`persisted deep replay`。
- 新增结构测试，禁止普通 UI 默认订阅或默认展示 deep / child / handoff 事件。
- 新增文档说明哪些文件属于兼容处理，哪些文件属于普通主干。

### 2. 部分测试仍偏结构检查

当前已有不少结构测试用于防止边界倒退。这有价值，但不能替代行为测试。

改进方向：

- 对普通入口增加端到端行为测试：创建 run、冻结能力、工具调用、确认、恢复、失败、持久化读取。
- 对前端 read-model 增加行为测试：后端缺字段时清空旧能力事实，终态刷新不能保留 stale run view。
- 对模型失败和上下文维护失败增加用户可见投影测试，确保不会被完成态吞掉。

### 3. 模型运行时仍应继续独立成模块

当前普通 Agent 主干已经开始区分模型事实、工具循环和 run facts，但模型运行时还需要继续成为独立模块，而不是被 provider adapter 或 panel helper 吸收。

改进方向：

- 统一模型请求、流式输出、失败归一化、输出校验和安全投影。
- 普通 Agent、deep、verification、governance 后续都只通过模型运行时契约使用模型能力。
- 不允许 panel route 或 adapter 私自解释 provider 私有失败字段。

### 4. 用户视图还要继续做减法

普通 Agent 的默认 UI 已经减少了部分内部管线痕迹，但还要继续检查是否存在调试字段、内部事件名和过重产品术语。

改进方向：

- 默认首屏只展示状态、当前动作、必要确认、最终回答、关键工具动作和失败原因。
- token、raw ref、debug ref、deep 术语、内部 canvas 结构只进入诊断视图。
- 失败文案必须说明真实边界，例如模型失败、工具未授权、等待确认、上下文溢出，而不是泛化成“处理中”。

### 5. Agent 能力提升还没有真正展开

当前工作主要是“把主干做对”，不是“把 Agent 做聪明”。这一步必要，但还不是终点。

后续能力提升应集中在：

- 更好的上下文装配和压缩。
- 更合理的工具描述与工具选择反馈。
- 工具结果回灌给模型时保留足够事实。
- 确认后的继续执行语义。
- 模型失败、输出校验失败、工具失败后的自然恢复策略。

这些能力必须在单一普通 Agent 主循环上生长，不能靠前端状态机或新的伪流程替代模型判断。

## 下一轮优先级

建议按以下顺序继续：

1. 固化普通入口端到端验收：从 `/api/conversations` 到 run view、persistence、frontend refresh 的完整行为测试。
2. 标记并隔离兼容路径：明确哪些 deep / workSession / handoff / child 逻辑只服务历史恢复或显式 deep。
3. 强化模型运行时模块：把 provider failure、streaming、output validation、visible projection 收敛到统一契约。
4. 清理普通用户视图：移除默认首屏中的内部术语、无意义状态和调试感信息。
5. 再扩展工具能力：只有在 tool visibility、confirmation、safe projection 和 tests 稳定后，才新增更强工具或 MCP 执行。

## 验收门

后续每一轮普通 Agent 主干开发，至少应通过：

```powershell
.\node_modules\.bin\tsc.cmd -p tsconfig.json --pretty false
node --test dist/app/run-mode-policy.test.js dist/app/run-facts-policy.test.js dist/app/panel-run-jobs.test.js dist/app/panel-server/run-execution.test.js dist/app/panel-server/basic-agent-run-view.test.js dist/app/panel-server/persisted-run-response.test.js dist/kernel/intelligence/tool-use-loop.test.js
```

如果改动涉及前端 read-model，还必须增加并运行对应的 panel UI runtime structure / behavior 测试。

如果改动涉及模型运行时，还必须增加模型失败、输出校验失败和安全可见投影测试。

如果改动涉及工具能力，还必须证明：

- 模型只看见本轮可见工具。
- 未授权工具调用不会进入 broker。
- ToolCenter 仍会执行 run permission。
- 需要确认的工具不会绕过确认。
- 给模型的工具事实足够继续工作。
- 给用户的工具投影不泄漏 raw prompt、raw provider response、raw tool output、完整 stdout/stderr 或未授权文件正文。

## 当前判断

当前普通 Agent 主干已经具备继续长期演进的基础，但还没有完成全部质量目标。

可以继续在这条主线上开发；不建议此时新增多 Agent、默认 deep、MCP 工具执行或复杂前端编排。下一阶段最重要的不是堆功能，而是把现有普通 Agent 主干的入口、兼容路径、行为测试和模型运行时边界继续收紧。
