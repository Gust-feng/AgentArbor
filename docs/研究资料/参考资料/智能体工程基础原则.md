# Agent 工程基础参考沉淀

本文是对外部 Agent 工程资料的项目内沉淀。

它不是 AgentArbor 的主架构，也不是最终标准，只是用于避免早期生成物混乱的基础工程参考。

## 1. 参考范围

本文只关心低层工程问题：

```text
一个 Agent 项目应该如何组织自身资产？
```

它不回答：

```text
AgentArbor 是什么？
AgentArbor 为什么存在？
AgentApp 如何出生、演化、分化和重生？
```

这些问题由深度研究和 AgentArbor 自身规划回答。

## 2. 单 Agent 项目资产

一个单 Agent 项目可以参考以下资产拆分：

```text
agent.yaml              # Agent 声明
manifest.yaml           # 项目元信息
prompts/                # 系统提示词和任务提示词
schemas/                # 输入输出 Schema
tools/                  # 工具绑定
policies/               # 权限边界
memory/                 # 记忆策略
tests/                  # 基础测试
evals/                  # 质量评测
src/                    # 少量定制逻辑
```

这只是工程参考，不是最终标准。AgentArbor 后续可以根据 AgentApp 契约调整目录和字段。

## 3. 低层工程原则

### 3.1 Agent 项目保持薄

单个 Agent 不应复制完整运行时。

它只声明：

* 我是谁。
* 我要完成什么任务。
* 输入输出是什么。
* 可以使用哪些能力。
* 不能做什么。
* 如何被测试和评测。

模型调用、工具执行、权限校验、运行日志、验证闭环应属于 AgentArbor 或 AgentApp 运行时。

### 3.2 Prompt 不是唯一资产

一个合格 Agent 不能只有 Prompt。

至少还需要：

* 输入 Schema
* 输出 Schema
* 工具绑定
* 权限策略
* smoke test
* eval case

否则它只是提示词片段，不是可维护工程资产。

### 3.3 权限应显式声明

每个 Agent 应明确：

* 能读什么。
* 能写什么。
* 能调用哪些工具。
* 是否能联网。
* 是否能访问密钥。
* 哪些操作需要人工确认。

权限不能只藏在 Prompt 里。

### 3.4 工具面要收窄

不要把所有工具都暴露给所有 Agent。

工具应按任务、角色、风险和上下文裁剪。

### 3.5 测试和评测必须随 Agent 版本化

每个 Agent 至少应有 smoke test。

重要 Agent 应有 eval case。

测试不是附属物，而是 Agent 能否被保留、复用和演化的依据。

## 4. 对 AgentArbor 的启发

这些原则可以用于 AgentArbor 的生成物底层：

```text
AgentApp/
  agents/
    <agent>/
      agent.yaml
      prompts/
      schemas/
      tools/
      policies/
      tests/
      evals/
```

但 AgentArbor 还必须在应用级增加自己的核心资产：

```text
arbor.json
goal.md
phase-plan.md
workflow-ir.json
validation-result.json
lineage.md
logs/
```

这些应用级资产才体现 AgentArbor 的灵魂。

## 5. 反例提醒

外部参考中的一些问题应避免：

* 多个事实源并存。
* 文档声称有的 Agent，注册表里没有。
* 权限只写在配置或 Prompt 中，运行时不强制。
* 叙事命名污染平台核心模型。
* 多 Agent 只有角色名字，没有真实输入输出和验证。

AgentArbor 不能重复这些问题。
