# ADR-0017: 约束工程与可执行约束模型

## Status

Accepted, amended by [ADR-0022](ADR-0022-AgentArbor桌面通用Agent与双运行时架构.md).

## Context

以下正文保留约束工程的历史语义原貌。当前产品主线由 ADR-0022 定义为 `Desktop Shell -> Task Soil -> Underground Cognitive Runtime -> Plan -> Aboveground Execution Runtime -> Fruits -> Governance Pipeline -> Global Soil`。

AgentArbor 已经确立原生概念树架构：`Soil -> Underground Center -> .agentarbor -> Aboveground Center -> Fruits -> Governance -> Soil`。约束必须在地下成形、方向交接、地上计划、执行验证、果实治理和入土回流中保持可引用、可执行、可验证。

目标、非目标、权限、成本、时间、技术边界、安全要求、验收标准和资产治理如果只停留在自然语言备注中，动态 Agent 集群会出现局部正确但整体偏离的问题。尤其当 Path Bias、Nutrient Request、Nutrient Patch、Growth Plan Revision 和 Capability Asset 共同存在时，系统必须知道哪些约束能指导偏好，哪些约束会阻断行动，哪些约束需要用户或治理门确认。

## Decision

AgentArbor 新增“约束工程”作为横向架构原则。约束工程不是治理系统的重复；治理系统定义权力、审批和规则边界，约束工程负责把规则和目标边界转化为可提取、可传递、可执行、可验证、可沉淀的契约对象。

约束生命周期如下：

```text
Soil 提供长期治理约束和资产使用约束
  -> Underground Center 提取候选约束、冲突和未知项
  -> .agentarbor Direction Handoff 记录 ConstraintRef、证据和升级条件
  -> Aboveground Center 裁决冲突并写入 Growth Plan
  -> Workflow IR 把约束分发到任务和工具执行门
  -> Aboveground Growth 按约束切片执行并提交证据
  -> Verification 验证约束满足情况
  -> Run Memory 记录约束变化、失败和偏离
  -> Fruits 携带候选经验或能力
  -> Governance 决定能否入土
  -> Soil 只吸收稳定、可治理的长期约束
```

Path Bias 只能影响偏好和方案排序，不能覆盖硬约束。任何历史有效路径在遇到新的权限、目标、成本、安全或验收约束时，都必须重新接受 Aboveground Center 裁决和 Verification。

## Constraint Contract

```ts
type Constraint = {
  id: string;
  source:
    | 'user'
    | 'underground_center'
    | 'agentarbor_handoff'
    | 'aboveground_center'
    | 'aboveground_growth'
    | 'verification'
    | 'governance'
    | 'soil'
    | 'external';
  type:
    | 'goal'
    | 'non_goal'
    | 'scope'
    | 'permission'
    | 'cost'
    | 'time'
    | 'technical'
    | 'data_security'
    | 'human_approval'
    | 'verification'
    | 'asset_governance'
    | 'evolution';
  level: 'hard' | 'soft' | 'preference';
  statement: string;
  owner:
    | 'user'
    | 'underground_center'
    | 'aboveground_center'
    | 'verification'
    | 'governance';
  appliesTo: string[];
  evidenceRefs: string[];
  enforcementGate:
    | 'direction_handoff'
    | 'growth_plan'
    | 'task_assignment'
    | 'tool_execution'
    | 'verification'
    | 'fruit_governance'
    | 'soil_promotion';
  conflictPolicy:
    | 'block'
    | 'ask_user'
    | 'aboveground_center_decides'
    | 'verification_reviews'
    | 'governance_review';
  status:
    | 'proposed'
    | 'approved'
    | 'active'
    | 'waived'
    | 'violated'
    | 'retired';
};
```

`ConstraintRef` 是 Direction Handoff、Growth Plan、TaskSpec、Verification Result、Capability Asset 和 Fruit Detachment 对统一约束对象的引用。自然语言说明可以保留，但只能作为解释材料，不能成为执行门的唯一来源。

## Consequences

- Direction Handoff、Growth Plan 和 TaskSpec 不应只保存字符串数组式约束说明，而应保存 `constraintRefs`。
- Aboveground Center 必须显式裁决约束冲突，不能把冲突留给 Aboveground Growth 自行处理。
- Verification 必须验证约束满足情况，并把违反、豁免和不适用证据写入验证结果。
- Run Memory 必须记录本次运行中新发现、被修改、被违反或被证明无效的约束。
- 只有经过治理、稳定且可复用的约束才能进入 Soil；单次任务的临时限制不能自动成为长期资产。
