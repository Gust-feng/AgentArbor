# 模块划分

## 组织原则

AgentArbor 使用同仓功能模块化单体。模块所有权优先按纵向业务闭环判断，`domain / kernel / adapters / app` 只是技术分层，不是把同一功能拆散到多个无主目录的理由。

当前一级功能边界：

```text
Workbench Shell
Ordinary Agent Feature
Multi-Agent Feature
Sub-Agent Tool Feature
Neutral Model / Tool / Confirmation / Context Capabilities
System Adapters
Host Composition Root
```

不拆 pnpm packages，不引入 DI 框架，不建设统一 `RunRuntime`、全局业务状态、工作流引擎或 service locator。目录边界由公开端口、唯一 Composition Root 和依赖测试守住。

## 当前目录与 owner

当前代码仍在渐进归位，以下是 owner 判断，不表示必须立即改名：

| 当前目录/区域 | Owner | 收口要求 |
| --- | --- | --- |
| `app/ordinary-agent/`、`app/agent-definitions/`、`app/agent-prompts/` | Ordinary Agent | feature command/query/event、`ordinary-run/v5`、Session refs、确认/取消/恢复和 Ordinary read-model 只在该 feature 内解释 |
| `app/desktop-agent/` | Ordinary 输入契约 | 只保留桌面模型输入与附件契约，不拥有 session、loop 或业务状态 |
| `deferred/deep/`（已归档） | Multi-Agent | 拥有 manager、TaskBoard、scheduler、child、synthesis、Deep store/registry；不依赖 Ordinary 实现 |
| `app/sub-agents/` | Sub-Agent Tool | 通过 Ordinary AgentTool 贡献端口接入；拥有定义发现、输入解析和权限收窄，不拥有 runner、trace 或 read-model |
| `app/model-runtime/`、`kernel/intelligence/`、`adapters/intelligence/` | Neutral Model Capability | 只处理 provider/channel、协议与技术失败；移除 feature 工具工厂和业务完成语义 |
| `app/tool-center/`、`kernel/tools/`、`adapters/tools/` | Neutral Tool Capability | ToolCenter 返回执行事实；Host 按 feature 装配工具贡献 |
| `app/context-maintenance/` 及 tokenizer/message integrity 原语 | Neutral Context Capability | 只保留机械算法；Ordinary/Deep 策略、事件和 outcome 回到各 feature |
| `app/skills/` | Ordinary capability contribution | Skill 定义与资源加载归自身模块，通过 Ordinary 装配端口贡献上下文/工具 |
| `app/panel-server/` | Host + HTTP/SSE adapter | `runtime.ts` 是后端 Composition Root；route 只调用 feature facade |
| `app/panel-conversation/`、`app/panel-read-model/` | Panel UI 投影 | 只消费 Ordinary 后端 read-model；不得成为跨 feature 业务状态或模型历史来源 |
| `app/panel-ui/` | Workbench Shell + feature surfaces | Shell、Ordinary surface、Multi-Agent surface 状态分离；只组合判别 summary |
| `app/run-runtime-core/` | 中性运行机械原语 | 只保留 event stream、snapshot store 与 run mode policy；不得重新扩成 service locator 或业务 runtime |
| `domain/underground/agent-fabric*` | Multi-Agent 有效领域契约 | 正式 Deep 仍使用的 run-tree 契约；不代表应用层 Underground 或旧 HTTP 入口仍存在 |
| `app/config-center/`、`app/desktop/`、`app/app-update/` | Host/System modules | 提供配置与系统端口，不拥有 Agent 业务状态 |

文件移动不是目标本身。每次归位必须同时移动实现、类型、测试和资源，并证明模型可见事实、工具 continuation、确认和 read-model 未退化。

## 代码命名规范

命名必须表达稳定职责，而不是当前迁移阶段、视觉版本或个人习惯。函数和公开类型的名称应让不了解历史的开发者能够判断输入、输出和副作用。

### 函数命名

- 查询使用 `get`、`find`、`list`、`select`、`project`、`resolve` 等与返回语义匹配的动词；纯函数不得使用 `handle`、`process`、`doSomething`、`data` 等空泛名称。
- 命令使用“动作 + 对象”，例如 `openConversation`、`startConversation`、`renameSpace`、`refreshKnowledge`、`cancelRun`。有持久化、网络或状态副作用时，名称必须让副作用可推断。
- React Hook 使用 `use` 加职责名：`useWorkbenchNavigation`、`useConversationSession`、`useKnowledgeSubscription`。只有组合多个命令并拥有明确边界的对象才称为 `Controller`；普通 helper、formatter 和 adapter 不得称为 agent、manager 或 runtime。
- 组件使用稳定产品对象或内容类型命名，例如 `PersonalWorkbench`、`ConversationPage`、`ConversationTranscript`、`KnowledgePage`。禁止使用 `Redesign`、`New`、`V2`、`Temp` 等迁移期词作为新的正式导出名。

### 迁移与兼容命名

- 迁移期可以保留旧导出，但必须把正式名称作为唯一实现，并在兼容导出上写明 `@deprecated`、替代名称和删除条件。
- `Legacy`、`Compat` 只能用于确实承担兼容职责的文件或适配器，不能把正常生产代码统称为 legacy。
- 目录和 CSS 选择器的改名必须与依赖图、结构测试和视觉回归一起迁移。不能为了清除一个历史词而同时改变 DOM、class、动画 key 或状态时序。
- 新增概念前必须说明它承担的独立职责、输入输出、失败方式、测试边界和可观察投影；否则使用已有 owner 的朴素名称。

当前工作台的命名收口已经完成第一阶段：生产目录使用
`src/app/panel-ui/src/personal-workbench/workbench/`，组合根使用
`PersonalWorkbench`，对话渲染器使用 `ConversationTranscript`，样式作用域使用
`aa-workbench-root` 与 `aa-conversation-transcript`。`RedesignWorkbench` 仅保留为
带 `@deprecated` 标记的兼容导出，新的源码、测试和文档不得再引入该名称或
`redesign` 路径；待外部导入清零后删除兼容导出。

Sidebar 负责空间列表的创建、重命名、删除动作编排，行内编辑归
`SidebarInlineRenameField`；空间数据和删除语义仍由 Space feature 拥有，不能把
业务状态或源内容删除策略回填到 Workbench 组合根。

### 交付检查

提交前至少检查：名称是否与真实 owner 一致；是否泄漏 prototype、provider 或内部实现；函数是否区分查询与命令；兼容别名是否有迁移终点；是否因改名扩大了行为、样式或运行时变更范围。

## Ordinary Agent 边界

Ordinary 必须拥有：

- `OrdinaryAgentFeature` command/query/event facade；它是当前生产 owner，不是转发旧执行器的空 facade。
- conversation、run lifecycle、模型输入装配与 Pi Session refs。
- AgentDefinition、capability snapshot 与工具可见性业务决策。
- 确认、取消、失败、恢复和完成 outcome。
- Ordinary event、repository、read-model 和测试。
- Skills 与 Sub-Agent 的贡献端口。

Panel、Deep 或 neutral runtime 不能读取 Ordinary store、registry 或专用 reducer。Sub-Agent 可以通过明确工具贡献端口接入，但不能取得整个 Ordinary runtime 属性包。

## Multi-Agent 边界

Multi-Agent 必须拥有：

- `MultiAgentFeature` command/query/event facade。
- DeepConversation、DeepRun、intake 与 history。
- manager 决策、TaskBoard、scheduler、child 与 parent synthesis。
- control/continuation registry、instruction queue、active run tracking。
- Deep store、event、read-model、资源释放和测试。

`/api/deep/*` route 只是 adapter。它不能包含 `WeakMap` 状态、`new Store`、`createMinimalRuntime()`、provider 工厂或 ToolCenter 工厂。Multi-Agent 需要模型、工具、确认或上下文机械能力时，由 Composition Root 注入精确端口。

## Sub-Agent 边界

Sub-Agent 拥有定义发现、Pi AgentTool 贡献、输入解析和权限收敛。它不是独立 surface，不维护 runner、trace、Deep task board 或独立 read-model，也不能递归调用 Sub-Agent 工具。

父 run 冻结权限是上限；Sub-Agent 声明只能进一步收敛。完整模型可用输出和工具事实必须回到父 Agent，UI 摘要不能替换这些材料。

## 中性能力边界

中性能力必须：

- 不导入任何 feature 或 Panel。
- 不保存 conversation、run、child、synthesis 等业务状态。
- 不决定 Ordinary/Multi-Agent 模式、完成语义或工具路径。
- 不暴露所有服务组成的属性包。
- 以明确输入输出返回模型、工具、确认、上下文或系统技术事实。

当前允许的共享方向包括：

- provider/channel 与协议能力。
- `ToolCallResult`、工具 schema、执行/取消/确认机械边界。
- tokenizer、消息完整性和压缩执行。
- 配置读取、系统路径、secret、进程和外部协议 adapter。

业务 event、repository、read-model、context policy 和 outcome 不属于共享层。

## Composition Root 与 route

生产后端只有 `createPanelRuntime()` 一个 Composition Root：

```text
createPanelRuntime()
  -> host config / adapters
  -> create OrdinaryAgentFeature
  -> create MultiAgentFeature
  -> register route/SSE adapters
  -> close resources
```

当前 Ordinary 的 conversation、run lifecycle、Session refs、确认 continuation、仓储和事件重放均由 `createOrdinaryAgentFeature()` 收回。Panel route 只解析输入并投影 feature command/query/event；Host 装配 Pi AgentHarness/Session adapter、ToolCenter、Skills、MCP、Sub-Agent AgentTool 与系统资源。

只有 Composition Root 可以同时导入多个 feature factory。route 每个操作一对一委托一个 feature command/query/event；跨功能历史只在 Workbench query/projection 层按判别 summary 组合。

测试可以创建单 feature fixture，但不能复制一套生产装配。资源遵循“谁创建、谁释放”，禁止模块全局 mutable singleton、route `WeakMap` 和隐藏 service locator。

## 依赖规则

允许：

- Host / adapter -> feature facade。
- Composition Root -> feature factory + concrete adapter。
- feature -> neutral capability port。
- adapter -> neutral contract。
- Sub-Agent -> Ordinary tool contribution port。

禁止：

- neutral capability -> feature。
- Multi-Agent -> Ordinary/Desktop 实现。
- feature -> `panel-server` / `panel-ui`。
- feature -> 另一个 feature 的 store、event 或 read-model。
- route/controller -> feature 内部对象。
- adapter 定义核心业务模型。
- `domain`、`kernel` 或业务编排直接调用 provider/MCP SDK。

## 共享抽象准入

只有两个真实且稳定的消费者使用同一机械语义时才提取共享原语。字段相似、文件重复或未来“可能复用”都不够。

在准入前，blob、journal、repository、workflow、event bus、state machine 和 transaction 留在 owner 内。不得为了消除少量重复引入更大的跨 feature 耦合。

## `src/app` 顶层规则

`src/app` 顶层长期只保留：

- 应用入口和唯一组合根入口。
- 极小的跨模块中性契约。
- 正在迁移且有明确删除计划的兼容 facade。

新增或大改时必须进入 owning feature/能力目录；facade 只能 re-export，不能重新承载逻辑。源码结构测试必须验证依赖方向和行为边界，不得永久锁定历史文件名、compat export 或源码字符串。

## 长期模块

Task Soil、Plan、Aboveground、Fruits、Governance、Global Soil 与 Lineage 只有在真实业务契约和消费者出生后才建立 feature 边界。它们不能预先并入 Ordinary/Multi-Agent，也不能组成每次请求必经的全局 workflow。
