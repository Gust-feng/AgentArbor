# AgentArbor 项目计划书

## 0. 项目摘要

**项目名称：** AgentArbor
**项目定位：** 面向垂直场景的 AI Agent 应用生成平台
**英文标语：** Let every scenario grow its own Agent.
**中文标语：** 让每个场景，长出自己的 Agent。

AgentArbor 不是一个普通的聊天助手，也不是一个只生成提示词的工具。它面向 AI 原生应用开发中的核心痛点：用户知道自己想解决什么问题，却很难把一个场景需求转化为可运行的 Agent 应用。

AgentArbor 允许用户用自然语言描述一个垂直场景，系统自动完成需求理解、Agent 架构设计、工具选择、工作流编排、提示词生成、代码工程生成、测试样例生成与运行说明生成，最终产出一个可运行、可修改、可部署的单 Agent 或多 Agent 应用工程。

它的核心目标不是让 AI 替用户完成一次任务，而是帮助用户生成一个能够长期服务某类任务的 Agent 系统。

> 通用 Agent 是帮人做事。
> AgentArbor 是帮人创造能做事的 Agent。

---

## 1. 产品愿景

未来的 AI 应用不会只存在于少数大型平台里。每个行业、每个组织、每个个人，都可能需要属于自己的垂直 Agent。

学生需要论文阅读 Agent、课程规划 Agent、复习计划 Agent。
开发者需要代码审查 Agent、项目理解 Agent、文档维护 Agent。
小团队需要会议纪要 Agent、资料整理 Agent、竞品调研 Agent。
普通人需要文件管理 Agent、旅行规划 Agent、个人事务 Agent。

问题在于，真正创建一个 Agent 应用并不简单。用户需要理解模型调用、Prompt 设计、工具接入、RAG、工作流编排、多 Agent 协作、上下文管理、权限控制、运行环境和项目部署。哪怕用户有非常明确的需求，也很难从零搭建一个可运行的 Agent 工程。

AgentArbor 的愿景是降低这道门槛。

它希望让用户不再从代码、节点和配置开始，而是从一个真实目的开始。用户描述场景，系统负责把这个场景拆解、组织、生成和验证。

> 每一个场景意图，都是一颗种子。
> AgentArbor 让它长成一个可运行的 Agent 应用。

长期来看，AgentArbor 希望成为 AI 原生应用时代的“智能体生成层”：它不只是生成代码，更生成一种新的软件创建方式。

## 2. 项目背景

### 2.1 AI 应用正在从问答走向执行

大语言模型最初被广泛用于文本生成、问答和内容摘要。但随着工具调用、多模态理解、RAG、代码生成和多 Agent 协作能力的发展，AI 应用正在从“回答问题”走向“完成任务”。

用户不再只满足于问：

> 这篇文章讲了什么？

而是希望 AI 能够：

> 阅读这批资料，整理成报告，生成待办事项，并输出可编辑文档。

这意味着 AI 应用的形态正在变化。传统软件依赖固定功能和按钮，AI 原生应用则依赖自然语言目标、动态规划、工具调用和持续执行。

### 2.2 Agent 创建仍然门槛很高

当前市面上已经出现很多 Agent 平台、低代码平台和 AI 编程工具。它们提供了强大的能力，但对普通用户和初级开发者来说，仍然存在明显门槛。

用户需要回答很多问题：

* 这个场景应该用单 Agent 还是多 Agent？
* 每个 Agent 应该承担什么职责？
* 哪些工具需要接入？
* 工具权限如何分配？
* 工作流如何编排？
* Prompt 如何设计？
* 输出格式如何约束？
* 项目结构如何组织？
* 如何测试生成结果是否可用？

这些问题本质上不是用户想解决的问题，而是用户为了创建 Agent 被迫学习的中间负担。

AgentArbor 想把这部分负担交给 AI。

### 2.3 从“使用 Agent”到“生成 Agent”

通用 Agent 的核心价值是替用户完成任务。AgentArbor 的核心价值则是替用户生成一个能反复完成某类任务的 Agent 应用。

这是一种更上游的能力。

如果说普通 Agent 是一个会干活的工人，那么 AgentArbor 更像是一棵树。用户给它一个场景，它会生长出适合这个场景的枝干：角色、工具、流程、代码、测试和文档。

## 3. 核心问题与机会

### 3.1 用户有场景，但缺少工程化路径

很多用户能清楚说出自己想要什么，却不知道如何把它转化为应用。

例如：

> 我想要一个能帮我读论文、解释术语、生成笔记的 Agent。

这句话背后其实包含多个模块：PDF 解析、文本切分、摘要、术语解释、知识库、问答、笔记导出。对用户来说，这是一个需求；对开发者来说，这是一个系统。

AgentArbor 要做的事，就是把“需求”变成“系统”。

### 3.2 现有平台偏向手动搭建

许多平台提供了节点、工具、插件、变量和流程配置。它们很强，但更像是给用户一堆积木，让用户自己搭建。

AgentArbor 的方向不是让用户从零搭，而是让用户描述目标后，由系统自动生成初始工程。

用户仍然可以修改，但不必从空白开始。

### 3.3 许多生成工具只停留在 Prompt 层

只生成 Prompt 不等于生成应用。

一个真正的 Agent 应用至少需要：

* Agent 定义
* 工具模块
* 工作流
* 运行入口
* 配置文件
* 测试样例
* 输出格式
* README
* 错误处理

AgentArbor 的关键边界是：它生成的不是一段话，而是一个可运行工程。

## 4. 产品定义

### 4.1 AgentArbor 是什么

AgentArbor 是一个自然语言驱动的垂直 Agent 应用生成平台。

用户输入场景需求后，系统自动完成以下步骤：

1. 理解用户需求。
2. 判断任务复杂度。
3. 设计单 Agent 或多 Agent 架构。
4. 选择所需工具模块。
5. 生成 Agent Prompt 与职责定义。
6. 生成协作工作流。
7. 生成代码工程。
8. 生成测试样例。
9. 生成运行文档。
10. 提供导出与运行验证。

最终产物是一个可以运行、可以修改、可以继续扩展的 Agent 项目。

### 4.2 AgentArbor 不是什么

AgentArbor 不是普通聊天机器人。它不以单次问答为目标。

AgentArbor 不是 Prompt 生成器。它不会停留在角色设定和提示词模板层面。

AgentArbor 不是传统低代码平台。它不要求用户从节点和连线开始搭建。

AgentArbor 也不是通用 Agent 的直接竞品。它不强调自己替用户完成所有任务，而是强调生成适合具体场景的 Agent 应用。

### 4.3 一句话定位

> AgentArbor 将自然语言场景需求转化为可运行的垂直 Agent 应用工程。

### 5.1 学生开发者

他们有比赛、课程设计、科研辅助、个人工具开发等需求，但缺少完整 Agent 应用工程经验。

AgentArbor 可以帮助他们快速生成论文阅读、课程管理、资料整理、项目日报等 Agent 应用。

### 5.2 独立开发者

他们需要快速验证 AI 应用想法，但不希望每次都从零搭建工程结构。

AgentArbor 可以作为 AI 应用 MVP 生成器，帮助他们快速获得一个可运行起点。

### 5.3 小团队与工作室

小团队经常面对大量重复性信息处理任务，例如用户反馈分析、竞品调研、会议纪要、文档审阅和周报生成。

AgentArbor 可以帮助他们生成内部专用 Agent，降低自动化工具开发成本。

### 5.4 AI 应用学习者

很多人想学习 Agent 应用如何构建，但直接阅读复杂框架往往门槛很高。

AgentArbor 生成的工程、注释、README 和测试样例，可以成为学习材料。

## 7. 核心功能设计

### 7.1 自然语言需求输入

用户通过自然语言描述想要生成的 Agent 应用。

系统需要识别：

* 目标场景
* 用户角色
* 输入类型
* 输出结果
* 所需工具
* 是否需要联网
* 是否需要文件读写
* 是否需要多 Agent 协作
* 是否需要长期记忆
* 是否需要导出文档

这一层决定生成结果的方向，是 AgentArbor 的根系。

### 7.2 需求结构化分析

系统将自然语言转为结构化需求对象。

示例：

```json
{
  "domain": "academic_reading",
  "goal": "generate a paper reading agent",
  "inputs": ["PDF", "user_question"],
  "outputs": ["summary", "key_points", "term_explanations", "reading_notes"],
  "complexity": "medium",
  "requires_multi_agent": true,
  "tools": ["PDFParser", "MarkdownWriter", "VectorStore"],
  "constraints": ["local_file_access", "explainable_output"]
}
```

结构化需求是后续架构设计、代码生成和测试生成的统一依据。

### 7.3 Agent 架构规划

系统根据任务复杂度判断生成单 Agent 还是多 Agent 集群。

单 Agent 适合：

* 流程短
* 工具少
* 输入输出清晰
* 不需要审查或分工

多 Agent 适合：

* 流程长
* 多步骤推理
* 多工具协作
* 需要审查
* 需要不同角色分工

系统需要生成：

* Agent 名称
* Agent 职责
* Agent 输入
* Agent 输出
* Agent 工具权限
* Agent Prompt
* Agent 协作关系

### 7.4 工具规划与权限分配

AgentArbor 不应让所有 Agent 拥有所有工具。

系统应遵循最小权限原则：

* 读文件的 Agent 不一定能写文件。
* 搜索 Agent 不一定能执行命令。
* 报告 Agent 不一定能访问原始敏感数据。
* 审查 Agent 只需要读取结果并给出判断。

初期工具可以包括：

* 文件读取
* Markdown 写入
* PDF 解析
* Web 搜索
* 代码 diff 读取
* 简单向量检索
* 本地配置读取
* 日志记录

工具不必多，但必须边界清晰。

### 7.5 工作流生成

AgentArbor 为每个生成项目创建工作流配置。

例如：

```text
User Request
  ↓
PlannerAgent
  ↓
ResearchAgent
  ↓
CompareAgent
  ↓
CriticAgent
  ↓
WriterAgent
  ↓
Final Report
```

工作流需要包含：

* 执行顺序
* 输入输出传递
* 失败处理
* 结果校验
* 最终输出格式

### 7.6 代码工程生成

这是 AgentArbor 的核心边界。

生成结果不是自然语言建议，而是完整工程。

建议初版工程结构：

```text
generated-agent-app/
├─ agents/
│  ├─ planner.agent.json
│  ├─ researcher.agent.json
│  └─ writer.agent.json
├─ prompts/
│  ├─ planner.md
│  ├─ researcher.md
│  └─ writer.md
├─ tools/
│  ├─ file-reader.tool.yaml
│  ├─ markdown-writer.tool.yaml
│  └─ web-search.tool.yaml
├─ workflows/
│  └─ main.workflow.json
├─ tests/
│  └─ sample_task.json
├─ outputs/
│  └─ .gitkeep
├─ runtime.yaml
└─ README.md
```

项目应能通过命令运行：

```bash
agentarbor run generated-agent-app --sample tests/sample_task.json
```

生成物第一版不应被限定为某一种语言工程。它应优先是声明式 AgentApp，由 AgentArbor Runner 在受控环境中读取并执行。

### 7.7 测试样例生成

每个生成项目必须带 sample task。

例如论文阅读项目：

```json
{
  "task": "Read sample.pdf and generate a reading note.",
  "expected_outputs": [
    "summary",
    "key_points",
    "term_explanations",
    "further_questions"
  ]
}
```

测试样例是判断生成项目是否真实可运行的证据。

### 7.8 README 与运行文档生成

系统自动生成文档，包括：

* 项目简介
* 适用场景
* Agent 架构说明
* 工具说明
* 如何配置模型
* 如何运行
* 示例任务
* 如何扩展新工具
* 常见问题

文档不是装饰，而是复现能力的一部分。

### 7.9 可视化生成过程

前端不应只是一块聊天框。

建议设计为“生长式流程”：

```text
场景意图
  ↓
需求根系
  ↓
Agent 枝干
  ↓
工具叶片
  ↓
代码躯干
  ↓
运行果实
```

实际 UI 可以简化为五个阶段：

1. 需求理解
2. 架构规划
3. 工具选择
4. 工程生成
5. 运行验证

这样既符合 AgentArbor 的名字，也能让评委看见系统内部过程。

## 8. 技术方案

### 8.1 总体架构

```text
AgentArbor
├─ UI Layer
├─ Requirement Analyzer
├─ Agent Architect
├─ Tool Planner
├─ Workflow Generator
├─ Prompt Generator
├─ Code Generator
├─ Test Generator
├─ Runtime Validator
├─ Project Exporter
└─ Agent Runtime Template
```

### 8.2 模块说明

#### Requirement Analyzer

负责将用户自然语言需求转为结构化需求。

输入：用户文本。
输出：结构化 JSON。

#### Agent Architect

负责判断是否需要多 Agent，并设计 Agent 职责。

输入：结构化需求。
输出：Agent 架构描述。

#### Tool Planner

负责选择工具并分配权限。

输入：Agent 架构与需求。
输出：工具清单与权限配置。

#### Workflow Generator

负责生成工作流。

输入：Agent 架构与工具配置。
输出：工作流 JSON。

#### Prompt Generator

负责生成每个 Agent 的系统提示词和输出规范。

输入：Agent 职责。
输出：Prompt 文件。

#### Code Generator

负责基于模板生成代码工程。

输入：需求、架构、工具、工作流。
输出：可运行项目文件。

#### Test Generator

负责生成 sample task。

输入：项目用途。
输出：测试任务与预期输出说明。

#### Runtime Validator

负责运行生成项目中的测试任务，记录日志与错误。

输入：生成项目。
输出：运行结果、错误信息、输出文件。

#### Project Exporter

负责导出 zip 文件或项目目录。

输入：生成工程。
输出：可下载项目。

### 8.3 技术栈建议

主技术栈明确使用 TypeScript。

理由是 AgentArbor 需要同时覆盖 CLI、Workbench、模型接口、配置校验、模板渲染和 Runner 适配。TypeScript 可以让前后端共享核心类型，也便于用声明式 Schema 管理 `arbor.json`、Workflow IR、Agent Manifest、Provider 配置和 ValidationResult。

推荐组合：

* 语言：TypeScript
* 运行时：Node.js LTS
* 包管理：pnpm workspace
* CLI：Node.js CLI
* Workbench：React + TypeScript
* 本地存储：SQLite
* 配置文件：JSON / YAML
* Schema：Zod / JSON Schema
* 模板系统：Handlebars / Eta / 自定义模板
* 模型接口：Provider Adapter，优先支持 OpenAI-compatible API
* 日志系统：结构化 JSON 日志
* 导出方式：zip
* 受控执行：Linux Container Runner，后续接入 CubeSandbox / E2B

### 8.4 生成策略

为了保证生成代码可运行，不建议完全依赖 LLM 自由生成工程。

应采用：

> 稳定模板骨架 + LLM 定制填充

也就是说：

* 项目结构由模板控制。
* 基础运行时由开发者写好。
* LLM 负责生成 Agent 配置、Prompt、工具选择、工作流和少量适配代码。
* 高风险代码不让 LLM 完全自由发挥。

这样可以减少生成失败，提高演示稳定性。

## 9. MVP 设计

### 9.1 MVP 目标

在最小版本中，AgentArbor 要完成一个关键闭环：

```text
自然语言需求
  ↓
Agent 架构生成
  ↓
代码工程生成
  ↓
测试样例生成
  ↓
一键运行验证
  ↓
导出项目
```

### 9.2 MVP 支持的三类 Agent

#### Research Agent

用于资料调研、信息整理和报告生成。

#### File Agent

用于文件扫描、分类、摘要和整理。

#### Code Review Agent

用于读取代码变更、分析问题和生成审查报告。

这三类覆盖不同能力：信息处理、本地工具调用、开发者场景。

### 9.3 MVP 不做什么

第一版不做：

* 完整插件市场
* 任意复杂场景生成
* 完整云端部署平台
* 大规模多人协作
* 复杂权限沙箱
* 完整可视化拖拽编辑器

第一版只打穿主线。

## 10. 创新点

### 10.1 从“AI 回答”到“AI 生成应用”

AgentArbor 不满足于让 AI 输出答案，而是让 AI 输出一个可运行系统。

### 10.2 从“手动搭建”到“自然语言生成”

用户不需要学习节点编排和工程结构，只需要描述场景。

### 10.3 从“Prompt 模板”到“工程产物”

AgentArbor 的产物包括代码、配置、工作流、测试和文档。

### 10.4 单 Agent 与多 Agent 自适应规划

系统根据任务复杂度决定生成单 Agent 或多 Agent 集群。

### 10.5 面向垂直场景，而非追求万能

AgentArbor 不直接制造一个万能 Agent，而是生成适合具体场景的专属 Agent。

### 10.6 生成结果可验证

通过 sample task 与运行日志证明生成工程真实可用。

## 11. 竞赛适配性分析

AgentArbor 更适合赛道一：架构级 AI 原生应用开发。

原因如下：

第一，它的核心功能离开 AI 无法成立。需求理解、架构生成、Prompt 生成、工作流设计和代码生成都依赖 AI。

第二，它不是传统软件加 AI 功能，而是以 AI 作为应用生成的核心驱动力。

第三，它探索的是 AI 原生应用开发方式本身，即如何让自然语言成为创建 Agent 应用的入口。

第四，它具有明确工程产物，不停留在概念层。

第五，它可以展示单 Agent 与多 Agent 应用生成，体现架构级 AI 原生能力。

参赛时应重点强调：

> AgentArbor 不是一个 Agent 应用，而是一个生成 Agent 应用的平台。它让 AI 参与 AI 原生应用的设计、生成、验证和交付过程。

## 15. 风险分析与应对

### 风险一：项目范围过大

表现：想支持所有场景，最终每个场景都不够深。

应对：第一版只支持三类模板，先保证闭环。

### 风险二：生成代码不可运行

表现：LLM 生成代码不稳定，运行失败。

应对：采用模板骨架，不让 LLM 自由生成核心运行时。

### 风险三：看起来像 Prompt 生成器

表现：评委觉得只是生成提示词。

应对：必须展示代码工程、运行入口、测试样例和输出结果。

### 风险四：多 Agent 流于概念

表现：Agent 名字很多，但协作不真实。

应对：每个 Agent 必须有清晰输入、输出、工具权限和工作流位置。

### 风险五：与现有平台重叠

表现：被认为类似 Dify、Coze、Flowise。

应对：强调差异：那些平台偏手动搭建，AgentArbor 偏自动生成可运行工程。

### 风险六：演示不稳定

表现：现场运行失败或输出不可控。

应对：准备离线示例、固定 sample task、保留生成日志和备份视频。

## 17. 项目叙事

每一个垂直 Agent 的诞生，都始于一个尚未成形的场景意图。

用户知道自己想解决什么问题，却未必知道如何设计 Agent 架构、编排工具、组织流程、编写代码与测试。于是，很多本该生长出来的 AI 应用，停在了想法里。

AgentArbor 想改变这一点。

它将自然语言需求转化为可运行的 Agent 工程。意图是根，工具是枝，工作流是脉络，代码是躯干，测试与文档让它真正站立。最终，一个具体场景不再只是想法，而是长出属于自己的智能体系统。

> AgentArbor，让每个场景长出自己的 Agent。

## 19. 最终总结

AgentArbor 的价值不在于再做一个通用 Agent，而在于把 Agent 应用的创建过程本身 AI 原生化。

它面对的是一个正在到来的问题：当每个垂直场景都需要自己的智能体时，人们不可能都从零学习 Agent 工程。

AgentArbor 给出的答案是：

> 用户描述目的，系统生成智能体应用。

这使它不只是一个工具，而是一种新的 AI 应用开发入口。

如果最终作品能够稳定完成“需求输入 → 架构规划 → 工程生成 → 测试运行 → 项目导出”的闭环，它就具备清晰的赛道一竞争力。

它有名字，有叙事，有工程边界，也有可演示的结果。

更重要的是，它不是追着已有通用 Agent 跑，而是站在更上游的位置，回答一个更有野心的问题：

> 未来的 Agent，不该只由少数平台制造。每一个真实场景，都应该有机会长出自己的智能体。
