# 总览

## 本指南解决什么问题

本指南给 AgentArbor 后续实现提供统一口径。它回答四个问题：

1. AgentArbor 的产品边界是什么。
2. Ordinary、Multi-Agent 与 Sub-Agent 如何分工。
3. 哪些能力可以共享，哪些业务事实必须隔离。
4. 功能如何通过唯一 Composition Root 被装配、验证和渐进迁移。

## 当前产品主线

```text
Workbench
  ├─ Ordinary Agent（默认工作方式）
  │    └─ Sub-Agent（按需工具能力）
  └─ Multi-Agent（用户显式选择的深入协作功能）

Ordinary / Multi-Agent -> 各自结果与活动 -> Workbench 统一展示
```

Workbench 是统一产品壳，只组合任务输入、工作区上下文、surface 导航、历史和结果展示。Ordinary 与 Multi-Agent 各自拥有业务流程、状态、事件、仓储和 read-model；Sub-Agent 只拥有定义发现、Pi AgentTool 贡献和权限收窄，调用结果进入父 Ordinary run，不是独立产品模式。

模型、工具、确认、tokenizer、消息完整性、上下文压缩执行、配置和系统适配可以作为中性能力被各功能调用。共享能力不拥有 feature 业务状态，不决定模式、完成语义、综合结论或工具路径。

当前事实源是 [ADR-0028-AgentArbor统一Workbench与功能模块化单体架构](../架构设计/产品架构/ADR-0028-AgentArbor统一Workbench与功能模块化单体架构.md)，工程规则见 [功能模块边界与组合根](06-工程实现/11-功能模块边界与组合根.md)。

## 当前实现与目标的差异

长期目标边界已经统一，但当前生产运行时已先将 Multi-Agent 延期隔离：

- 默认进入普通 Agent。
- 当前 release 不显示 `设置 -> 关于` 的 beta 开关与侧栏 `Agent 集群` 按钮，启动期不加载 Deep 历史。
- `/api/deep/*` 固定返回 `410 multi_agent_deferred`，不再提供 Multi-Agent 后端接口。
- Deep DTO、conversation/run store 和独立数据目录只作为未来重构参考保留，不由当前运行时读取。

这不是把 Deep 状态转换成 Ordinary 状态，也不是删除长期 Multi-Agent 方向。恢复它必须建立新的产品和运行时契约，不能仅重新挂接旧入口。

## 当前稳定结论

- AgentArbor 是桌面通用 Agent Workbench，不是聊天框、完整 IDE、终端代理或一次性脚手架。
- Ordinary Agent 是默认工作方式，负责连续会话、模型工具循环、命令确认、取消、恢复、持久化和结果展示。
- Multi-Agent 当前是延期的代码基础；其历史 intake、manager、TaskBoard、child 与 synthesis 实现不进入生产组合根。
- Sub-Agent 是 Ordinary 的工具能力；不能递归派生，不能扩张父 run 权限，输出由父 Agent 综合使用。
- Workbench Shell 不拥有 run 状态，不从 SSE 或 UI 文案推导业务事实。
- Ordinary 与 Multi-Agent 不共享业务事件、状态、仓储或 read-model；Sub-Agent 不建立平行状态、仓储或 read-model。
- 模型、工具、确认、上下文机械算法和系统 adapter 通过中性端口复用。
- 后端只有一个生产 Composition Root；route 不创建 feature store、provider、ToolCenter 或隐藏 runtime。
- 不拆 pnpm packages，不引入 DI 框架、universal Run runtime、全局业务状态、工作流 DSL、Event Sourcing 或统一状态机。
- 工具执行遵循 ADR-0027 的单向事实链；一个结果不能在多个层重复改写终态。
- 普通模型正文、工具结果、错误、stdout/stderr、文件内容和 continuation 不能被 UI 摘要或“安全投影”覆盖。
- 命名必须匹配职责；普通编辑、helper、adapter 或状态更新不能包装成 Agent、Plan、Handoff 或 atomic mutation。

## 长期能力如何理解

Task Soil、Underground、Plan、Aboveground、Fruits、Governance 和 Global Soil 仍有长期架构价值，但不是每次请求必经的产品流水线：

- 普通任务可以直接由 Ordinary 完成。
- 多路探索可以由 Multi-Agent 完成并产出综合结论，不必伪造 Plan。
- 真实需要可持久化执行交接时才出生 Plan / Aboveground 能力。
- 产生候选经验且满足治理契约时，才进入 Governance / Global Soil。

这些能力后续作为独立纵向模块，通过端口被 Workbench 功能调用；不能提前塞入统一 runtime 或全局工作流。

## ADR 关系

- ADR-0028：当前产品与模块化事实源。
- ADR-0024：Ordinary 默认和基础能力优先，继续有效。
- ADR-0025：Multi-Agent 内部 manager/child 闭环，继续有效；独立产品定位被取消。
- ADR-0026：Sub-Agent 工具能力，继续有效。
- ADR-0027：工具执行事实与单向消费，继续有效。
- ADR-0022：部分取代；仅保留长期能力边界和历史判断。
- ADR-0023：历史 Profile 方案。
