# AgentArbor 0.3.1 工具系统设计与评测研究报告

## 报告定位

本文面向后续开发者和评审者，说明 AgentArbor 0.3.1 工具系统为什么重做、五个候选如何演进、最终方案如何设计，以及结论由哪些测试支持。

本文是研究报告，不是运行事实源，也不保存原始 trial。当前产品行为以 `CURRENT_RUNTIME_MODE.md`、开发指南、ADR 和代码为准；评测 harness、任务集、指标、候选报告和紧凑证据由独立分支 `codex/eval` 持有。主线只保留最终实现、稳定设计口径和这份可读报告。

报告冻结点：

| 对象 | Git 身份 | 用途 |
| --- | --- | --- |
| 0.3.0 发布基线 | `64596228`，tag `v0.3.0` | Pi 原生 Agent 运行底层 |
| C05 候选闭环 | `30a2fb83`，分支 `codex/c05` | 第五版工具设计候选 |

## 一页结论

0.3.1 选择 C05，不是因为它在每一项统计中都领先，而是因为它在正确性门槛内取得了目前最清楚的工具职责和最低的上下文成本，并且盲审发现的问题能够用局部、确定性的方式闭环。

最终默认 workspace 工具面为：

```text
Read / Glob / Grep / Write / Edit / Shell / ProcessRead / ProcessStop
```

`HttpRequest`、附件读取和 `ReadOutput` 等能力按真实运行能力与本轮授权条件曝光，不为维持固定工具数量注册空壳。当前不建设 `ToolSearch`；基础工具面足够小，尚无数据证明再增加一层工具发现协议能够产生净收益。

核心结论：

- 工具数量不是唯一目标，正交职责、短名称、窄 schema 和高价值结果事实共同决定模型使用成本。
- `Read / Glob / Grep` 应保持分离；它们分别表达读取、路径发现和内容搜索，合并只会把选择复杂度转移进 schema。
- 默认移除 `List / Delete`。目录发现由 `Glob` 完成，删除由通用 `Shell` 完成，减少低价值重叠。
- `Edit` 使用精确唯一匹配，并要求修改既有文件前先 `Read`；陈旧读取后的写入必须拒绝。
- 工具结果必须提供可核验事实。任何截断都必须有真实、可执行且单调前进的 continuation。
- GPT-5.6 Sol 在 C05 上 30/30 通过；DeepSeek V4 Pro 为 29/30，唯一失败是任务语义实现错误，不是工具 schema、调用或变更范围错误。
- 两个模型都显示 C05 明显降低总 Token 和工具定义 Token；它们没有一致证明工具调用次数下降，因此“更少调用”不是 0.3.1 的已确认收益。

## 1. 为什么重新设计工具系统

0.3.0 完成了 Ordinary Agent 到 Pi 原生 Agent Session/AgentTool 运行底层的迁移。迁移解决了主循环、Session、工具调度和模型接入问题，但没有自动保证工具面本身足够好。

第一版暴露出的主要问题不是“工具不能执行”，而是模型看到的信息质量不稳定：

- 名称和职责不够统一，模型需要额外判断多个相近入口。
- schema 带有历史兼容字段或多个表达同一动作的分支，定义成本高。
- 部分结果只证明“执行过”，没有充分返回 changed、hash、bytes、diff、截断范围等可继续判断的事实。
- 工具定义、执行授权、确认策略和本轮模型可见集合容易被混为一个概念。
- 大结果若只有截断标记而没有可执行 continuation，模型看似获得结果，实际无法继续。

因此本轮研究没有从“再增加几个工具”开始，而是把问题拆成四个独立目标：

1. 模型是否容易选对工具。
2. 模型是否容易生成合法参数。
3. 工具结果是否足以支持下一步判断。
4. 在任务正确的前提下，定义和交互消耗是否合理。

## 2. 设计来源

### 2.1 项目内部原则

工具系统必须服从 AgentArbor 的功能所有权边界：ToolCenter 只负责定义、授权校验、确认、执行和结果归一化；Ordinary Agent 拥有自己的运行状态、事件、持久化与完成语义。不能为了工具优化再造统一 runner、第二套业务事实或全局动态权限状态。

工具系统同时遵循以下分离：

- frozen catalog：run 创建时冻结的工具定义集合。
- execution allowed：本轮真正允许执行的工具集合。
- confirmation policy：副作用调用如何确认。
- model active set：当前模型请求实际看到的工具集合。

减少模型可见定义不能扩大执行权限，加载定义也不能绕过确认。

### 2.2 外部实现参考

研究参考了 Claude Code 等成熟 coding agent 的公开工具面与可观察行为，吸收的是通用设计原则，而不是逐项复制：

- 使用短、稳定、可预测的 canonical name。
- 文件读取、路径发现、内容搜索和命令执行保持清楚分工。
- 命令工具承担通用执行环境，不把常见 shell 命令拆成大量微工具。
- 长输出必须能够继续读取，结果不能只留下不可执行引用。
- 模型可见性、执行权限和确认分别处理。

Claude Code 的工具发现机制没有直接进入 0.3.1。AgentArbor 当前基础工具面较小，而 MCP 长尾工具已有独立的冻结、成本门控和渐进曝光边界；在没有真实规模数据前再增加 `ToolSearch`，会增加协议和测试负担。

### 2.3 不向前兼容的研究边界

五个候选属于同一轮实验，不承担旧候选 schema 的兼容义务。最终方案删除了没有正式消费者的实验性兼容字段和 alias，避免模型同时学习多套输入方式。已经成为正式能力且有真实消费者的契约，仍必须通过版本化迁移处理，不能借“简化”任意删除。

## 3. 五个候选如何演进

| 候选 | 研究重点 | 得到的经验 | 主要不足 |
| --- | --- | --- | --- |
| C01 · Pi Baseline | 验证 Pi 原生 runtime 下的基础工具闭环 | 证明迁移后的真实模型、工具和快照链路可测 | 工具暴露和结果信息价值不足，整体成本最高 |
| C02 · Definition Boundary | 强化定义边界和工具结果事实 | 工程完成度高，盲审排名第一 | 名称与最终模型工具面仍不够简洁 |
| C03 · Canonical Surface | 统一 canonical name 与基础职责 | 调用次数趋势较好，命名方向成立 | 定义和总 Token 仍偏高，历史输入面仍较宽 |
| C04/C04.1 · Claude-style Surface | 参考成熟 coding agent，收窄 schema | 工程任务正确性、Token 和定义成本优于 C03 | 默认工具仍有 12 个，`List/Delete` 与现有能力重叠 |
| C05 · Minimal Surface | 保留正交核心，删除低价值重叠和兼容字段 | 默认模型工具数降至 10，写结果事实完整，Token 最低 | 初版存在未被模型样本触发的 `Glob` continuation 缺陷 |

这条演进路线说明，C05 不是从 C01 直接“删工具”得到的。它吸收了 C02 的定义与事实边界、C03 的 canonical naming、C04.1 的精简 schema，再对默认工具面做最后收口。

## 4. 0.3.1 最终设计

### 4.1 工具职责

| 工具 | 单一职责 | 关键边界 |
| --- | --- | --- |
| `Read` | 读取文件内容 | 有界窗口，截断时提供下一位置 |
| `Glob` | 按路径模式发现文件 | continuation 保留 pattern、path、limit 与 offset |
| `Grep` | 按内容搜索 | continuation 保留查询、过滤条件与下一 offset |
| `Write` | 创建或完整写入文件 | 返回 changed、前后 hash、bytes 与 diff 事实 |
| `Edit` | 对既有文本执行精确替换 | `oldText` 必须唯一匹配；写前校验读取状态 |
| `Shell` | 执行前台或后台命令 | 统一确认、退出码、stdout/stderr、超时与进程事实 |
| `ProcessRead` | 查询已登记后台进程 | 使用稳定 process identity，不按命令文本猜测 |
| `ProcessStop` | 停止已登记后台进程 | 返回实际停止结果，不把请求成功当作进程已结束 |

### 4.2 输入契约

- canonical definition 只保留名称、客观 description、完整 object JSON Schema 和必要执行元数据。
- 可由 schema 表达的约束必须进入 schema，不能依赖 prompt 或错误后的猜测。
- `Edit` 只保留 `path + edits[].oldText/newText`；零匹配、多匹配和重叠编辑明确失败。
- 不通过名称、描述关键词或字段形状推断权限、副作用或 provider 能力。
- run 冻结 definition hash；定义或 executor 发生漂移时，不使用兼容 fallback 偷偷执行。

### 4.3 写入纪律

修改既有文件前必须经过 `Read`。写入工具保存读取时的文件状态，并在实际修改前检查目标是否已经变化；若读取已陈旧，则拒绝覆盖。这不是替模型决定编辑内容，而是保护并发写入的一致性边界。

`Write` 和 `Edit` 的成功结果必须包含模型可继续验证的事实，而不是只返回“成功”：

- 是否实际发生变化；
- 修改前后内容 hash；
- 修改前后字节数；
- 规范 diff 或 diff 无法内联时的明确边界。

### 4.4 结果与 continuation

`ToolCallResult` 是唯一执行事实。模型消息和 UI 都从它单向投影，不能各自生成另一套结果。

producer continuation 与 transport retention 分开：

- `Read / Glob / Grep` 自己知道如何分页，应返回原工具可重放的完整 `nextInput`。
- producer 的下一页必须保留原查询条件并保证位置前进。
- 不能把 `Glob` 的下一页错误投影成 `Grep`，也不能返回缺少必需字段的死 continuation。
- 其他无法安全分页的大结果由 `ReadOutput` 读取保留证据；它不能重放原副作用调用。

### 4.5 条件曝光

八个 workspace 工具构成默认基础面。`HttpRequest`、`ReadOutput`、附件工具、MCP 和其他能力必须同时满足真实 executor、run 冻结授权和模型协议能力，才进入本轮可见集合。

对 MCP 长尾工具，0.3.1 保留基于真实定义成本的渐进曝光机制，但它只改变当前模型请求的 active set，不改变 frozen catalog、execution allowed 或 confirmation policy。基础 workspace 工具不进入这套延迟加载。

### 4.6 同轮并行语义

Ordinary 把同一 assistant turn 返回的所有工具调用视为模型表达的一组独立工作，并统一交给 Pi 并行执行。调用依赖不由工程层根据工具名称、read/write 分类或 Shell 命令文本推断：模型需要先查看 A 的结果再决定 B 时，应自然地在下一 turn 发出 B。

并行不削弱机械边界。每个调用仍独立经过 schema、冻结授权、确认、取消和结果交付；一个调用失败不自动取消同批其他调用。完成事件可按真实完成顺序出现，但进入下一次模型请求和 Pi Session 的 tool result message 保持 assistant 原始调用顺序。写入冲突由读取状态校验、陈旧写拒绝和工具自身的一致性契约处理，而不是用整批串行掩盖。

## 5. 评测方案

### 5.1 隔离方式

评测器位于 `codex/eval`，不编译进候选。每个 trial：

1. 从候选源码构建真实 Node 运行产物。
2. 在独立临时配置目录和全新 fixture workspace 中启动真实 Panel/Ordinary Agent 入口。
3. 禁用用户 Skills、Sub-Agent、MCP 和 Web Search，避免机器环境污染内建工具对比。
4. 使用自动确认，消除人工等待对调用过程的影响。
5. 保存候选 commit、源码指纹、任务版本、workspace 前后 hash、run snapshot 和归一化指标。
6. trial 结束后关闭运行时，下一次从干净 workspace 开始。

候选源码指纹在 trial 前复核；源码变化会使当前实验失效。API key、授权头和密钥路径不进入 manifest 或 Git。

### 5.2 测试集

正式结论使用两个独立任务集，每组各有低、中、高三个复杂度：

| 任务 | 类型 | 主要观察点 |
| --- | --- | --- |
| M1 | 结构化事实提取 | 文件发现、读取、排序和最终证据完整性 |
| M2 | 局部缺陷修复 | 定位、最小修改和测试验证 |
| M3 | 工程调查 | 搜索、证据引用和不确定性表达 |
| N1 | 多文件事实汇总 | 跨文件发现和字段完整性 |
| N2 | 边界规范化修复 | 精确编辑、隐藏边界和变更范围 |
| N3 | 跨文件修复 | 实现、回归测试和多步工程闭环 |

任务契约后续升级为 `tool-benchmark-tasks/v2`：grader 的硬性文件范围必须在用户提示中明确披露。旧 N2 中未披露的限制不再用于评价模型或工具的范围纪律。

### 5.3 模型与重复

- 模型：DeepSeek V4 Pro、GPT-5.6 Sol。
- 思考模式：不显式设置，由模型自行决定。
- 确认策略：自动确认。
- 重复次数：每个候选、每个任务至少 5 个有效样本。
- 无效基础设施样本：排除并补跑，不进入正确率或 Token 均值。
- 模型速度：不属于本研究的评价维度，不用于排序或推荐。

### 5.4 指标顺序

评测不构造任意加权总分，按以下顺序判断：

1. 数据是否有效、证据是否完整。
2. 任务是否通过可见测试、隐藏检查和明确的变更范围。
3. 工具参数是否满足 schema，工具结果与 continuation 是否可消费。
4. 在正确样本中比较工具调用、总 Token、工具定义 Token 和重复调用。

低调用、低 Token 不能补偿错误结果。provider 报告的模型 Token 与 AgentArbor 本地计算的工具定义/包络 Token 分开记录，不能相加伪造账单口径。

## 6. 评测结果

### 6.1 C05 与 C04.1 同模型比较

| 模型 | 候选 | 功能通过 | 平均工具调用 | 平均总 Token | 平均定义 Token |
| --- | --- | ---: | ---: | ---: | ---: |
| DeepSeek V4 Pro | C04.1 | 30/30 | 7.23 | 26,175 | 11,169 |
| DeepSeek V4 Pro | C05 | 29/30 | 6.87 | 23,738 | 9,616 |
| GPT-5.6 Sol | C04.1 | 30/30，修正任务口径 | 11.10 | 53,828 | 10,461 |
| GPT-5.6 Sol | C05 | 30/30 | 11.70 | 43,371 | 8,502 |

C05 相对 C04.1：

| 模型 | 调用变化 | 总 Token 变化 | 定义 Token 变化 |
| --- | ---: | ---: | ---: |
| DeepSeek V4 Pro | -5.1% | -9.3% | -13.9% |
| GPT-5.6 Sol | +5.4% | -19.4% | -18.7% |

可以确认的共同结论是总 Token 和定义 Token 下降。调用次数方向不一致，因此不能宣传 C05 一定减少工具调用。

DeepSeek V4 Pro 的唯一有效失败发生在 N2：模型只修改了允许的源码文件，工具调用和 `Edit` schema 均正常，但错误地扩大了 slug 规范化规则。这是模型业务实现错误，必须计为失败，但不构成恢复 `List/Delete` 或旧 `Edit` 字段的理由。

### 6.2 GPT-5.6 Sol 五候选趋势

| 候选 | 功能正确 | 平均调用 | 平均总 Token | 平均定义 Token |
| --- | ---: | ---: | ---: | ---: |
| C01 | 30/30 | 9.87 | 62,953 | 缺失 |
| C02 | 30/30，修正任务口径 | 10.80 | 56,651 | 12,312 |
| C03 | 30/30 | 10.37 | 56,239 | 12,876 |
| C04.1 | 30/30，修正任务口径 | 11.10 | 53,828 | 10,461 |
| C05 | 30/30 | 11.70 | 43,371 | 8,502 |

这组历史数据跨越任务契约 v1 到 v2，只用于观察趋势，不是严格相同提示词的配对实验。趋势仍然清楚：C05 的 GPT 总 Token 和定义 Token 最低，但平均调用最高。它赢在每轮工具面和上下文成本，不赢在探索轮数。

## 7. 匿名盲审与缺陷闭环

模型评测完成后，五个候选隐藏身份进行工具设计盲审，评分完成后才揭盲：

| 盲审身份 | 候选 | 分数 | 结论 |
| --- | --- | ---: | --- |
| D | C02 | 86 | 当前工程完成度最高 |
| C | C05 | 78 | 工具面和写结果事实更符合目标，但初版未完全闭环 |
| E | C04.1 | 76 | 稳定清晰，默认工具面仍可收敛 |
| A | C03 | 72 | canonical 方向成立，输入面仍偏重 |
| B | C01 | 52 | 工具暴露和结果信息价值不足 |

盲审分数没有被当作自动选举器。C02 的高分说明它是重要工程参照；C05 被选为 0.3.1，是因为它代表已验证的演进方向，并且发现的问题可以在不扩大 schema 的前提下修复。

盲审发现 C05 的 `Glob` 在 output-budget 二次裁剪时会错误生成 `Grep` continuation，且缺少必需的 `pattern`。60 个有效模型样本没有触发该大结果分页路径，但代码审查证明它是真实缺陷。

闭环修改包括：

- `Glob` 和 `Grep` 分别生成自己的 continuation，保留完整查询和下一位置。
- 删除 registry 已不暴露的 `List` 实现与专用测试，避免死代码回流。
- 新增生产 `createAgentToolRegistry` 契约测试，锁定八个默认 workspace 工具并禁止 `List/Delete`。
- 新增 output-budget continuation 回归测试。

证据口径必须诚实：双模型 60 个有效样本对应盲审修复前的 C05 源码指纹；修复后的候选和 0.3.1 主线通过 build 与确定性回归，但没有伪装成重新完成了一轮双模型全量评测。

## 8. 为什么最终选择 C05

选择依据按优先级排列：

1. 正确性仍是第一门槛。GPT-5.6 Sol 全部通过；DeepSeek 的单次失败属于业务语义实现，而非工具不可用。
2. 两个模型一致显示定义和总 Token 下降，收益方向可重复且能归因于较小 schema。
3. 八个 workspace 工具职责正交，没有为了数量继续合并 `Read/Glob/Grep`。
4. 写结果、读取前置和陈旧写拒绝提升了工程任务的可验证性。
5. 盲审缺陷已由确定性测试闭环，没有通过增加兼容层掩盖。

没有采用的方向：

- 不恢复 `List/Delete` 或旧 `Edit` 兼容字段。
- 不因 C03 调用次数较低就迁回更宽的默认工具面。
- 不继续删除基础工具来追求更小数字。
- 不以模型速度、服务可用性或主观单次体验决定工具版本。
- 不在当前规模下建设 `ToolSearch`。

## 9. 证据边界与复现

`main` 中的本文只负责解释，不复制评测事实。独立分支 `codex/eval` 持有：

- `src/app/tool-benchmark/`：候选构建、隔离 trial、指纹、指标与 grader。
- `src/app/tool-benchmark-ui/`：评测过程面板。
- `docs/研究资料/工具评测/工具调用评测任务集*.md`：M/N 任务契约。
- `docs/研究资料/工具评测/工具调用评测指标.md`：有效性、正确性和成本口径。
- `docs/研究资料/工具评测/工具系统候选C05双模型全量评测报告.md`：C05 结果。
- `docs/研究资料/工具评测/工具系统五候选盲审报告.md`：匿名审查与修复记录。

评测器自身的验证入口如下。命令应在 `codex/eval` 对应 worktree 中执行：

```powershell
pnpm build:benchmark-tools
node --test dist/app/tool-benchmark/*.test.js
```

逐次运行产生的完整 workspace、snapshot 和模型正文保存在本地忽略目录 `benchmark-artifacts/`，不进入 `main` 或 Git。长期归档应使用独立制品存储并以实验 ID、SHA-256 和 manifest 索引，不能把大体积原始产物塞入产品主线。

## 10. 局限与后续观察

- 每个模型、任务、候选通常只有 5 个有效重复，足以识别大方向，不足以消除模型随机性。
- 历史候选跨越任务契约 v1/v2，旧数据只能作为趋势，不能用于细微排名。
- C05 盲审修复后的源码没有重跑 60 个模型样本；当前证据是修复前模型评测加修复后确定性回归。
- 测试集覆盖本地文件、搜索、编辑、命令和工程验证，不代表所有真实桌面任务。
- `exactRepeatCount` 仍然偏高；下一轮应研究重复探索和结果信息密度，而不是继续横向删工具。
- MCP 渐进曝光应在真实长尾工具规模下单独评测，不能从八个 workspace 工具的结果外推。

0.3.1 的合理后续不是立即设计 C06，而是在真实工程任务中观察三件事：重复读取是否下降、失败结果是否足以让模型自主恢复、不同模型是否继续稳定理解精确 `Edit` 和 continuation 契约。只有这些轨迹出现可复现问题，下一轮工具设计才有真实出生依据。

## 11. 长期判断与演进门槛

### 11.1 当前成熟度判断

0.3.1 已经可以作为长期工具架构的第一版稳定基线，而不是等待下一轮试验替换的临时候选。当前最有价值的成果不是工具数量从 12 个降到 10 个，而是以下边界已经清楚：

- `Read / Glob / Grep` 的职责正交，基础文件探索不依赖多模式万能 schema。
- 定义、执行授权、确认策略和模型 active set 分别冻结与解析。
- 写入前读取和陈旧写拒绝形成明确的一致性边界。
- `ToolCallResult` 保留执行事实，模型与 UI 只做单向投影。
- producer continuation 和 transport retention 各自承担真实职责。
- 条件能力只在 executor、授权与协议能力同时满足时曝光。

这些边界适合长期保留。未来即使增加工具，也不应破坏它们或恢复名称推断、平行结果 envelope、全局动态权限等旧问题。

0.3.1 仍不是最终形态。现有评测证明它适合作为主线，但没有覆盖删除密集任务、大规模重构、超大仓库搜索和大规模 MCP catalog。后续应把它视为稳定观察基线，而不是宣称所有工具问题已经解决。

### 11.2 三个仍未完全确定的取舍

#### `Delete` 是否应长期由 `Shell` 承担

当前不暴露独立 `Delete`，可以减少默认定义和低价值重叠；但这会把常见的破坏性文件操作放进通用命令环境。长期风险包括：目标路径和删除范围不再天然结构化、确认摘要更依赖命令解析、执行结果不如专用工具容易归一化。

当前测试集没有充分覆盖删除类工程任务，因此“由 `Shell` 删除”只能视为当前合理选择，不能写成永久结论。只有真实任务持续出现下列证据，才考虑恢复独立 `Delete`：

- 模型频繁生成平台不兼容或范围不清的删除命令。
- 删除确认无法稳定表达实际目标和影响范围。
- 删除后状态需要额外 `Glob/Shell` 才能反复确认，形成明显调用浪费。
- 通用命令结果无法满足删除审计或结构化错误处理。

若没有这些证据，不因“文件工具应该完整”而恢复 `Delete`。

#### 精确 `Edit` 是否足以覆盖长期工程任务

当前精确唯一匹配设计简单、可靠、容易验证，适合局部修复，也是 0.3.1 应继续保持的默认编辑能力。它可能在重复代码、大范围重命名、多个关联文件或结构化重构中显得笨重。

后续若真实轨迹显示模型频繁通过临时脚本绕过 `Edit`，或因多匹配失败反复执行 `Read/Grep/Edit`，可以研究独立 `Patch`。新增能力必须满足：

- 有多个稳定真实任务证明精确 `Edit` 无法经济完成，而不是单次模型偏好。
- `Patch` 有清楚的补丁格式、部分失败语义、冲突事实和可验证结果。
- 不把 `dryRun`、occurrence、range、anchor 等多套表达重新堆回 `Edit`。
- 新工具与 `Edit` 的选择边界可以用客观职责说明，不依赖关键词路由。

优先新增正交能力，而不是把当前可靠工具扩成分支繁多的万能编辑器。

#### `ToolSearch` 何时才值得建设

八个 workspace 工具不需要 `ToolSearch`。MCP 长尾工具已经有 frozen catalog、真实成本门控和 active-set 边界，但是否需要面向模型提供显式搜索/加载控制，仍必须由规模数据决定。

只有同时出现以下情况，才进入正式设计：

- 真实 run 中 MCP 定义成本持续占据显著上下文，而不是偶发峰值。
- 全量曝光下出现可复现的选错、漏选或定义成本问题。
- 延迟完整定义后存在明确净 Token 收益，并且任务完成率不下降。
- provider、run 恢复、delegated Agent 和确认边界都有可验证的一致行为。

即使建设，`ToolSearch` 也只能改变下一次模型请求的 active set，不能连接或执行远端工具，不能扩大 frozen execution authorization，更不能变成按关键词替模型选择工具的语义路由器。

### 11.3 下一阶段的真正重点

C05 的双模型结果对工具调用次数给出了不同方向，但都显示 Token 下降。这意味着下一阶段瓶颈更可能位于结果信息密度和模型探索，而不是工具名称或数量。

应优先观察：

- `Read/Grep/Glob` 一次结果是否提供了足够的范围、完整性和跳过事实。
- “没有匹配”“部分跳过”“输入非法”“结果截断”是否被清楚区分。
- continuation 是否被模型正确消费，是否存在重复读取同一页。
- 写入失败是否提供足够事实让模型自主调整，而没有注入固定恢复建议。
- 精确重复调用来自模型探索、结果信息不足，还是评测归一化误判。

优化目标不是机械压低调用次数。额外一次验证调用可能提高正确性；真正需要减少的是没有获得新信息的重复调用，以及由模糊结果导致的反复搜索。

### 11.4 分阶段路线

#### 阶段一：冻结与观察

- 保持 0.3.1 默认工具面和 schema 稳定，不立即启动 C06。
- 在真实工程任务中记录有界调用计数、定义成本、结果尺寸、错误分类、continuation 和重复调用事实。
- 对失败轨迹做人工分类，区分模型语义错误、工具输入错误、结果信息不足和执行缺陷。
- 使用确定性测试守住权限、陈旧写、分页、结果完整性和进程清理。

#### 阶段二：结果质量优化

- 只针对可复现轨迹改善现有工具的事实字段和错误区分。
- 优先减少无新信息的重复读取与搜索，不改变工具职责。
- 使用同一任务、同一模型和同一任务契约做配对对照；正确率仍是第一门槛。
- 结果改进若增加大量定义文本或 schema 分支，需要证明净收益。

#### 阶段三：按证据出生新能力

- 删除类任务证明通用命令边界不足时，评估结构化 `Delete`。
- 大型重构证明精确编辑不足时，评估独立 `Patch`。
- MCP 长尾规模证明全量定义不可持续时，评估 `ToolSearch`。
- 每项能力独立形成候选和任务集，不把三个方向打包成下一版大改。

### 11.5 停止条件

工具系统不需要无限版本化。若 0.3.1 在真实任务中同时满足以下条件，应停止工具面重设计，把资源转向 Ordinary Agent 的任务理解、验证和上下文能力：

- 基础工具 schema 无持续无效输入。
- 任务失败主要来自业务理解，而不是工具不可达或结果不可消费。
- continuation、陈旧写拒绝和进程工具没有系统性死路。
- 重复调用没有形成显著正确性或 Token 回归。
- 新增工具无法在正确率不下降的前提下证明净收益。

长期维护的目标不是拥有更多或更少的工具，而是让模型以稳定契约获得足够事实，并让工程层只守住授权、确认、一致性、证据和执行边界。
