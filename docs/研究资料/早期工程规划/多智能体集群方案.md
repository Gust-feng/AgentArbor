# AgentArbor 多智能体集群方案 v0.1

> AgentArbor 不是一个简单生成 Agent 的工具。
> 它是一套由多智能体集群协作完成需求成像、能力调用、构建执行、测试验收与经验沉淀的 Agent 生长系统。

---

## 0. 核心定义

AgentArbor 的目标不是“用户说什么，就生成什么”。

它更像一个孕育系统：

```text
用户给出一个模糊愿望
  ↓
系统看清意图、补齐上下文、审计可运行性
  ↓
必要时调研、探测、分析数据
  ↓
生成符合 AgentArbor 标准的 Agent Package
  ↓
测试、验收、交付
  ↓
沉淀能力资产，进入下一轮生长
```

一句话概括：

> **AgentArbor 是一个由多智能体群落协作完成 Agent 孕育、验证、交付与进化的生长型系统。**

它不是工作流平台。
它是一个让 Agent 从模糊愿望里长出来的生态。

---

## 1. 设计原则

### 1.1 Agent 集群不是会议室

多 Agent 最容易做成假热闹：

```text
A：我认为应该这样。
B：我同意。
C：我补充一点。
D：总结得很好。
```

这种东西没有价值。

AgentArbor 的 Agent 集群必须遵守一条铁律：

> **每个 Agent 必须产生结构化交付物，否则它就不该存在。**

Agent 不是为了“说话”而存在。
它是为了留下判断、证据、计划、测试结果、失败记录和可复用经验。

---

### 1.2 每个集群必须有明确边界

不同集群负责不同阶段：

```text
看清楚       → Council Cluster
查明白       → Research Cluster
理数据       → Data Cluster
造出来       → Forge Cluster
跑起来       → Trial Cluster
验合格       → Gate Cluster
留下来       → Asset Cluster
```

它们不是同时开会。
而是由 Core 按任务需要调度。

---

### 1.3 先判断能不能做，再开始做

AgentArbor 不能听见需求就开工。

尤其是这些任务：

```text
需要 API Key
需要用户数据
需要登录授权
需要第三方平台
需要长期运行
需要联网抓取
需要真实推送
需要部署环境
```

必须先经过：

```text
Readiness Auditor：可运行性审计
Probe Agent：最小可行探测
```

否则系统很容易做到一半才发现：

```text
没 Key
没数据
没权限
网站打不开
验证码拦住了
提醒渠道不存在
用户其实要的不是这个
```

这不是执行失败。
这是开工前就没看路。

---

### 1.4 结构化交接，而不是靠聊天记录传递

每个集群之间不能靠“上一轮对话”传递上下文。

必须靠结构化文件交接：

```text
Council Cluster   → requirement-imaging-report.yaml
Seed Collector    → context-pack.yaml
Readiness Auditor → arbor.readiness.yaml
Probe Agent       → probe-report.yaml
Research Cluster  → research-pack.yaml
Data Cluster      → data-profile.json / metrics.yaml
Forge Cluster     → Arbor Package
Trial Cluster     → trial-report.json
Gate Cluster      → acceptance-report.md
Asset Cluster     → capability.assets.yaml / growth-record.md
```

聊天记录是雾。
结构化交付物才是桥。

## 2. 总体架构

```text
用户目标
  ↓
Cluster Router 群落调度器
  ↓
Council Cluster 前置成像集群
  ↓
Readiness / Probe 可运行性审计与最小验证
  ↓
Research Cluster 深度调研集群（按需）
  ↓
Data Cluster 数据分析集群（按需）
  ↓
Blueprint Synthesizer 蓝图综合
  ↓
Forge Cluster 执行构建集群
  ↓
Trial Cluster 测试验证集群
  ↓
Gate Cluster 验收审查集群
  ↓
Asset Cluster 能力沉淀集群
  ↓
Growth Engine 生长引擎
```

本质上，AgentArbor 要让每一次生成都变成一次有记录、有验证、有沉淀的生长。

不是：

```text
用户说一句 → AI 生成一堆代码
```

而是：

```text
愿望进入系统 → 成像 → 探路 → 建造 → 试炼 → 验收 → 留种 → 再生长
```

## 3. 核心集群设计

# 3.1 Council Cluster：前置成像集群

Council Cluster 是 AgentArbor 的眼睛。

它负责回答：

```text
用户到底要什么？
这件事属于什么领域？
用户没有说清楚的地方有哪些？
哪些可以默认？
哪些必须追问？
这件事要跑起来缺什么？
是否需要最小验证？
应该生成什么类型的 Agent？
```

## 成员设计

```text
Intent Cartographer        意图制图师
Domain Interpreter         领域解释者
Seed Collector             种子采集官
Readiness Auditor          可运行性审计官
Probe Agent                探路蜂
Asset Librarian            能力资产馆员
Assumption Builder         假设建模师
Skeptic                    怀疑者
Blueprint Synthesizer      蓝图综合师
```

## 职责拆解

| Agent | 核心职责 | 产出 |
|---|---|---|
| Intent Cartographer | 把用户模糊目标拆成可能意图 | intent-candidates |
| Domain Interpreter | 识别该领域真正难点 | domain-insights |
| Seed Collector | 主动向用户采集资料、偏好、边界 | context-pack.yaml |
| Readiness Auditor | 判断真实运行还缺什么 | arbor.readiness.yaml |
| Probe Agent | 做最小验证，如访问 URL、测试 API、检查环境 | probe-report.yaml |
| Asset Librarian | 查已有能力资产和模板 | reusable-assets |
| Assumption Builder | 在信息不足时建立可回滚默认假设 | assumptions |
| Skeptic | 质疑方案，防止过度工程和脑补 | risk-notes / disputes |
| Blueprint Synthesizer | 收束成可执行蓝图 | agent.blueprint.yaml |

## 关键产物

```text
Requirement Imaging Report       需求成像报告
Context Pack                     上下文包
Runability Contract              可运行性契约
Probe Report                     探测报告
Blueprint Draft                  初始蓝图
```

## 3.1.1 Seed Collector：种子采集官

Seed Collector 是前置集群里最像“人”的一环。

它不是普通的提问 Agent。
它负责主动把用户脑子里的材料、偏好和边界捞出来。

它问的不是：

```text
请补充完整需求。
```

而是：

```text
这件事如果要长得像你，需要哪些种子？
```

### 以小说生成 Agent 为例

用户说：

```text
帮我做一个小说生成 Agent。
```

Seed Collector 应该收集：

```text
1. 有没有已有资料：大纲、人物、世界观、章节草稿、样章
2. 希望偏哪种方向：灵感生成、章节续写、长篇管理、网文连载
3. 有哪些禁止事项：不要套路文、不要仿写具体作者、不要低幼表达
```

它不能甩给用户十几个问题。
它最多问三类高价值问题。

### Seed Collector 的原则

```text
1. 只采集高价值上下文，不做审讯
2. 问题少于 3 个
3. 每个问题都必须说明为什么重要
4. 用户不回答也能继续，但要记录默认假设
```

### Context Pack 示例

```yaml
context_pack:
  raw_goal: 帮我做一个小说生成 Agent

  user_materials:
    outline: null
    characters: null
    worldbuilding: null
    sample_texts: []
    references: []

  user_preferences:
    language: 中文
    preferred_mode: 长篇创作助手
    tone: 未指定
    genre: 未指定
    interaction_style: 用户给方向，Agent 负责规划、生成、修订

  negative_preferences:
    - 不仿写具体作者
    - 不默认生成低质套路文

  inferred_needs:
    - story_bible
    - chapter_planner
    - character_memory
    - consistency_checker
    - revision_agent

  external_research_needed: false

  assumptions:
    - 用户没有提供资料，先生成通用版本
    - 用户没有指定类型，默认支持多类型扩展
    - 用户没有指定部署方式，默认生成 CLI + 可扩展 Web 结构
```

Seed Collector 让 AgentArbor 的生成物不只是“正确”，而开始有一点“像用户”。

## 3.1.2 Readiness Auditor：可运行性审计官

Readiness Auditor 负责判断：

> **这个任务现在有没有资格开工？**

它审计的不是需求美不美，而是现实条件够不够。

### 它需要识别的阻塞项

```text
缺 API Key
缺用户数据
缺权限授权
缺目标 URL
缺运行环境
缺第三方平台配置
缺提醒渠道
缺日程来源
缺真实测试条件
缺部署方式
```

### Runability Contract 示例

```yaml
runability_contract:
  task: 生成一个可运行的 AgentArbor Agent

  required_inputs:
    - agent_goal
    - target_runtime
    - model_provider
    - test_api_key

  required_permissions:
    - 是否允许调用模型 API
    - 是否允许在本地创建文件
    - 是否允许运行测试命令

  required_secrets:
    - name: LLM_API_KEY
      reason: 没有测试 Key，Agent 只能生成代码，无法验证真实运行
      storage: secret_vault
      required_for: runtime_test

  blocking_items:
    - test_api_key_missing

  can_continue_without_blocking_items: partial

  allowed_progress:
    - 生成代码骨架
    - 生成 mock 测试
    - 生成 README
    - 生成配置模板

  forbidden_progress:
    - 宣称真实运行通过
    - 调用真实模型
    - 生成最终可用报告
```

Readiness Auditor 的价值在于：

> 它让 AgentArbor 不会把“还不能跑”的东西伪装成“已经完成”。

---

## 3.1.3 Probe Agent：探路蜂

Probe Agent 负责做最低成本验证。

它不是正式执行任务。
它只是回答一句话：

> **这条路是不是通的？**

### 适用场景

```text
爬虫 Agent
API 集成 Agent
第三方平台 Agent
提醒 Agent
自动化监控 Agent
数据采集 Agent
```

### 以爬虫 Agent 为例

用户说：

```text
帮我做一个每天自动爬数据的 Agent。
```

Probe Agent 要先检查：

```text
1. 目标 URL 能不能访问
2. 是否需要登录
3. 是否存在验证码
4. 是否动态渲染
5. 是否存在公开 API
6. 是否有 robots / 条款限制
7. 是否能稳定抽取最小样本
8. 是否适合无人值守每日运行
```

### Probe Report 示例

```yaml
probe_report:
  target: example.com/data
  result: blocked

  findings:
    - 首页可访问
    - 数据页需要登录
    - 登录后存在验证码
    - 页面数据通过动态接口加载
    - 未发现公开稳定 API

  feasibility:
    status: high_risk
    reason: 自动化访问可能被验证码和风控拦截

  recommended_strategy:
    - 优先寻找官方 API
    - 允许用户提供导出的 CSV/Excel
    - 允许用户手动上传数据
    - 不建议承诺每日自动稳定爬取

  can_build:
    - 数据处理模块
    - 定时任务框架
    - 手动导入模式
    - 可插拔采集器接口

  cannot_build_yet:
    - 稳定自动爬虫
    - 无人值守抓取
```

Probe Agent 的意义是：

> **先验证道路，再设计车辆。**

# 3.6 Gate Cluster：验收审查集群

Gate Cluster 是 AgentArbor 的判断力。

测试通过，不代表可以交付。
能运行，不代表有用。

Gate Cluster 负责回答：

> **这个结果能不能交付给用户？**

## 成员设计

```text
Requirement Match Agent       需求匹配审查
UX Review Agent               使用体验审查
Security Review Agent         安全审查
Boundary Review Agent         权限边界审查
Maintainability Agent         可维护性审查
Acceptance Judge              最终验收裁决
```

## 输出物

```text
acceptance-report.md
delivery-decision.json
known-limitations.md
user-facing-summary.md
```

## 示例：爬虫 Agent

Trial Cluster 可能说：

```text
代码可以运行。
```

Gate Cluster 可能说：

```text
不能交付为“稳定每日自动爬取 Agent”。
因为目标网站存在验证码和风控。
只能交付为“半自动采集 + 手动导入兜底方案”。
```

这就是验收的价值。
它保护系统不自欺欺人。

## 5. 多 Agent 对话机制

AgentArbor 的 Agent 可以互相讨论。
但不能自由闲聊。

必须使用：

> **Blackboard + Deliberation Protocol**

---

## 5.1 Blackboard：共享黑板

所有 Agent 把判断写进黑板。

```ts
export interface CouncilBlackboard {
  rawGoal: string

  intentCandidates: IntentCandidate[]
  domainInsights: DomainInsight[]
  userMaterials: UserMaterial[]
  assumptions: Assumption[]
  missingInputs: MissingInput[]
  blockingItems: BlockingItem[]
  risks: Risk[]
  reusableAssets: CapabilityAssetRef[]
  missingCapabilities: MissingCapability[]
  disputes: Dispute[]
  decisions: Decision[]
}
```

黑板不是聊天记录。
它是结构化判断池。

---

## 5.2 Deliberation Protocol：审议协议

流程：

```text
Round 1：独立判断
Round 2：写入黑板
Round 3：互相质询
Round 4：冲突归并
Round 5：裁决生成
Round 6：输出结构化交付物
```

关键原则：

> **先独立，再讨论。**

否则第一个 Agent 的判断会污染后面的 Agent。

---

## 5.3 裁决机制

不建议投票。

投票会让平庸答案胜出。

更好的方式是：

```text
多方审议
单点裁决
Core 保留否决权
```

结构：

```text
多个 Agent → Blackboard → Synthesizer → Arbor Core → Final Decision
```

Blueprint Synthesizer 负责综合。
Arbor Core 负责最终放行。

## 6. 状态门控机制

AgentArbor 必须知道任务现在处于什么状态。

---

## 6.1 四种灯

```text
绿灯：信息足够，可以构建并真实验证
黄灯：可以构建原型，但无法完整验证
红灯：缺关键输入，不能继续核心工作
灰灯：任务不可行或风险过高，需要换方案
```

---

## 6.2 五种构建模式

```text
Full Build       完整构建
Prototype Build  原型构建
Mock Build       模拟构建
Spec Build       只生成规格方案
Blocked          阻塞等待
```

---

## 6.3 缺少 API Key 示例

```text
状态：黄灯

可以做：
- 生成代码骨架
- 生成 mock provider
- 生成配置模板
- 生成测试用例

不能做：
- 真实调用模型
- 声称运行通过
- 生成最终验收结论
```

---

## 6.4 日程提醒助手缺少提醒渠道示例

```text
状态：红灯或黄灯

可以做：
- 日程数据结构
- 提醒规则引擎
- 通知渠道接口
- mock 测试

不能做：
- 真实提醒
- 后台长期运行
- 第三方推送集成
```

---

## 6.5 爬虫目标网站有验证码示例

```text
状态：灰灯或黄灯

可以做：
- 手动导入方案
- 官方 API 方案
- 半自动采集器
- 数据处理模块

不能做：
- 承诺每日稳定自动爬取
```

## 10. 核心接口草案

### 10.1 Cluster 接口

```ts
export interface ArborCluster<I, O> {
  id: string
  name: string
  description: string

  canHandle(context: ArborContext): Promise<boolean>

  run(input: I, context: ArborContext): Promise<O>
}
```

---

### 10.2 Agent 接口

```ts
export interface ArborAgent<I, O> {
  id: string
  role: string
  tools: string[]

  analyze(input: I, blackboard: Blackboard): Promise<AgentContribution>

  critique?(blackboard: Blackboard): Promise<AgentCritique>

  produce?(blackboard: Blackboard): Promise<O>
}
```

---

### 10.3 Artifact Bus

```ts
export interface ArtifactBus {
  write<T>(name: string, artifact: T): Promise<void>
  read<T>(name: string): Promise<T>
  list(): Promise<string[]>
}
```

Artifact Bus 很重要。
它让集群之间不靠“我记得刚刚说过什么”，而靠真实文件交接。

## 11. 安全与 Secret 机制

只要用户提供 API Key、Token、Cookie、登录凭证，都不能进入普通工作区。

禁止写入：

```text
README
logs
arbor.lock.json
growth.log
prompt
生成代码
普通配置文件
```

应该使用：

```yaml
secrets:
  - name: LLM_API_KEY
    ref: secret://project/llm_api_key
    used_by:
      - runtime_test
      - eval_runner
```

生成物只保存 `SecretRef`，不保存真实密钥。

这是底线。
AgentArbor 如果要成为严肃系统，Secret 管理不能靠自觉。

## 12. MVP 落地路线

不要第一版就做全。
那会把系统压死。

建议分四期。

---

## Phase 0：协议先行

先写清楚这些格式：

```text
arbor.agent.yaml
arbor.lock.json
agent.blueprint.yaml
context-pack.yaml
arbor.readiness.yaml
probe-report.yaml
research-pack.yaml
data-profile.json
trial-report.json
acceptance-report.md
capability.assets.yaml
```

先有骨骼，再长肉。

---

## Phase 1：最小闭环

只做四个集群：

```text
Council Cluster
Forge Cluster
Trial Cluster
Asset Cluster
```

目标：

```text
用户输入 Agent 想法
→ 系统生成需求成像
→ 生成 Agent 蓝图
→ 生成 Arbor Package
→ mock 测试
→ 沉淀能力资产
```

第一阶段先别追求全自动。
先让闭环活着。

---

## Phase 2：加入 Readiness + Probe

重点解决：

```text
缺 Key
缺数据
缺授权
缺运行环境
外部网站不可访问
第三方平台限制
```

这一步会让 AgentArbor 从“能生成”变成“更可靠”。

---

## Phase 3：加入 Research + Data

让系统具备：

```text
查官方文档
做竞品调研
分析平台限制
理解数据结构
生成指标体系
输出分析报告
```

这一步会让 AgentArbor 开始进入复杂任务。

---

## Phase 4：独立 Gate Cluster

把验收从测试里独立出来。

重点做：

```text
需求匹配
安全边界
可维护性
用户体验
交付判断
```

这一步会让 AgentArbor 开始像一个真正的交付系统。

## 13. 三个典型任务流程

---

## 13.1 小说生成 Agent

```text
用户：帮我做一个小说生成 Agent

Council：
判断为高模糊创作类 Agent

Seed Collector：
询问是否有大纲、人物、世界观、样章、偏好和禁忌

Readiness：
判断无需外部 Key，可黄灯原型构建

Forge：
生成 LongFormNovelAgent

Trial：
测试章节生成、角色记忆、一致性检查

Gate：
判断是否符合“长篇创作助手”定位

Asset：
沉淀 story-bible 模板、角色一致性 eval
```

---

## 13.2 日程提醒 Agent

```text
用户：帮我做一个日程提醒助手

Council：
识别为提醒自动化 Agent

Readiness：
阻塞项：
- 日程来源
- 提醒渠道
- 运行方式

Seed Collector：
只问三个关键问题：
1. 日程从哪里来？
2. 提醒发到哪里？
3. 在哪里运行？

Forge：
若用户未补充，只生成 prototype

Trial：
mock 测试提醒规则

Gate：
禁止声称已实现真实提醒

Asset：
沉淀 reminder-rule 模板和 notification adapter
```

---

## 13.3 爬虫 Agent

```text
用户：做一个每天自动爬数据的 Agent

Council：
识别为自动数据采集 Agent

Readiness：
要求目标 URL、数据字段、频率、授权说明

Probe：
先访问目标网站
检查登录、验证码、动态渲染、robots、接口稳定性

Research：
查官方 API 或替代方案

Forge：
根据 Probe 结果生成：
- 稳定爬虫
或
- 半自动采集器
或
- 手动导入 + 数据处理 Agent

Trial：
沙箱运行最小抓取

Gate：
不允许夸大稳定性

Asset：
沉淀 crawler-probe 模板和反爬风险记录
```

## 14. 风险与防护

### 风险一：Agent 太多，系统变慢

解决：

```text
Cluster Router 按需启动
轻任务走 Light Mode
复杂任务才走 Full Mode
```

---

### 风险二：多 Agent 互相废话

解决：

```text
禁止自由闲聊
必须写 Blackboard
必须产生 Artifact
没有交付物的 Agent 不启动
```

---

### 风险三：过度追问用户

解决：

```text
只问影响架构走向的问题
每轮最多 3 个问题
用户不回答也要有降级路径
```

---

### 风险四：资产库被污染

解决：

```text
Asset Cluster 必须评估复用价值
失败经验进入 failures，不直接进入 capability
能力资产需要版本号和来源
```

---

### 风险五：测试通过但产品不可用

解决：

```text
Trial 和 Gate 分离
测试负责能不能跑
验收负责能不能交付
```

---

### 风险六：密钥泄露

解决：

```text
SecretRef 机制
禁止日志记录真实 Key
禁止进入生成文件
禁止进入 prompt 和 lock
```

---

## 15. 总结：AgentArbor 的群落秩序

AgentArbor 的多智能体集群，不应该像一群人在吵闹。
它应该像一棵树的器官：

```text
Council 是眼睛
Research 是根须
Data 是脉络
Forge 是双手
Trial 是疼痛感
Gate 是判断力
Asset 是年轮
Core 是树干
```

真正成熟的系统，不是永远成功。
而是知道什么时候不能开工，什么时候只能做原型，什么时候该探路，什么时候该承认现实拦住了它。

**AgentArbor 的高级之处，不是它会生成 Agent。**

而是它能在生成之前看见雾，
在执行之中摸到墙，
在失败之后留下年轮，
在下一次生长时不再从零开始。
