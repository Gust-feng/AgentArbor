# ADR-0034：远程协同与选择性同步架构

## 状态

已接受。首版以本地可验证的桌面端、Linux Relay 和 Android 9+ PWA 为交付边界；公网域名、TLS 证书与真机验证在部署验证阶段补充。

## 背景

AgentArbor 需要让同一个用户在手机和电脑之间继续对话、处理待确认动作，并同步软件自己拥有的 Space、笔记和文件。它不是远程桌面，也不是把电脑磁盘镜像到云端。若直接同步整个 runtime 数据库、工作区路径或工具输出，会混淆 feature 所有权，扩大隐私面，并让云端错误地成为第二个 Agent runtime。

用户已确认以下产品边界：

- 手机和电脑属于同一个唯一用户；设备完成双向配对后相互信任，直到显式撤销。
- 两端配对时显示并确认同一个配对码。
- 手机可以发送 Ordinary 消息、取消运行，并作出 `approve_once / deny / guidance` 确认决定。
- 手机可以创建 Space，并同步 AgentArbor 自己创建和维护的数据。
- 暂不做端到端加密；Relay 可以读取同步正文。公网部署仍必须使用 TLS，不能把“无 E2E”解释为允许明文公网传输。

## 决策

### 1. 三端职责

```text
Android 9+ PWA  <──WebSocket/HTTPS──>  Linux Relay  <──WebSocket/HTTPS──>  Desktop Connector
                                                                    │
                                                                    ▼
                         Ordinary / Space / Workbench Assets / Agent Notes
```

- **桌面端**是 Ordinary 执行、确认 continuation、本地 feature 数据和受管文件的权威。远程消息最终仍由桌面端 Ordinary feature 接受和执行。
- **Relay**只拥有配对、设备身份、可撤销信任、持久消息投递、顺序、ACK 和离线队列；不装配模型、工具、Ordinary 或本地 feature。
- **手机端**是面向同一用户的轻客户端，只提交命令并展示桌面端发布的正式投影，不在本地伪造运行终态。
- **Remote Collaboration feature**是独立纵向模块，拥有协议、连接生命周期、本地 outbox/inbox、幂等应用、远程 ID 映射、同步状态与冲突。它只能通过 Host 注入的窄 command/query 端口使用其他 feature，不能读取其他 feature 的 store、registry、SQLite 表或 Panel HTTP。

### 2. 配对与信任

1. 桌面创建短时配对会话，Relay 返回六位配对码与一次性 claim secret。
2. 手机输入配对码加入，Relay 向两端返回同一个配对码供人工核对。
3. 两端分别提交确认；只有双方都确认后才建立信任关系。
4. Relay 为每台设备签发独立、可撤销的高熵 bearer token，只保存 token 哈希。
5. 配对完成后两端按“同一个用户”互信，不对每条普通同步命令增加第二套身份审批。危险本地工具仍必须走 Ordinary 已有确认边界。

配对码不是长期凭据，过期、错误或单边确认都不能建立信任。设备撤销后，其 token 立即失效，未确认投递不再继续发送给该设备。

### 3. 同步数据白名单

允许同步：

- Space 元数据及 `asset_folder`、`workbench_asset` 引用；
- AgentArbor 创建的 `managed_folder` 及其相对路径内文件；
- Workbench Assets 的可同步正文与元数据；
- 全局 Agent Note 和工作区 Agent Note；
- 用户从手机创建或从电脑显式共享的 Ordinary 对话、用户消息、正式回答与必要运行状态；
- 当前确认请求及确认决定所需的完整事实；
- 设备、同步状态、版本与冲突事实。

禁止同步：

- `local_file`、`workspace_folder` 及它们引用的外部内容；
- 外部磁盘绝对路径、工作区根路径和目录扫描结果；
- API Key、模型/provider 配置、Skills、MCP 与命令环境配置；
- reasoning、完整工具输出、stdout/stderr；
- 整个 `runtime/`、SQLite 文件、Session 原始历史或任一 feature 私有仓储。

工作区 Agent Note 的正文允许同步，但 Relay 使用随机 `notebookId` 与用户可见标签映射，不上传 `workspaceRoot`。命令确认是临时控制事实：为让同一用户知情批准，可以包含完整命令、风险、影响资源和必要本地路径；它不进入 Space/笔记同步数据，也不作为长期云端知识资产。

### 4. 可靠投递和幂等

- Relay 为每条持久消息分配接收设备方向上的单调 `sequence`，客户端按 cursor 重放并显式 ACK。
- WebSocket 只负责在线推送；最终投影和未 ACK 消息必须持久化。文本 delta 可以瞬时转发，但不能替代最终回答。
- 每个可重试命令都有稳定 `commandId`。Relay 允许至少一次投递，接收方用 inbox 去重并保存最终 command result。
- 远程 Ordinary 消息直接把 `commandId` 复用为 `submissionId`，利用现有 Ordinary 幂等契约，避免断线重投启动两个 run。
- UI 状态按 `pending -> accepted -> applied | conflict | failed` 推进；桌面 ACK 前，手机不得把本地操作显示为正式业务事实。
- 不宣称跨进程或跨网络 exactly-once。传输重复由 inbox 去重，副作用幂等由 owning feature 的稳定 ID、版本或 CAS 契约保障。

### 5. 冲突

- Agent Notes 与可编辑资产使用完整正文替换和版本/fingerprint CAS。版本不匹配时形成可见冲突，不做静默 last-write-wins。
- Space 创建和引用写入使用显式稳定 ID，重复命令返回既有事实。
- `managed_folder` 内容只允许相对路径，禁止 `..` 越界；同一路径的并发编辑使用内容 fingerprint CAS。
- 对话和审批是桌面权威的命令/投影流，不做双主合并。

### 6. 移动端产品面

首版移动端只有四个主要面：对话、待确认、Space、笔记/设备。默认层只展示正文、当前状态和主要动作；完整命令、路径、风险、版本与冲突信息仅在需要决定时展开。它不复制桌面 Workbench 的工具时间线、设置中心和本地文件选择能力。

首版使用 React PWA 以覆盖 Android 9+ 主流浏览器。需要原生推送、后台保活或商店 APK 时，再用 Capacitor 包装同一前端和协议客户端，不提前维护第二套 UI。

## 不采用

- 同步整个 runtime 或各 feature SQLite 表：破坏所有权，协议不可演进。
- 让 Relay 运行第二套 Ordinary/工具循环：会产生双主执行和确认 continuation 分裂。
- 同步电脑工作区或任意用户文件夹：超出 AgentArbor 自有数据边界。
- 首版使用 CRDT：当前文档量和单用户冲突频率不足以承担其复杂度，CAS 冲突更清楚可测。
- 首版开发原生 Android 客户端：PWA 已满足交互闭环，原生包装留到推送需求出生后。

## 后果

- 远程协同不会污染 Ordinary、Space、Assets 和 Notes 的私有仓储；未来可替换 Relay 部署方式而不重写业务 feature。
- 手机离线、桌面离线和网络重复投递都有明确状态，代价是客户端必须维护 cursor、inbox 和 command result。
- 云端能够读取同步正文；这必须在产品设置中明确告知用户。E2E 加密若未来出生，需要新增密钥生命周期 ADR，不能在传输层临时加密字段伪装完成。
