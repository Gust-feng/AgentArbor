# 工具系统 V3 研究

## 研究问题

工具系统需要同时满足模型能力、权限边界和桌面可观察性。重点不是发明新的工具协议，而是明确哪些事实必须保留、哪些集合可以按请求变化，以及 Pi/MCP/provider 能力如何接入而不污染 Ordinary 业务状态。

## 证据等级与研究边界

- **官方事实**：产品或 API 官方文档明确承诺的公开行为，可以作为外部设计证据。
- **实现证据**：公开 SDK、协议或可观察事件能够证明的当前实现，不等于长期产品承诺。
- **推断**：只能从行为或缺失文档推断的结论，只用于识别未知项，不能直接固化为 AgentArbor 契约。

本研究比较 Claude Code、OpenAI Codex、Trae 与 Qoder 的公开工具面。闭源产品未公开的内建 schema、结果保留和评估机制不作事实猜测；产品安全策略也不直接成为 AgentArbor 的权限事实。

## 主流产品对照

| 产品 | 定义与参数面 | 权限与确认 | 渐进曝光与成本 | 结果与续读 | 可观察性与评估 |
| --- | --- | --- | --- | --- | --- |
| Claude Code | 官方 custom tool 契约包含 name、description、input schema、handler；结果支持 content、structured content 与 error。 | 官方区分工具可见性与 allow/ask/deny，参数级规则仍在执行前判定。 | 官方 Tool Search 可延迟完整定义，`auto` 使用定义上下文占比门控；不支持时回退全量。 | 官方 Bash 对超长输出保留文件并返回预览/路径；Read 使用 offset/limit 续读。 | 官方 OTel 与 hooks 覆盖 tool decision/result、耗时、错误和大小；未发现通用工具质量 eval runner 的公开承诺。 |
| OpenAI Codex | 官方 MCP 配置支持 server instructions、enabled/disabled tools 和工具级 approval；内建工具 schema 不是稳定公开 API。 | 官方把 sandbox 技术能力与 approval policy 分开；destructive annotation 影响确认。 | 官方 Codex 与 API 文档提供 Tool Search：先暴露 namespace/server 信息，主要延迟参数 schema，并兼容不支持的模型/provider。 | 官方 `codex exec --json` 输出工具与文件变更事件；未发现产品级完整输出持久化和统一续读保证。 | 官方 JSONL、OTel tool decision/result 与技能 eval 指南可以组成 trace 和离线检查。 |
| Trae | 官方 MCP 契约保留 name、title、description、inputSchema、outputSchema，结果支持 text 与 structured content。 | 官方要求首次 MCP 连接授权，并提供 Manual、Allowlist、Denylist、Always Run 等命令策略。 | 官方明确所有启用 MCP 工具都会占用总上下文并建议缩减集合；未公开成本门控或延迟 schema 契约。 | 官方工具面板展示过程、结果和 MCP 日志；未公开稳定的大结果 continuation 契约。 | 官方 structured logging、服务日志和终端结果用于诊断；未发现通用事件 API 或工具 eval 承诺。 |
| Qoder | 官方 custom tool 要求 name、description 和 object JSON Schema，并校验未知名、大小写冲突与保留前缀。 | 官方每次调用形成 allow/ask/deny，按 deny、安全检查、ask、allow 的固定优先级解析。 | 官方支持显式 enabled tool 裁剪；未公开按真实成本延迟 schema。不同 API 的空数组含义不一致，不能照搬。 | 官方 custom tool 以 pending action 暂停同一 turn，客户端按 tool-use ID 回传 result/error 后继续；未公开大输出续读协议。 | 官方事件流区分 tool use/result、权限结果和 MCP/custom tool，并支持 SSE replay 与 outcome evaluation 事件。 |

产品共同点不是某一套具体参数，而是：定义与执行权限分开；确认在执行边界判定；大工具面需要可验证的裁剪或延迟机制；结果必须能被继续消费；工具生命周期必须可观察。各产品没有公开承诺的部分不能用同类产品行为补齐。

## 结论

- canonical 工具定义必须保留名称、描述、完整输入 schema，以及 provider 实际提供的 output schema、annotations、来源和稳定 hash；MCP 原始协议名只在 catalog 映射层使用。模型可见投影和成本只计算真正发送的 name、description 与 input schema，不把执行元数据伪装成模型定义。
- 曝光、执行授权、确认是三个正交决策。渐进曝光只能减少当前模型请求的定义，不得减少授权或改变确认。
- core 常驻定义应直接注入；MCP 长尾定义只有在真实 provider catalog 可见、服务已启用且配置完整、缓存定义与惰性 executor 已进入 run 冻结边界且定义成本达到门控时才延迟。成本使用实际模型可见序列化定义计算，不能用 provider/model 名猜测 native tool search；搜索/加载本身不预连接服务器。
- Pi 的 run-local active set 适合承载当前请求的动态可见性；Pi Session 适合保留真实协议历史，但不适合作为权限注册表。live activation marker 不能成为新 root/delegated run 的恢复来源，也不能从公开工具输出重建。
- provider 返回 immediate failure 或缺少 canonical 结果时，保留原始文本并归一化为 ToolCallResult；失败应说明取消、执行失败或 schema/runtime 拒绝，并禁止盲目重试。
- MCP text、structured content、错误与附件必须先形成一份 canonical 结果；structured result 不因 provider 投影限制而被丢弃或复制成多套语义事实。
- 大结果沿既有 ToolOutputStore/read_output 续读，完整正文始终是正式事实，摘要只能是额外展示字段。

## 可观察性与评估

运行时指标只记录 definition hash/token、active/deferred 数量、调用身份、输入/输出大小、耗时、状态、错误分类和续读结果，不保存正文或改变执行事实。离线评估应把以下问题分开：

1. 模型是否选择了能够完成目标的工具。
2. 参数是否满足完整 schema 与运行边界。
3. 结果、错误和 continuation 是否完整可消费。
4. 渐进曝光与全量曝光相比是否真实节省定义 token，且没有降低任务完成率。
5. 权限、确认、同批调用隔离、跨 run reset 和完整证据是否通过确定性回归。

真实模型 A/B 只能评估选择质量和任务结果，不能替代权限、持久化、取消与结果完整性的确定性测试。

## 方案比较

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 全量注入所有 MCP 定义 | 仅作为回退 | 保真但可能吞噬上下文，无法随规模稳定扩展 |
| 按 provider/model 名猜测原生搜索 | 不采用 | 名称不是能力证明，容易产生协议不匹配和隐式失败 |
| 全局动态工具注册表 | 不采用 | 把 run-local 可见性与 durable 权限混为一体，恢复和并发边界不清 |
| MCP 自行重建搜索/加载工作流 | 不采用 | 重复 Pi 的 active set/Session 机械能力，并制造第二套事实 |
| 成本门控 + Pi active set + live marker / cross-run reset | 采用 | 优化局部模型输入，保留真实 transcript，同时让新执行重新应用冻结边界而不继承历史可见性 |

## 未采用的外部做法

- 不把 AI 安全分类器、工具描述或模型判断当作执行授权事实。
- 不复制不同 API 中“空数组代表全部或无工具”的多义语义，所有集合都要求明确契约。
- 不采用有损首尾截断作为正式结果；预览必须保留完整证据或可执行 continuation。
- 不把“自动发现 MCP”或 provider/model 名称误写成已证明的延迟 schema 能力。

## 适用边界

该研究只约束 Tool System V3。它不定义模型何时选择工具、是否继续探索、候选取舍或业务完成语义；这些仍由 Ordinary Agent 与模型协作决定。它也不把 Multi-Agent、Plan 或 Governance 变成普通请求的必经链路。
