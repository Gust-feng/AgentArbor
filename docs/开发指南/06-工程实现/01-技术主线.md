# 技术主线

## 默认方向

当前实现路线是统一 Workbench 与功能模块化单体。Ordinary Agent 保持默认工作方式，Multi-Agent 作为用户显式选择的深入协作功能，Sub-Agent 是 Ordinary 的 SDK AgentTool。Ordinary 与 Multi-Agent 共享中性模型、工具、确认、上下文算法和系统适配，但不共享业务状态、事件、仓储或 read-model；Sub-Agent 调用事实进入父 Ordinary run，不建立平行运行时。当前 UI 仍有 Agent 集群 beta 侧栏入口和独立 `/api/deep/*`，这是待收口实现，不是第二个产品。

实现以 TypeScript 自研架构为主：

- 语言：TypeScript。
- 本地服务：Node.js。
- 持久化：由 feature 自己拥有的版本化文件快照；Ordinary 使用原子 `ordinary-run/v3` snapshot，Multi-Agent 保留独立 Deep store。当前不引入 SQLite、ORM 或跨 feature 统一数据库。
- 前端：TypeScript Web 技术栈。
- 测试：后端和确定性契约使用 `node:test`；Panel 真实交互使用 Vitest + React Testing Library。源码字符串结构守卫只保护无法由行为测试表达的依赖边界。
- 外部系统：通过 adapter 接入。
- 成熟机械能力：OpenAI Agents SDK 承担 Ordinary 模型-工具循环，Zod 解析外部 JSON，`diff` 生成 canonical unified diff，`read-excel-file` 与 `unpdf` 分别解析 XLSX 和 PDF 文本。

## 实现原则

- 按 Ordinary、Multi-Agent、Sub-Agent 的功能闭环维护业务事实；Workbench 只组合导航和展示。
- Ordinary 与 Multi-Agent 可以调用同一中性能力，但不得读取对方 store、事件或 read-model；Ordinary 也不得被工程规则自动升级为 Multi-Agent。
- Multi-Agent 当前已经存在正式 `/api/deep/*` 与最小协作闭环；后续按 ADR-0028 渐进收口入口和所有权，不另建平行运行平台。
- 避免过度设计指的是普通路径命名和实现语义不能过重，不是删除 deep 长期方向。
- 新增名称应先匹配真实职责：普通文件编辑叫编辑或补丁，helper 叫 helper，adapter 叫 adapter；只有有目标理解、行动选择、输入输出契约和可观察运行边界时才叫 agent。
- 先保证权限、命令确认、验证和可恢复运行，再扩展自动化。
- 只把已有两个稳定消费者的机械语义提取为共享能力；业务 RunEvent、仓储和完成语义留在 owning feature。
- 普通 HTTP/SSE/面板/会话投影不得因脱敏或安全投影吞掉普通回答、工具结果、错误信息、文件正文、stdout/stderr 或开发上下文；运行记录可以为体积和结构保存摘要，但不能替代模型可继续使用的真实工具结果。
- TanStack Query 只管理普通服务端查询；当前试点仅限使用统计，不能接管 Ordinary/Deep active run、SSE、cursor、busy、confirmation 或业务持久化。
- 先证明可恢复、可审计、可取消、可命令确认的桌面 Agent 运行，再谈 Governance 回流和能力资产出生。

## 不提前引入

除非进入明确实现阶段并证明能减少自研代码、没有形成第二状态源，否则不引入新的包管理器、构建系统、运行时框架或测试框架。当前不采用 Hono、Execa、SQLite、DI 框架、ORM 或统一工作流引擎。
