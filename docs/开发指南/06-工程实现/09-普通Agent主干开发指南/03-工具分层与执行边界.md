# 工具分层与执行边界

## 工具必须分三层处理

普通 Agent 的工具体系必须按三层理解，而不是混成一团：

1. `assemble`：本轮向模型提供哪些工具定义和工具说明。
2. `model`：模型当前能看见哪些工具。
3. `execute`：真正调用时哪些工具能执行、哪些要确认、哪些会被拦下。

要求：

- 工具注册表负责“系统里有哪些工具”。
- 可见性策略负责“这个 Agent / 这轮 run 能看到哪些工具”。
- ToolCenter 负责“执行时如何统一校验、确认、取消、调用 executor 和归一化执行事实”；事件、持久化与审计投影由调用 runtime 消费同一结果完成。
- Ordinary 的 Pi AgentTool adapter 必须在调用 ToolCenter gateway 前强制校验本轮 `allowedTools`，不能只依赖具体 broker 自觉遵守权限；Deep 的 `AgentTurnRuntime` 在自己的调用边界执行同类校验。
- 模型拥有工具选择权，但没有绕过执行边界的能力。
- 普通 run 创建时必须冻结本轮 `capabilitySnapshot`；本轮模型配置、工具可见集合、工具状态、工作区根、模型能力和技能触发集合都以该快照为准。
- Ordinary run 的模型配置事实必须来自 `capabilitySnapshot.activeModel`，避免执行按快照模型运行、read-model 却显示当前全局模型配置。
- Ordinary run 创建后不得再读取当前全局模型配置作为第二事实源；请求未显式指定 `aiMode` 时，从 `capabilitySnapshot.activeModel.defaultAiMode` 派生。旧 Underground 兼容路径已经删除，不保留无快照 fallback。
- 冻结的工具状态既可以收窄本轮能力，也可以保留本轮已经授权的可执行工具；例如当前全局默认关闭某个敏感工具时，已创建 run 仍应按出生快照中的 enabled/disabled 状态执行，不能被后续当前配置反向覆盖。
- 技能正文可以在执行时按 `sourcePath` 按需加载，但“哪些 skill 对本 run 可见、可触发”不能重新读取当前全局 skill 状态；用户后续启停 skill 只影响新 run。
- MCP 当前进入配置目录、`capabilitySnapshot.mcpCatalog`、能力草案投影和默认普通 `agent` 工具边界；MCP executor 保持独立 `mcp` scope，不挂到 `desktop-basic`，但默认普通 Agent 的 `AgentDefinition.toolVisibilityProfile` 会允许 `mcp` scope。只有已启用、已连接、已冻结进本轮 snapshot 且通过工具边界裁剪的 MCP 工具，才会作为模型可见工具和可执行工具进入本轮运行。
- MCP 工具发现按单服务限制 128 项、128 KiB 序列化 metadata；普通 run 装配时对所有服务聚合后的模型可见 MCP 工具再次应用同一总边界，防止多个正常大小的服务合并后绕过模型输入保护。prompts/resources/templates 共享单服务 1,024 项、1 MiB 的引用目录预算。条目或字节边界超出必须以 `mcp_catalog_limit_exceeded` 明确失败，不能截断后缓存或发布部分目录。lazy MCP provider 的释放必须取消并等待连接中 client，且重复释放幂等；已释放 provider 不得重新连接或接受迟到连接。

工具只有一份模型契约：canonical name、客观 description 和完整 input schema。适用边界直接写进 description，参数约束进入 schema；不再维护平行说明对象，也不把结果字段写成静态指导散文。provider description 使用 512 字符显式上限，超限带截断标记。真实 result/continuation 边界由 `ToolCallResult`、ToolCenter 归一化和 executor 行为契约承担。用户预览长度、折叠和隐藏策略只由 Panel/read-model 从调用事实派生。

Ordinary run 必须把 frozen definitions 与 live gateway 分开携带：模型曝光、渐进加载和 delegated Agent 都只读取 run 创建时冻结的定义，实际调用才进入 live gateway。definition hash 覆盖 description、输入/输出 schema 和执行元数据；缺 schema、缺 hash 或当前 executor 契约漂移时工具直接退出本轮边界，不使用兼容 fallback。

禁止事项：

- 用工具名前缀、零散白名单或 UI 分支逻辑替代正式的工具可见性策略。
- 让前端、prompt 或临时 helper 决定工具是否真的可以执行。
- 把工具描述文案当作权限系统。
- 排队或恢复 run 执行时重新向当前 `CapabilityCenter` 取 skill/tool 状态并覆盖 run 创建事实。
- 仅因为 MCP server 写入了配置目录，就把 MCP tool 暴露给普通 Agent；MCP 工具必须已启用、已连接、已进入本轮冻结快照，并通过 `AgentDefinition.toolVisibilityProfile`、`allowedTools` 和 ToolCenter 执行边界。

## 工具属于后端基础设施能力

工具首先是后端基础设施能力，不是前端能力，也不是 prompt 自由幻想出来的能力。它接收已经解析且已授权的工具调用，执行实际能力，并如实返回结果；它不替模型思考，也不承担会话、展示或持久化编排。

要求：

- 工具执行必须统一经过 ToolCenter。ToolCenter 只负责查找 executor、校验调用者和 `allowedTools`、校验输入、应用必要的命令确认/取消边界、调用 executor，并形成标准工具调用结果。
- Tool adapter 只负责其外部能力的实际操作与事实结果；它不生成模型解释、UI 卡片、上下文摘要或持久化记录。
- 工具定义只保留执行真正需要的名称、客观描述、输入 schema 和执行策略。显示名称、预览长度、摘要文案、UI 风险标签和卡片样式不属于工具基础设施的必填契约。
- 工具权限、命令确认、路径/网络/命令边界必须在后端完成。
- 本轮 `allowedTools` 是模型可见和工具执行的共同交集；即使模型或恢复路径请求了未授权但已注册的工具，Agent Session adapter/gateway 也必须返回标准失败结果，而不是交给具体 executor 执行。
- skills、browser、workspace、search、MCP 都先视为能力来源，再经过普通 Agent 的可见性和执行边界裁剪；MCP 默认允许进入普通工具循环，但不能绕过冻结快照和执行器重建。
- 工具失败必须作为标准结果回到模型，而不是中途丢失或由工程代答。

职责边界：

- Ordinary `AgentLoop` 负责 SDK 模型-工具-模型机械循环、结果回灌、取消和 live confirmation continuation；Ordinary feature 负责业务停止语义、确认状态、事件与持久化。Deep 的同类职责留在 `AgentTurnRuntime` 与 Multi-Agent feature。
- owning feature 负责先接受同一工具调用事实，再生成自己的事件、历史与 read-model；它不要求 ToolCenter 预先生成摘要、envelope 或展示对象。
- UI/read-model 层负责从模型消息和工具调用记录形成视图；它可以折叠或格式化，但不能创造新的工具事实。
- 工具调用次数不是 ToolCenter 的状态。它是本轮 Agent runtime 的预算事实，应由调用循环或预算模块维护。

禁止事项：

- 绕过 ToolCenter 直接调用 workspace、shell、browser 或 provider adapter。
- 把工具失败吞掉，只给用户一个空泛状态。
- 把前端交互事件当成工具执行事实源。
- 让 ToolCenter 生成模型回灌内容、上下文摘要、UI display/envelope、stream payload 或持久化副本。
- 用工具名、输入字段名或展示需求推断执行语义；工具只依据显式调用、授权、schema 和执行策略工作。

## 默认基础工具面

0.3.1 的默认 workspace 工具面为：

```text
Read / Glob / Grep / Write / Edit / Shell / ProcessRead / ProcessStop
```

设计要求：

- 名称使用简短 PascalCase，描述只说明真实能力、必要输入和客观限制。
- `Read` 读取文件内容；`Glob` 按路径模式发现文件；`Grep` 按内容搜索，三者不合并成多模式工具。
- 默认不暴露 `List` 与 `Delete`。目录发现由 `Glob` 承担，删除由通用 `Shell` 承担，避免低价值重叠工具扩大选择面。
- `Edit` 只接受 `oldText/newText` 精确唯一匹配，不保留 `dryRun`、`occurrence`、行范围、`anchor/replacement` 等历史兼容字段。
- 修改既有文件无需先 `Read`。`Edit` 只在其 `oldText` 能对当前内容精确唯一匹配时写入；同一文件的并发修改由写入协调器串行执行。
- `Write` 与 `Edit` 返回 `changed`、前后 Hash、字节数和规范 diff 等可核验事实，不返回替模型决策的建议。
- 所有截断结果必须提供真实、可执行、单调前进的 continuation。producer 必须保留原工具的完整查询输入；例如 `Glob` 的后续页不能被投影成 `Grep` 调用。
- `HttpRequest`、附件读取和 `ReadOutput` 等能力只在真实 runtime 能力与本轮授权满足时按需曝光，不为保持固定数量注册空壳。
- 当前不建设 `ToolSearch`。只有未来默认可见工具规模和真实任务数据证明模型选择成本成为瓶颈时，再单独设计和评测。

该口径追求较小且正交的工具集合，不以减少工具数量为唯一目标。后续优化应优先提高结果信息价值、减少重复探索并保持正确性，而不是继续合并 `Read / Glob / Grep` 或删除必要基础能力。

## 工具只返回事实，解释属于模型消息

模型可以在调用工具前、调用工具时或工具结果回来后自然输出一段用户可见文本。这是正常的模型消息，不是工具契约，也不是工具必须返回的“为什么调用”解释。

要求：

- 工具只返回真实执行事实：输入对应的资源、状态、结构化结果、错误、截断和真实 continuation。
- 不要求每次工具调用附带解释文本，不为此增加 tool input、tool output、event 或 projection 字段。
- 前端以后台记录的模型消息和工具调用事实为准：模型说了什么就展示什么，工具做了什么就展示什么；前端不得补造模型意图、恢复建议或工具调用理由。
- UI 可以折叠大输出、提供简短标题或按需展开事实，但这些只是同一工具调用记录的视图，不能成为另一套运行时事实或覆盖模型续跑内容。
- 模型继续工作所需的正文、stdout/stderr、文件片段和错误事实必须保留完整或提供真实可执行的 continuation。

断代口径：`ToolSafeProjection`、`ToolResultEnvelope`、`projection`、`envelope` 和 ToolCenter 调用计数接口已经删除，不保留 alias 或旧记录读取分支。旧 snapshot 不满足新契约时视为开发期失效数据。

`ToolCallRequest.input` 与 `ToolCallResult.input/output` 使用 `ToolFactValue`。它只接受 JSON 可表达的事实；循环引用、`BigInt`、函数、symbol、非有限数字和 class instance 必须明确失败。模型消费的 `ToolResult` 正文只能是 `none / text / json` 之一，同一完整结果不能同时进入文本和结构化字段。模型消息协议已经携带的 `callId / toolName` 不得在正文重复，`durationMs` 留给事件和观察视图。

通用 ToolCenter/kernel 只认工具输出顶层的 `continuation / continuations`。MCP 规范本身没有工具结果 continuation，MCP adapter 不按 `structuredContent` 中的 `continuation / continuations / nextInput` 字段形状猜测分页；这些字段原样保留为服务端业务事实。只有拥有明确分页或稳定引用契约的专用 producer/adapter 才返回 canonical continuation。`Read / Glob / Grep` 由 producer 在共享内联预算内返回一页事实和下一位置；模型需要更多时，把 `nextStartChar / nextStartLine / nextOffset` 的值分别传给原工具的 `startChar / startLine / offset` 再次调用。这是普通工具调用，不保存额外业务状态。任何其他当前结果序列化后仍超过共享内联预算时，Host-owned 文件系统持久化 `ToolOutputStore` 必须先保存完整结果并返回 `ReadOutput`；ToolCenter 不能仅根据 read-only metadata 猜测第三方工具可以重放或缩小查询。任何达到真实 offset/字符 ceiling 的 producer，或无法安全重放副作用请求的 producer，必须返回明确失败事实，不得返回 `completed + truncated` 的死引用；禁止递归猜测下一位置字段，禁止不可执行的 synthetic ref，禁止给某类工具设置更大的 transport 特例来掩盖契约缺失。

固定内联边界按单个完整模型工具包络计算：正文目标 4,000 tokens、硬上限 6,000 tokens，不随模型上下文窗口变化。该边界不是单轮工具数、同批 aggregate budget 或并行上限。producer 必须先按自己的语义缩页；只有当前完整事实仍越界时，ToolCenter 才保留完整 evidence 并交付 reader continuation。canonical `ToolCallResult` 保留 source ref、SHA、byte length 和 availability；模型投影只去掉与协议输入或存储元数据完全重复的字段，不能删除正文、错误、stdout/stderr 或可执行 nextInput。

Pi AgentTool 的 `executionMode` 负责 Ordinary 的模型同批调度：同一 assistant turn 的全部工具调用统一为 `parallel`。模型需要先消费 A 的结果再决定 B 时，应在下一 turn 发出 B；工程层不得按工具名、read/write 分类或 Shell 命令内容猜测依赖。AgentArbor 不维护第二套 Agent 级 FIFO/写屏障；具体 adapter 仍负责自己的机械一致性，例如本地文件 `Write` / `Edit` 由 Host-owned 路径协调器只串行同一规范路径的短读改写区间，同一 run 的非重叠精确替换顺序组合，重叠替换和外部陈旧版本明确失败，不同路径继续并行。ToolCenter 仍逐调用负责权限、确认、取消和事实，观察层只记录执行耗时与并发度。工具完成事件允许按真实完成顺序发生，Pi 写入下一次模型请求和 Session 的 tool result message 必须保持 assistant source order。工具定义、执行包络、retained、continuation 与观察指标分别在模型请求、ToolCenter/reader 和执行观察边界采集，使用 bounded histogram 聚合，不得复制原始输入或正文形成第二套事实库。

模型输入附件走带外 `ModelMessage.attachments`，内部类型明确区分 `image / audio / file`，JSON 只保留必要元数据。MCP 的 `content[]` 与可选 JSON 对象 `structuredContent` 是服务端协议事实，可以同时存在；非对象或非 JSON-safe 的 `structuredContent` 必须在 adapter 边界明确失败。只有 text part 可解析为 JSON 且与 `structuredContent` 深度完全相等时，才允许删除这份精确镜像。图片、音频和非图片 embedded resource blob 分别保留为 image、audio 和 file attachment；单个 MCP 结果当前最多 16 个模型附件、单附件最多 20 MiB、合计最多 32 MiB。MCP 已返回后发生附件预算或结果归一化失败时，必须保留 post-execution delivery failure、可交付正文、`sourceExecutionStatus` 与 `doNotBlindlyRetry`，不能伪装成远端未执行。OpenAI-compatible Chat Completions 只对原始 user 消息映射 image、inline/file-id file 与内联 wav/mp3 `input_audio`；它不能承载 tool-origin 二进制附件，provider adapter 必须返回 `request_validation`，不得改变来源角色。OpenAI Responses 可承载 user/tool-origin image 和 file，但当前拒绝 audio；对 inline file_data 与携带 byteLength 的 file_id/file_url，在整份请求范围校验单文件小于 50 MB、文件合计不超过 50 MB，未知远端文件大小由 provider 最终校验；tool-origin audio 在当前 OpenAI adapters 中均不支持。任何 provider 无法消费的媒体都必须形成可观察失败。任何非精确镜像都完整保留；不得做模糊/摘要式去重，也不得额外生成第二份 summary/result 包装。

`ToolCallResult` 的 `completed / failed / cancelled / approval_required` 是互斥执行结果。Ordinary 把 requested、结果和确认写入 `ordinary-run/v5` facts；Pi Session 只保存模型可见的有界 tool-result message；Multi-Agent 写入自己的 Deep facts。各 feature 从自己的权威状态单向派生 event/replay/read-model，不建设跨 feature 的统一 append-only reducer。Panel display 只能从对应 feature 的调用事实派生。

禁止事项：

- 把“解释为什么调用工具”做成每个工具的强制字段、固定 prompt 要求或前端推断规则。
- 用过度摘要让模型看不见继续工作所需的工具事实。
- 把 raw prompt、raw provider response、raw tool output、完整 stdout/stderr、未授权文件正文直接暴露到用户默认视图。
- 为了“安全”把正常可用的工具事实压成空壳。

## 工具结果必须尊重事实

工具结果是模型下一步判断的事实输入。工具层只能记录真实发生了什么、哪些字段可观察、哪些内容因为预算被限制，不能替模型判断下一步该怎么做。

要求：

- 小结果默认完整返回；只有可能撑爆上下文或 UI 的大体量结果才做有界预览。
- 任何截断都必须是事实化字段，例如 `truncated`、`stdoutTruncated`、`stdoutChars`、`stdoutOmittedChars`、`hasMoreAfter`，不能只给一句“已摘要”。
- 已经由 producer 有界分页的当前页直接回到模型；序列化后仍超过内联预算的其他文本、JSON 或完整失败证据，必须有可执行的 `tool-output://` 引用和 `ReadOutput` 入口。producer continuation 只负责其自身后续页，不能替代当前超大页的保存。引用失效或 store 容量不足时要返回明确错误，不能假装结果完整。
- `ToolOutputStore` 只在 `ReadOutput` 已注册且父 run 已授权 reader 时介入；Deep child / Sub-Agent 可把该 reader 作为 transport companion 自动加入自己的执行边界，但不能借此继承父级其他业务工具。外置必须保留原结果上的模型附件；外置失败也必须保留原 failed/cancelled/approval 状态、错误域、错误码和确认请求。
- `ReadOutput` 使用 UTF-16 code-unit `startChar`，单次最多请求 29,000 字符，并按实际 JSON 包络动态缩小当前页，确保长 provider call id 或高转义正文不会触发二次截断后跳过偏移；窗口边界不得拆分 emoji 等 surrogate pair。它只读保存内容，不能刷新来源或重跑原工具。文件与附件文本的带省略号字符窗口最小为 3，并严格拒绝小数、负数、越界或拆分 surrogate pair 的 offset，保证 continuation 每次前进。最后一段读完只释放 live-only 测试存储的 ref；持久化证据继续可读，Ordinary 与 Deep 分别在 conversation 删除时释放稳定 run owner，Panel 关闭只等待在途写入完成。
- 默认引用不设置 TTL，也不静默淘汰旧 evidence；完整内容、UTF-8 byte length、SHA-256 和来源元数据写入 `runtime/tool-evidence/`，进程重启后同一引用仍可读取。Host 默认按单项 256 MiB、总计 4 GiB、10,000 项执行容量准入，容量不足时明确失败而不是截断证据。owning conversation 删除、显式清理或证据损坏会使引用失效，读取端必须按明确 `tool_output_not_found` / `tool_output_corrupt` 处理。
- 外置失败时，原 completed 结果转为明确 delivery failure，同时保留 `sourceExecutionStatus: completed` 与 `doNotBlindlyRetry`，防止模型把“不完整交付”当成功或盲目重放副作用；原 failed/cancelled 保留自身状态、错误和失败事实。如果原结果正在等待确认，必须保留 `approval_required`、确认前部分输出、附件与原确认请求，不能因为结果过大把用户确认误投影为普通失败。
- 并行批次若 executor 动态返回 `approval_required`，Agent loop 仍必须暂停对应调用，不能把确认请求当成普通工具观察继续模型；确认等待期间取消、deny/guidance 或多阶段再次确认都必须保留已经产生的输出和附件。同批其他独立调用可以继续完成，一个调用失败也不能自动取消其他调用。用户 guidance 按请求体上限完整进入模型事实，不做固定 1,000 字静默截断。
- 错误结果必须保留原始可用事实，例如错误码、退出码、信号、端口、hostname、duration、cwd、toolName、callId。
- HTTP、文件、搜索、命令等工具的非成功业务状态要按真实结果返回；例如 HTTP 404 是结构化响应，不是工具异常。
- 工具失败可以进入模型后续回合，让模型自己决定重试、换路径、询问用户或停止。
- 可选的 UI 标题或预览只能从同一工具调用事实派生，不能成为唯一事实源、模型解释的替身或新的持久化契约。

禁止事项：

- 在工具错误里注入 `try`、`suggest`、`recommend`、`recoveryHint` 或“建议你下一步……”这类替模型思考的文案。
- 把真实错误改写成更顺滑但不准确的产品化结论。
- 为了显得可靠而伪造可用性，例如端口未 ready 时不能只返回“后台进程已启动”。
- 把不可观察的信息当作事实返回；例如搜索引擎路径无法知道 skipped files 时，应明确事实不可得，而不是编造跳过数量。
- 暴露空壳工具能力；未实现或永远返回空的 source 不能出现在模型可见工具契约里。

## 命令工具是通用执行环境

Shell/command 工具不是 `mkdir`、`copy`、`npm`、`python`、`git` 等命令的集合，也不应把每个常见命令拆成单独工具。命令工具的价值是给模型一个接近真实终端的执行环境，同时由工程层守住确认、超时、进程、日志和可观察性边界。

要求：

- 命令工具应允许模型自主组合常规命令；目录创建、脚本运行、包管理、测试、文件枚举等低层动作优先通过命令环境完成。
- 确认策略只有 `prompt` 和 `full_access` 两类：`prompt` 下 `Shell` 执行前必须等待确认；`full_access` 只跳过逐条确认，不是 sandbox，也不代表命令风险被隐藏。
- 即使处于 `full_access`，命令工具仍必须经过 ToolCenter、工具事件、runtime facts 和日志链路，不能绕过执行 broker、审计或结果投影。
- 前台命令必须返回真实 `exitCode`、`stdout`、`stderr`、`durationMs`、`timedOut`、`cancelled` 和截断事实。
- 后台命令必须返回 `pid`、`logPath`、`stopCommand`；这些小体量元数据不应因为 stdout/stderr 预算而被截断。
- `waitForPort` 只能表达端口事实：ready 就返回 `portReady: true`，超时或取消就返回 `portReady: false` 及对应事实字段。
- 超时、取消和进程退出必须分开表达，不能都折叠成“运行失败”。
- 停止后台进程后，测试和运行时都应检查关键子进程或端口是否真的结束，避免留下残留进程造成后续卡死。

禁止事项：

- 为每个普通 shell 命令增加一个微工具。
- 把 `exitCode: 0` 但端口未 ready 的后台任务展示成“服务已可用”。
- 把大 stdout/stderr 全量塞进普通 UI 视图或长期运行记录。
- 因为担心模型误用命令而让工程层替模型选择命令方案；工程层只守确认、边界、预算和审计。

## 错误域必须分层

工具调用链上的失败来源不同，不能全部投影成“本次运行失败”或“模型服务连接失败”。错误域是事实分类，不是恢复策略。

要求：

- 至少区分 `tool_error`、`process_error`、`model_error`、`runtime_error`、`ui_submit_error`。
- shell / command 的执行失败、退出码异常、进程启动失败优先归为 `process_error`。
- 普通工具 adapter 的失败归为 `tool_error`，除非已有更具体事实。
- 模型 provider、模型配置、模型网络和模型响应失败归为 `model_error`。
- UI 提交流程失败归为 `ui_submit_error`，不能冒充工具失败或模型失败。
- 运行时调度、持久化、状态恢复等框架内部失败归为 `runtime_error`。
- 错误域只能附加在 run、tool call 或 runtime record 上，不得覆盖原始 `message`、`code`、`stderr`、`cause` 等事实。

禁止事项：

- 用关键词文案替代结构化错误域。
- 把工具失败统一投影成模型服务失败。
- 把错误域当作自动恢复建议或用户安抚文案。

## 后续工具打磨路线

当前普通 Agent 工具面已经覆盖基础文件、搜索读取、HTTP、命令和后台进程闭环。后续开发不应继续横向堆工具，而应优先补齐“事实链一致性”和“运行时可控性”。

近期可以继续推进：

- 搜索、读取、HTTP、命令、文件等 adapter 的失败事实应统一到同一工具调用记录的 `errorDomain`、`errorFacts` 和结构化结果；模型上下文、stream、transcript、runtime record 与 UI 都从该记录消费，不各自维护第二套结果投影。
- 无效输入、provider 不可用、网络失败、业务非成功状态必须显式返回状态和真实消息，不能投影成单纯空结果。
- 命令运行时继续加强进程 registry、端口事实、后台日志引用、取消链路和残留检测；这些属于 shell 运行环境守护层，不应拆成 `mkdir`、`npm`、`python` 等单命令工具。
- shell stdout/stderr 的默认返回应保持有界，完整大输出通过日志引用或后续读取路径探索；小体量元数据和截断事实必须完整保留。
- Windows / Bash / PowerShell 的换行差异只作为平台事实记录。编辑锚点应来自文件读取或实际文件字节，不能自动把 shell stdout 当成文件锚点进行隐式归一化。
- `search("")`、非法 `read` ref、二进制编辑、路径越界等低成本边界应返回明确事实，避免模型把输入错误误判为“没有结果”。

暂不推进但要保留方向：

- `run_memory` 属于高级能力，不进入当前默认模型可见工具契约。只有实现真实存储、检索、生命周期和治理边界后，才能作为可见 source 或工具暴露；在此之前不能以空壳形式出现在默认 schema 中。
- shell 工作区隔离属于后续安全运行时，不影响当前“命令工具是通用执行环境”的主线。实现前不能用 UI 文案或前端提示伪装成已隔离。
- 浏览器能力继续优先通过 MCP 或外部浏览器桥接接入，不在当前基础工具面重复建设。
- errorDomain 的扩展只能做事实分类，不能演变成固定 recovery hint、自动建议或替模型选择下一步。

验收要求：

- 每个工具打磨项至少覆盖 adapter 结果、模型回灌、stream/transcript、runtime record 与 UI 视图中的对应事实；这些表面必须来自同一工具调用记录。
- 只要某个事实对模型继续工作有价值，就不能只出现在 UI 摘要里。
- 只要某个事实可能误导模型，就不要返回；例如不可观察的 skipped 数量、未验证的端口状态、未实现的 memory source。
- 文档路线只能记录稳定边界和下一步开发口径，不能替代代码事实。

## 工具能力变更必须有验收矩阵

工具能力看起来“能跑”不等于可以上线。任何工具能力或工具调用记录变更都必须同时验证模型可见事实、人类 UI、运行记录和进程清理。

最低验收：

- `pnpm build:node`
- `pnpm typecheck:panel`
- 相关工具 adapter 测试。
- stream / transcript / UI 视图测试，确认它们没有补造或改写模型和工具事实。
- 工具能力 acceptance 测试，覆盖真实 demo 工作流、后台进程、端口等待、HTTP、超时和大输出。
- `git diff --check`
- 对会启动后台进程的测试，执行后检查无测试 server 或 `node --test` 残留。

## 工具命名和文案必须朴素

工具能力的命名和描述必须匹配真实职责。

要求：

- 普通文本编辑工具就叫编辑、补丁、替换、创建、删除。
- 批量编辑只有在真有全成功/全失败、一致性或回滚边界时，才允许使用 `atomic`。
- 工具描述应说明功能、输入、限制和确认规则，不加戏。

禁止事项：

- 把普通编辑工具包装成“原子智能编辑”“Plan 重写”“高级变异能力”。
- 用夸张描述掩盖基础能力本该可靠这一事实。
- 把浏览、快照、命令、搜索说成超出其真实职责的复杂系统。
