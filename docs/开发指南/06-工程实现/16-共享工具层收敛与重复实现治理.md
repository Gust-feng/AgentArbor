# 共享工具层收敛与重复实现治理

本文记录一次全仓代码审查的结论：AgentArbor 的工程纪律整体良好，但缺少一个内核级公共工具层，导致同一批小工具函数在各功能模块内被反复重写。本文固化问题清单、语义分歧证据、由此产生的真实缺陷，以及收敛方案与防复发守卫。

## 审查基线

审查针对 `47528e69`（0.3.2）时的 `src/` 全量源码。

| 指标 | 数值 |
| --- | --- |
| 生产源码 | 585 文件 / 139096 行 |
| 测试源码 | 267 文件 / 89902 行 |
| `as any` | 0 |
| `@ts-ignore` / `@ts-expect-error` | 0 |
| 空 `catch {}` | 0 |
| `shell: true` | 0 |

四项危险模式计数为零，说明类型纪律与命令执行安全没有系统性问题。本次治理只针对下述重复实现问题，不涉及架构调整。

### 现有共享模块未被遵守

该声明与事实不符：同期另有 26 个文件各自重写了 `asRecord`。文档性承诺没有任何机制保障，这是本次治理要同时修复的部分。

## 问题二：重名函数已产生语义分歧

重复实现不只是冗余，同名函数已经出现互不兼容的行为，调用方按名称推断语义时必然出错。

### `asRecord` 的三种不兼容返回值

```ts
// src/adapters/intelligence/model-provider-binding.ts:355 —— 失败返回 undefined
return typeof value === "object" && value !== null && !Array.isArray(value)
  ? value as Readonly<Record<string, unknown>>
  : undefined;

// src/adapters/intelligence/provider-value-utils.ts:53 —— 失败返回 {}
return isPlainRecord(value) ? value : {};

// src/app/runtime-guard/... 测试内版本 —— 失败直接断言抛出
assert.equal(typeof value, "object");
```

返回 `undefined` 与返回 `{}` 会让下游的 `?.` 与 `??` 判空逻辑走向完全不同的分支。

### `stringOrUndefined` 的三种不兼容 trim 语义

```ts
// src/adapters/intelligence/provider-value-utils.ts:38 —— 过滤空白串，且返回 trim 后的值
return typeof value === "string" && value.trim().length > 0 ? value.trim() : undefined;

// src/app/panel-read-model/run/panel-stream-tool-projection.ts:144 —— 过滤空白串，但返回未 trim 的原值
return typeof value === "string" && value.trim().length > 0 ? value : undefined;

// src/app/panel-read-model/panel-model-progress-copy.ts:13 —— 完全不过滤，空串也会返回
return typeof value === "string" ? value : undefined;
```

### `errorMessage` 的签名分歧

15 份实现中，`src/app/panel-ui/src/api.ts:44` 返回 `string | undefined`，其余 14 份返回 `string`。同名不同签名，跨文件搬运代码时类型检查未必能拦住语义错误。

## 问题三：原子写文件重复六遍，并导致 Windows 真实缺陷

“临时文件 + rename + 重试”的原子写入被独立实现了六遍：

- `src/adapters/config/file-system-config-store.ts`
- `src/adapters/runtime-storage/run-snapshot-store.ts`
- `src/adapters/runtime-storage/file-system-tool-output-store.ts`
- `src/app/ordinary-agent/conversation-control-repository.ts`
- `src/app/ordinary-agent/file-system-repository.ts`
- `src/app/skills/skill-installer.ts`

### 缺陷：`file-system-config-store` 在 EBUSY 下不重试

各实现对“可重试错误”的判定集合并不一致：

```ts
// src/adapters/config/file-system-config-store.ts:184
return code === "EPERM" || code === "EACCES" || code === "ENOTEMPTY";

// 其余三处一致
return isNodeError(error, "EPERM") || isNodeError(error, "EACCES") || isNodeError(error, "EBUSY");
```

Windows 上杀毒软件、搜索索引器或备份程序临时占用目标文件时，`rename` 抛出的是 `EBUSY`。因此 `file-system-config-store` 这条路径**不会进入重试**，会把写入失败直接抛给用户，而另外五条持久化路径会正常重试。

影响面：配置中心写入是用户改设置的主路径，Windows 又是当前主要发行目标（`pnpm dist:desktop:win`）。这是一个偶发、难复现、且会导致用户配置保存失败的真实缺陷。

同时，`ENOTEMPTY` 只在该文件出现，其余实现缺失；重试参数也不统一（可配 `maxAttempts` 对硬编码 6 次，`renameBackoffMs(attempt)` 对 `25 * attempt`）。

## 问题四：`cloneJson` 与 `structuredClone` 混用

全仓 `structuredClone` 已使用 103 处，但仍有 11 处 `JSON.parse(JSON.stringify(...))` 手写克隆，其中 4 处封装为 `cloneJson`。同一功能域内两种克隆语义并存：

```ts
// src/app/ordinary-agent/ordinary-agent-feature.ts:1812
function clone<T>(value: T): T { return globalThis.structuredClone(value); }

// src/app/ordinary-agent/file-system-repository.ts:732
function cloneJson<T>(value: T): T { return JSON.parse(JSON.stringify(value)) as T; }
```

JSON 往返会静默丢弃 `undefined` 值、把 `Date` 降级为字符串、丢失 `Map` / `Set`，并在循环引用时抛错。Node 22 下 `structuredClone` 为全局可用，保留 JSON 版本没有收益。

需要注意的是，新增的 `path-memory` 模块采用的仍是 JSON 版本，说明该坏模式仍在向新代码扩散，需要守卫拦截。

实施时发现这一判断需要修正：仓储中的 JSON 克隆并非纯粹的坏模式，它同时承担持久化形状归一化职责。详见下文“实施中修正的三处方案偏差”。

## 问题五：Ordinary Agent 的 20 个平行状态字典

`src/app/ordinary-agent/ordinary-agent-feature.ts:64-86` 在单个闭包内声明了 20 个按 `runId` 索引的 `Map` / `Set`：

```ts
const documents = new Map<string, OrdinaryRunSnapshotDocument>();
const conversationDocuments = new Map<string, OrdinaryConversationControlDocument>();
const unavailableConversationIds = new Set<string>();
const continuations = new Map<string, OrdinaryExecutionContinuation>();
const approvalReservations = new Map<string, string>();
const controllers = new Map<string, AbortController>();
// ... 共 20 个
```

这是本该由单个 `RunContext` 承载的状态被摊成 N 个并行字典。每新增一个 run 维度状态，都必须记得在 3 至 4 条终止路径上分别 `delete`。

清理覆盖率审查显示多数字典配平，但 `unavailableConversationIds` 为 `set` 2 处、`delete` 0 处，在长生命周期进程中单调增长。

本项列为低优先级：属于结构性改进，改动面大，不与本次收敛同批提交。

## 问题六：112 处静默 promise catch

空 `catch {}` 为 0，但 `.catch(() => {})` 与 `.catch(() => undefined)` 合计 112 处。其中相当部分是合理的 best-effort 清理（删除临时文件、释放资源），但该量级下必然混有应当记录日志的真实错误。

治理方向：引入具名 helper（如 `ignoreCleanupFailure()`），使“有意忽略”与“遗漏处理”在代码评审中可区分。本项列为中优先级。

## 结论：非问题项

以下事项经核查确认无需处理，记录在此避免后续重复审查。

- **依赖选型无造轮子**：模型循环使用 `@earendil-works/pi-agent-core`，schema 使用 `zod`，MCP 使用官方 SDK，tokenizer 使用 `js-tiktoken`，diff 使用 `diff`，PDF 使用 `unpdf`。未自研 tokenizer 或 diff 算法。
- **命令执行安全**：`spawn` 全部采用 `spawn(file, [...args])` 数组传参，`shell: true` 零使用，统一设置 `windowsHide`，Windows 侧通过 `taskkill /T /F` 处理进程树。无命令注入面。
- **`dangerouslySetInnerHTML` 的 7 处使用安全**：注入内容全部来自 `import ... from "./assets/**/*.svg?raw"` 的构建期静态资产。已核查 provider 配置链路，用户无法注入自定义 SVG。
- **React 层无 hook 堆积**：`useEffect` 密度最高的 `app-startup-intro.tsx` 为 13 处，其余均在 5 处以内，且已拆分出 `app-shell-effects.ts` 与 `app-form-state-sync.ts`。

## 收敛方案

### 共享层落点

新增 `src/kernel/values/`，作为全仓中性值处理工具的唯一事实源。

选择 `kernel` 的依据：`domain` 当前对 `kernel` 的依赖数为 0，若把共享层放进 `domain` 会让 `kernel`、`adapters`、`app` 三层反向依赖业务层。`kernel` 是既有的中性最小内核，符合 `AGENTS.md` 中“中性基础设施只提供可复用机械能力”的定位。

模块划分：

- `src/kernel/values/record.ts`：`isPlainRecord`、`asRecord`、`asOptionalRecord`。
- `src/kernel/values/scalar.ts`：`stringOrUndefined`、`rawStringOrUndefined`、`isString`、`numberOrUndefined`、`booleanOrUndefined`、`nonNegativeInteger`、`positiveInteger`。
- `src/kernel/values/collection.ts`：`uniqueValues`、`uniqueNonBlankStrings`、`stringArray`、`stringArrayOrUndefined`。
- `src/kernel/values/error.ts`：`errorMessage`、`isNodeError`、`isFileNotFound`、`isTransientRenameError`。
- `src/kernel/values/clone.ts`：`cloneDeep`、`toPersistedJsonShape`。
- `src/kernel/fs/atomic-write.ts`：`renameWithRetry`。

### 语义统一口径

替换过程中必须逐个确认调用点依赖的是哪种语义，不能整体替换：

- `asRecord(value)` 失败返回 `{}`；需要区分“缺失”与“空对象”的调用点改用 `asOptionalRecord(value)`，失败返回 `undefined`。
- `stringOrUndefined(value)` 统一为“过滤空白串并返回 trim 后的值”。依赖保留原始空白的调用点显式改用 `rawStringOrUndefined`。
- `isTransientRenameError` 统一为 `EPERM | EACCES | EBUSY | ENOTEMPTY` 四码并集，修复 EBUSY 缺陷。

### 实施中修正的三处方案偏差

方案落地时发现三处原计划不成立，按事实调整：

**一、`domain/` 不纳入收敛范围。** 原计划把共享层放进 `kernel` 后全仓替换。实测 `kernel` 已依赖 `domain` 62 处，而 `domain` 对 `kernel` 依赖为 0；让 `domain` 反向引用 `kernel/values` 会形成层级环，被既有的循环依赖测试拦截。因此 `domain/` 下的同名实现保持原样，直到共享层被下沉到比 `domain` 更底层的位置。

**二、原子写只收敛重试段，不合并整个写入流程。** 原计划把 6 处原子写合并为一个 `writeJsonFileAtomically`。实测这些实现在临时文件布局与持久化强度上存在被测试覆盖的真实差异：`file-system-config-store` 把临时文件放在目标同级并以 `.` 前缀命名（测试断言文件名形如 `^\.settings\.json\..+\.tmp$`）；`conversation-control-repository` 与 Ordinary `file-system-repository` 放进独立 `.tmp/` 子目录，因为它们的枚举按 `entry.isDirectory()` 遍历同级目录，临时文件混入会污染枚举；`run-snapshot-store` 额外做 `handle.sync()` fsync。强行合并会产出一个带大量开关的伪共享函数。因此只收敛逐字重复且曾出现语义分歧的 `renameWithRetry`。

**三、`cloneJson` 不能一律替换为 `cloneDeep`。** 原计划全量替换为 `structuredClone`。实测仓储的 `cloneJson` 承担双重职责：深拷贝，以及 JSON 形状归一化——`save()` 必须返回与后续 `get()` 从磁盘读回严格相等的文档，而磁盘上不存在值为 `undefined` 的键。直接替换会让 `save()` 保留 `pendingToolRound: undefined` 等键，导致 `deepEqual` 失败（已被 `file-system-repository.test.ts` 捕获）。因此拆分为两个命名：`cloneDeep` 用于普通深拷贝，`toPersistedJsonShape` 用于持久化边界并保留有损语义。

### 防复发守卫

`src/app/source-structure-tests/source-shared-value-utils-structure.test.ts` 断言三件事：

1. 已收敛的函数名不得在 `src/app`、`src/adapters`、`src/kernel` 内被重新定义（共享层自身、`domain/`、测试文件与登记豁免除外）。
2. 共享层保持中性：`src/kernel/values` 与 `src/kernel/fs` 只能依赖 `node:` 内置模块与自身。
3. `isTransientRenameError` 的四个 errno 一个都不能少——移除任一项都会让某条持久化路径退回“平台抖动即失败”。

语义确有差异的同名实现登记在 `SEMANTIC_DIVERGENCE_EXEMPTIONS` 中，每条附差异理由。新增豁免必须说明差异，否则应引用共享层或在共享层中新增语义显式的命名。

## 交付结果

本次收敛已完成的部分：

| 事项 | 结果 |
| --- | --- |
| `file-system-config-store` 的 `EBUSY` 缺失 | 已修复，四码取并集 |
| `src/kernel/values/` + `src/kernel/fs/` | 已建立，含 12 个单元测试 |
| `renameWithRetry` | 4 处收敛为 1 处 |
| `asRecord` / `isPlainRecord` | 生产代码 30 处降至 12 处（余下为 `domain/` 与登记豁免） |
| `stringOrUndefined` | 18 处降至 6 处（余下为 NOTRIM / LOOSE 语义与 `domain/`） |

验证：`pnpm test` 全绿——Node 1999 通过 / 0 失败，Panel 20 个测试文件通过，发布门 3 通过，dev scripts 4 通过。

`errorMessage` 保留 10 处的原因：`panel-ui/src/api.ts` 与 `app-attachments.ts` 的版本解析 HTTP 错误体并返回 `string | undefined`；`skill-installer` 等版本对空消息回退到 `error.name`；`research-tools` 版本回退到领域文案。这些是不同函数恰好同名，不属于重复实现。原计划提出的重命名为 `apiErrorMessage` 属于可选清理，未在本批执行。
