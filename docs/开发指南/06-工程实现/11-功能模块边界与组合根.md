# 功能模块边界与组合根

## 目标

本文件把 [ADR-0028](../../架构设计/产品架构/ADR-0028-AgentArbor统一Workbench与功能模块化单体架构.md) 转化为当前工程规则。AgentArbor 是同仓功能模块化单体：Workbench 是统一产品壳，Ordinary Agent 与 Multi-Agent 是独立业务功能，Sub-Agent 是 Ordinary Agent 的工具能力；模型、工具、确认、上下文算法和系统适配以中性端口被调用。

模块化的验收标准不是目录看起来整齐，而是一个功能能否在不读取其他功能内部状态的情况下被创建、调用、测试和释放。

## 模块 ownership

| 模块 | 必须拥有 | 只能通过端口使用 | 不得拥有 |
| --- | --- | --- | --- |
| Workbench Shell | surface 导航、输入动作、统一历史展示、布局 | Ordinary / Multi-Agent 的 UI facade | run 状态、业务事件、feature store、完成语义 |
| Ordinary Agent | conversation、run lifecycle、模型输入、canonical 模型历史、确认/取消/恢复、Ordinary event、仓储和 read-model | 模型、工具、确认原语、上下文压缩机械能力、系统 adapter；Sub-Agent 工具贡献 | Deep TaskBoard、Deep child、跨功能全局状态 |
| Multi-Agent | intake、manager 决策、TaskBoard、scheduler、child、纠正/停止/继续、parent synthesis、Deep event、仓储和 read-model | 模型、工具、确认原语、上下文机械能力、系统 adapter | Ordinary conversation/store/read-model、Panel 状态 |
| Sub-Agent | 定义发现、SDK AgentTool 贡献、输入解析、权限收窄和自身测试 | 父 Ordinary run 冻结权限与工具执行端口 | 独立 runner、状态、事件、仓储、read-model、递归派生、Deep run tree |
| Neutral capabilities | provider/channel、工具执行机械原语、tokenizer、消息完整性、压缩执行、配置与系统契约 | adapter contracts | feature 状态、业务 outcome、路由选择、Panel 类型 |
| Host / Composition Root | 配置解析、adapter 实例、feature 创建、资源生命周期、HTTP/Desktop 接线 | 各 feature factory 与公开 facade | 业务判断、事件重写、read-model 推导 |

一个文件若同时承担两行职责，必须先拆清 owner，不能用 `shared`、`runtime`、`services` 或 `utils` 命名掩盖。

## 公开端口

每个业务 feature 对外只暴露三类 facade：

- command：启动、取消、确认、纠正、继续、停止等会改变本 feature 状态的操作。
- query：读取 conversation、run view、history summary 和诊断投影。
- event：订阅该 feature 已定义的变化通知或业务事件。

端口必须使用 feature 自己的输入输出类型。不要为了减少接口数量创建通用 `RunCommand`、`RunState`、`RunRepository` 或 `RuntimeServices` 属性包。

HTTP/SSE、Electron 和 Panel UI 是 adapter：解析外部输入，调用一个 command/query/event，再映射外部协议。route 不得：

- `new` feature store、continuation registry、scheduler 或 provider。
- 调用 feature 内部 reducer 或修改 live map。
- 从 SSE 事件重建权威 run 状态。
- 同时读取 Ordinary 与 Multi-Agent store 拼成业务对象。

## 唯一 Composition Root

`createPanelRuntime()` 是当前后端唯一 Composition Root。它负责：

1. 解析 Host 路径和配置。
2. 创建共享但中性的 adapter 和进程级资源。
3. 创建 `OrdinaryAgentFeature`，并注入 OpenAI Agents SDK loop、ToolCenter、Skills、MCP、Sub-Agent 与系统资源等精确端口。
4. 创建 `MultiAgentFeature`。
5. 把精确 facade 交给 Panel route / SSE adapter。
6. 统一关闭由它创建的资源。

`OrdinaryAgentFeature` 已是当前正式生产 owner：它拥有 conversation、run lifecycle、canonical 模型历史、工具事实、确认/取消、仓储与事件重放。`ordinary-routes` 不得重新持有这些事实，也不得从 Panel view 或 SSE 反向恢复模型上下文。

只有 Composition Root 可以同时导入多个 feature factory。测试可以创建单个 feature 的 test fixture，但不得形成第二个生产组合根。

资源遵循“谁创建，谁释放”：feature 创建的 store、live registry、control handle 和 continuation 由 feature 释放；Host 创建的 adapter 和进程级资源由 Host 释放。禁止用 route 级 `WeakMap`、模块全局 mutable singleton 或 `MinimalRuntime` service locator 隐藏生命周期。

Multi-Agent 的 run repository 提供按 conversation 与 root lineage 查询的 owner-specific 端口；删除、轮次编号等业务事实不得复用全局最近列表的展示 limit。同一 run 的 save/delete 通过 feature-owned FIFO 顺序执行，避免并发 child 的旧投影晚写覆盖新事实；不同 run 可以并发写入，feature 释放前必须 drain 已接收的写操作与失败。

Multi-Agent 对同一 conversation 的变更命令使用 feature 内部 FIFO 门，覆盖重命名、置顶、删除、已有会话 intake、启动/续跑、子 Agent 恢复/指令、重新综合和运行控制；不同 conversation 不互相阻塞。runId 命令优先使用 active-run 会话映射，以保留初始快照落盘前的立即控制能力，再回退持久化记录。命令进入门后仍由 owning command 重新读取并校验业务状态，保证删除先完成时晚到命令明确失败，不能重建已删除 run。该门只保护 Multi-Agent 自有一致性边界，不得抽成全局锁、统一 workflow engine 或跨 feature 事务。

大工具结果使用 Host-owned、文件系统持久化的 `ToolOutputStore` 作为中性机械能力：每个 PanelRuntime 只创建一个实例，Ordinary 与 Multi-Agent 的运行资源通过各自装配的 broker 使用同一精确端口；Sub-Agent 复用父 Ordinary broker，不自建第二套 ToolCenter 或 registry。Panel 关闭时由 Host 等待在途写入完成，但不删除持久化证据。它保存任何超过内联预算的当前完整文本、序列化 JSON 或显式失败证据。Deep child / Sub-Agent 只可在父 run 已授权且 broker 真实具备 reader 时把 `read_tool_output` 作为 transport companion 自动继承，不能扩张其他业务工具。外置不能丢失原结果的模型附件，也不能覆盖 failed/cancelled/approval 的状态、错误域、错误码或确认请求；原 completed 若无法完整交付则转为 delivery failure，并保留 `sourceExecutionStatus: completed` 与 `doNotBlindlyRetry`。reader 只按 opaque ref 读取已保存内容，不重跑来源工具，使用 UTF-16 code-unit offset、按实际序列化包络动态缩小页面且不得拆分 surrogate pair；最后一段读完只释放 live-only 测试存储的 ref；持久化证据由 owning feature 在 conversation 删除时按 run owner 回收。Multi-Agent 为 post-terminal child continuation 使用稳定的 run owner，只通过 feature 的窄 Host 清理端口在 conversation 删除时回收。模型附件字节仍只服务单次请求，不得进入持久化 child context；为恢复 OpenAI Responses 的 reasoning/function-call 连续性，只对白名单 `openai_responses_output_items` 做 JSON-safe 验证并原样保留。已知该 key 但内容无效或为空时，context persistence 必须以稳定错误 `model_protocol_continuation_not_persistable` 明确失败，不能静默丢弃、截断或摘要后声称可恢复；其他未知 provider protocol extension key 仍可忽略。`ToolOutputStore` 不设置 TTL，也不静默淘汰旧 evidence；超内联内容以完整正文、UTF-8 byte length、SHA-256 和来源元数据写入 `runtime/tool-evidence/`，引用元数据作为 `durable` 工具事实进入 owning feature snapshot，进程重启后仍可读取。Host 默认容量为单项 256 MiB、总计 4 GiB、10,000 项，达到边界时明确返回 `tool_output_item_too_large` / `tool_output_capacity_exceeded`，不能截断后声称证据完整；该能力不替代 feature 仓储，也不扩成通用 blob/repository。

`read_file / list_dir / grep_files` 不使用 `ToolOutputStore` 维持额外续读状态。它们由 producer 把当前页限制在共享内联预算内，返回下一位置事实，模型需要更多时再次调用原工具。ToolCenter 不得把这条规则扩大成“所有 read-only 结果都可重做”；不具备明确缩小查询契约的第三方或 MCP 工具超限结果，仍必须保留到 `ToolOutputStore`。

Ordinary 只通过 feature-owned repository 保存 `ordinary-run/v3` 完整 snapshot，并以独立 `ordinary-conversation/v1` control document 保存对话分支、标题、置顶与删除事实。旧 RuntimeDatabase、raw `run.json`、sidecar event/tool-call 写入和旧 snapshot 均不读取、不迁移、不双写；开发期失效数据直接视为废弃。该快照是当前唯一恢复事实，不等同 Event Sourcing。

Ordinary 的跨轮模型历史只来自 `ordinary-run/v3` snapshot 的 `canonicalMessages`。它保存模型实际消费的消息与工具链，并对白名单 OpenAI Responses output items 使用 JSON-safe 持久化边界；附件字节和未知 provider 私有字段不进入记录。Panel conversation、工具活动和 read-model 只是单向投影，不得作为兼容来源重建模型历史。旧 snapshot 直接拒绝，不迁移、不双读、不回填。

## 依赖方向

允许：

```text
Host / UI adapter -> feature facade
Composition Root  -> feature factory + neutral adapter
feature           -> neutral capability port
adapter           -> neutral contract
Sub-Agent         -> Ordinary 的工具贡献端口
```

禁止：

- `model-runtime`、工具基础能力、上下文机械算法等 neutral capability 导入 feature。
- Multi-Agent 导入 Ordinary/Desktop 的实现、store、read-model 或专用 facade。
- feature 导入 `panel-server`、`panel-ui` 或 Panel 展示类型。
- Ordinary 与 Multi-Agent 互相转换状态、共享 repository 或订阅对方内部事件。
- route、controller、UI hook 绕过 facade 访问 feature 内部对象。
- 除 Composition Root 外的生产文件同时装配多个 feature。

允许共享类型的前提是它表达机械事实，如模型响应、工具执行事实、确认决定、消息完整性或系统路径；`completed`、`blocked`、`synthesis`、`conversation` 和 `child` 等业务语义不能因为字段相似就抽成全局联合。

## 中性能力准入

提取共享能力前必须回答：

1. 是否已有至少两个真实、稳定消费者？
2. 两个消费者需要的是同一机械语义，还是仅仅名字相似？
3. API 是否不包含任何 feature 名、状态或默认流程？
4. 消费方是否能自行把技术结果映射为业务 outcome？
5. 删除其中一个 feature 后，这个能力是否仍然成立？

任一答案为否，就先留在 owning feature。不要提前抽象 blob、journal、repository、workflow、event bus 或 universal runtime。

## 状态与事件规则

- feature 内部状态只由本 feature command 和 reducer 改变。
- 工具执行以 `ToolCallResult` 为唯一事实，模型、事件和 UI 分别单向派生；遵循 ADR-0027。
- 一个技术 outcome 只在调用 feature 的边界映射一次，不能经过 Ordinary 语义再变成 Multi-Agent 语义。
- read-model 是 feature 对外查询结果，不写回业务状态。
- SSE/poll cursor 属于对应 surface；切换 surface 或 conversation 时必须使旧回调失效。
- Workbench 统一历史只能保存判别后的展示摘要与原始 feature id，不合并底层 conversation 或 store。

## 前端组合规则

前端 Shell 只认识两种可显示 surface：Ordinary 与 Multi-Agent。公共类型只能承载导航和展示，例如 `ActiveWorkbenchSurface` 与 `WorkbenchItemSummary`；它们不能进入后端业务状态或持久化。

- Ordinary surface 自有 controller、SSE/poll cursor、busy、confirmation 和 view projection。
- Multi-Agent surface 自有 controller、SSE/poll cursor、busy、confirmation 和 view projection。
- 输入区的“深入协作”是单次提交意图，不是持久化全局模式。
- beta 开关只控制该动作是否可用，不改变历史 run 的类型。
- Shell 按更新时间统一展示两类历史，选择后交给对应 surface 恢复。

当前 release availability 已隐藏侧栏 Agent 集群按钮，并以行为测试保证旧 beta 偏好不能重新暴露入口、启动期不加载 Deep 历史。全局 mode、内部 Multi-Agent surface 与两套历史逻辑仍是已知迁移项；不得把入口隐藏写成 UI 已完成收口或后端已经删除。

## 迁移阶段

截至当前代码基线，阶段一至阶段三要求的唯一组合根、资源所有权和中性依赖方向已经落地。`createPanelRuntime()` 同时创建 `OrdinaryAgentFeature` 与 `MultiAgentFeature`；Ordinary route 与 Deep route 都只调用各自 facade。Ordinary 的生产模型-工具循环由 OpenAI Agents SDK adapter 通过中性 `AgentLoop` 端口提供；Host 向 ToolCenter 贡献基础工具、MCP 与 Skills 资源工具，并向 SDK loop 贡献 Sub-Agent AgentTool。Deep 保留自己的业务执行闭环。正式 Ordinary 与 Multi-Agent 都不依赖 `MinimalRuntime`。

这里的“完成”表示后端正式入口、所有权和应用层 Legacy 主链已经收口：旧 BasicAgent、Desktop session、Panel run job、应用层 Underground、`MinimalRuntime`、旧 Sub-Agent runner 与 `/api/underground/*` 已删除。阶段四的 Workbench/UI surface 隔离仍未完成；Deep 继续使用 `/api/deep/*`、独立数据分区和 `domain/underground/agent-fabric` 中有效的 run-tree 契约。

### 阶段一：事实源与依赖门

- ADR-0028 与本指南成为当前事实源。
- 增加 neutral -> feature、feature -> Panel、Multi-Agent -> Ordinary 实现、非组合根装配的依赖测试。
- 冻结 Ordinary、Sub-Agent 与正式 Deep 的关键行为测试。
- 源码字符串或固定文件名测试只有在对应行为测试覆盖后才能删除。

### 阶段二：唯一后端组合根

- `createPanelRuntime()` 装配 Ordinary 与 Multi-Agent feature。
- Deep store、control/continuation registry、active run tracking 和释放职责归 Multi-Agent factory。
- `/api/deep/*` 只做协议适配，DTO、SSE、存储格式和 Deep 内部行为保持不变。

### 阶段三：共享能力中性化

- 模型运行时只负责 provider/channel 和协议能力。
- ToolCenter 工厂归工具能力模块；Host 向 ToolCenter 装配基础工具、MCP 与 Skills 资源工具，并向 Ordinary SDK loop 装配 Sub-Agent AgentTool。
- Tool Registry 的默认 scope 使用中性 `agent-basic`；现有 `desktop-basic` 只是 Host 在兼容能力快照边界显式选择的 wire scope，不能重新写死进 ToolCenter。
- Ordinary 通过中性 `AgentLoop` 使用 OpenAI Agents SDK adapter；SDK 对象和 provider 私有字段不得进入 feature 状态。
- Deep 只依赖 tokenizer、消息完整性和压缩执行等机械能力，不依赖 Ordinary compaction facade。
- 拆除 `MinimalRuntime` service locator，改为精确注入。

阶段三已经完成，已删除的 Underground/BasicAgent/Desktop 兼容实现不得通过 facade 或兼容读取重新进入当前功能依赖图。

### 阶段四：Workbench 入口收口

- 拆分 shell/config、ordinary surface、multi-agent surface 状态。
- 用判别联合统一导航和历史展示，底层存储继续分离。
- 移除持久化全局模式和独立 Agent 集群侧栏入口，改为输入区单次“深入协作”动作。
- 验证切换 surface 后旧 SSE/poll 回调不会污染当前视图。

### 阶段五：Legacy 退役

- 已删除 `/api/underground/*`、旧 root exports、demo、应用层 Underground 和未被正式路径使用的旧实现。
- Ordinary 持久化已归 `OrdinaryAgentFeature`，只保存 `ordinary-run/v3` snapshot 与 `ordinary-conversation/v1` control document；旧 RuntimeDatabase、sidecar 和旧 snapshot 不读取、不迁移。
- Sub-Agent 已切到 SDK 原生 `call_sub_agent` / `spawn_sub_agent` AgentTool，旧 runner、事件、trace、批量与专用续读工具已退役。
- Deep 仍使用的 `domain/underground/agent-fabric` run-tree 契约保持有效；后续若迁移所有权，只做 Multi-Agent 内部机械归位，不改变 `/api/deep/*`、DTO 或业务行为。

## 验收门

每阶段运行受影响的目标测试。阶段门至少执行：

```text
pnpm build:node
pnpm typecheck:panel
pnpm build:panel
git diff --check
```

最终收口执行 `pnpm test`。必须覆盖：

- Ordinary：完成、确认、取消、失败、恢复。
- Sub-Agent：权限继承、禁止递归、完整输出、确认冒泡。
- Multi-Agent：启动、child 调度、纠正、停止、综合、历史恢复。
- 架构：依赖方向、薄 route、共享资源释放。
- Workbench：统一历史排序、单次深入协作、surface 切换隔离。

本轮不要求浏览器视觉检查；只有 UI 视觉或交互本身发生不可由结构测试验证的变化时再执行。

## 审查清单

提交前确认：

- 这个变更有明确 feature owner。
- 公开端口没有泄漏 store、registry、provider 对象或 Panel 类型。
- 没有新增第二个组合根、全局状态或 service locator。
- 共享抽象已有两个真实消费者，且只包含机械语义。
- 一个事件没有在多个层重复推导终态。
- UI 摘要没有覆盖模型或工具事实。
- 对应行为测试和依赖测试已经更新。
