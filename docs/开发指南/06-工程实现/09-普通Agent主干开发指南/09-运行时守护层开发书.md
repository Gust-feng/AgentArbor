# 运行时守护层开发书

## 目标

运行时守护层负责让默认普通 `agent` 的长任务、后台进程、端口等待、取消和残留清理变得可观察、可终止、可恢复。它不是新的工具集合，也不是 sandbox 的替代品。

当前命令工具已经能执行前台命令、启动后台进程、返回 `pid` / `logRef` / `stopCommand`、等待端口和记录截断事实。下一阶段的重点不是继续扩 `shell_command` 参数，而是在普通 run 生命周期外侧建立一个事实账本，知道“谁在跑、为什么跑、占了什么资源、如何停止、是否残留”。

## 第一版范围

第一版只做运行稳定性闭环：

- 进程登记：记录由 AgentArbor 启动的后台进程和关键前台命令事实。
- 端口事实：记录 `waitForPort` 的目标端口、ready 结果、超时事实和已知占用者。
- 取消链路：用户取消 run 时，先 abort 模型/工具循环，再按 registry 停止本 run 关联进程。
- 残留检测：run 终态、测试结束和重复启动端口时，能判断已登记进程是否仍存活。
- 日志引用：继续以 `command-log://` 作为模型可读入口，`logPath` 只保留为诊断事实。

第一版不做：

- 不做完整 shell sandbox。
- 不做 `run_memory`。
- 不做每个命令的专用工具。
- 不替模型决定下一步恢复策略。
- 不做操作系统级全局进程管理器，只管理 AgentArbor 自己启动和登记的进程。

## ProcessRegistry 契约

后端运行时设施 `ProcessRegistry` 由命令 adapter 写入，由 `OrdinaryAgentFeature` / Panel Host 查询和清理。

最小记录：

```ts
type ProcessRecord = {
  readonly processId: string;
  readonly runId?: string;
  readonly toolCallId?: string;
  readonly pid?: number;
  readonly kind: "foreground" | "background";
  readonly owned: boolean;
  readonly commandLine: string;
  readonly cwd: string;
  readonly startedAt: string;
  readonly status: "starting" | "running" | "exited" | "killing" | "killed" | "unknown";
  readonly exitCode?: number;
  readonly signal?: string;
  readonly logRef?: string;
  readonly logPath?: string;
  readonly stopCommand?: string;
  readonly ports?: readonly ProcessPortFact[];
};

type ProcessPortFact = {
  readonly port: number;
  readonly host: "127.0.0.1" | "localhost";
  readonly requestedAt: string;
  readonly status?: "ready" | "not_ready" | "timeout" | "cancelled" | "error";
  readonly ready?: boolean;
  readonly checkedAt?: string;
  readonly durationMs?: number;
  readonly timeoutMs?: number;
  readonly timedOut?: true;
  readonly cancelled?: true;
  readonly error?: {
    readonly name: string;
    readonly message: string;
    readonly code?: string;
  };
  readonly externalOccupant?: {
    readonly pid?: number;
    readonly observedBy: "netstat" | "lsof" | "ss" | "platform_probe";
    readonly ownedByUs: false;
  };
};
```

要求：

- registry 只记录真实观察到的事实，不能猜测端口占用者。
- `status: "unknown"` 只能用于进程状态无法确认的场景，不能伪装成已退出。
- `runId` 和 `toolCallId` 可为空，用于隔离的低层工具测试；正式 Ordinary run 必须传入。
- registry 数据用于运行时治理和诊断，不进入普通模型上下文，除非工具结果显式需要该事实。
- cleanup 默认执行 kill-tree 语义。Windows 使用 `taskkill /PID <pid> /T /F` 等价能力，类 Unix 使用 process group 终止；不能只杀父 pid 后宣称清理完成。
- 外部端口占用者只能作为探测事实记录；即使拿到 PID，也不能自动 kill，必须另走用户确认和命令工具边界。

## 接入点

命令 adapter：

- 后台命令启动成功后登记 `running`。
- 后台命令早退登记 `exited`。
- `waitForPort` 完成后把端口事实写回登记。
- 前台命令 spawn 成功后也登记为 `foreground` active，结束、超时或取消后更新状态；普通短命令可以不长期保留，但运行中必须可被 run cancel 和 watchdog 观察到。
- 前台命令取消、超时和后台 cleanup 都必须走 kill-tree 终止路径，避免子进程残留。

ToolCenter / AgentLoop：

- `ToolExecutionContext` 应携带 `runId` 或等价运行引用，避免 registry 只能拿到孤立 `toolCallId`。
- failed / cancelled `ToolCallResult` 与工具生命周期事件应保留进程事实字段，但不注入恢复建议；不得恢复已删除的 envelope。

OrdinaryAgentFeature：

- `cancel(runId)` abort 当前运行后，应调用 runtime guard 停止本 run 登记的后台进程。
- run 进入 `completed`、`failed`、`blocked`、`cancelled` 时，应执行一次残留检测，结果写入运行事件或诊断记录。

Panel server：

- 取消按钮必须触发后端 abort 和 registry cleanup，而不只是改变 UI 状态。
- runtime record 可以保存守护层摘要，例如残留进程数量、端口事实、清理结果。

## 当前已落地行为

当前实现已经形成三条运行时守护闭环：

- Panel 只读可见性：live run read model 和 run response 会投影 `runtimeSummary`，记录当前 run 的进程状态、端口事实、`logRef`、`logPath` 和最新 cleanup/kill-tree fact。该摘要是后端/API 事实投影，不进入普通模型上下文；主聊天 UI 暂不主动展示，后续前端诊断面板统一设计后再接入。
- 关闭清理：Panel server 关闭时会 abort 活跃 run，并对 registry 中 `owned + background + unresolved` 的进程执行 best-effort kill-tree cleanup。清理结果只记录 `killed`、`already-exited`、`unknown`、`error` 等事实；外部或前台进程不会被 shutdown cleanup 自动处理。
- 启动前端口检查：`shell_command` 在 `background=true + waitForPort` 场景启动前先探测目标端口。端口已被占用时不会启动重复进程，而是返回 `notStarted: true`、`portReady: false` 和 `preStartPortOccupancy`，其中只包含端口、PID 是否已知、归属是否由平台 PID 与 registry PID 匹配确认、观察来源等事实。

仍然保持的边界：

- registry 仍是内存账本；应用重启后不追杀历史进程。
- 即使端口探测拿到外部 PID，也不能自动 kill。
- 只有平台观测到的 PID 与 registry 中活跃自有进程 PID 匹配时，才能标记 `ownedByUs: true`；只有 registry 端口记录而无 PID 匹配时，归属必须保持 `unknown`。
- `runtimeSummary`、cleanup fact 和端口占用 fact 只能描述事实，不能附带“下一步应该怎么做”的固定建议。

## 首轮验收门

第一轮实现必须覆盖以下验收：

- 启动一个后台 dev server，registry 能查到 `pid`、`commandLine`、`logRef`、`waitForPort` 和 `portReady`。
- `waitForPort` 成功时返回 `portReady: true`；超时时返回 `portReady: false` 和超时事实。
- 同一 run 取消后，已登记后台进程被停止；registry 状态进入 `killed` 或 `exited`。
- 同一 run 取消时，正在执行的前台命令也被终止并更新为 `killed`、`exited` 或 `unknown`。
- 进程已经自然退出时，清理逻辑不能报成功杀死，只能记录实际退出或 unknown。
- 重复启动同一端口时，能返回已有 registry 事实；如果不是 AgentArbor 启动的进程，只能记录外部端口占用事实，不能自动杀外部进程。
- 同一 session 内，Run #1 结束后如果残留后台进程，Run #2 启动同一端口时必须能报告 registry 残留或端口不可用事实。
- 应用重启后 registry 可以丢失内存记录，但端口探测仍应报告端口不可用，并明确不能确认占用者归属。
- 全量测试后无已登记测试 server 残留。

最低验证：

- `pnpm build:node`
- `pnpm typecheck:panel`
- 命令 adapter 相关单测。
- OrdinaryAgentFeature 取消链路测试。
- runtime record / panel stream 相关投影测试。
- `git diff --check`

## 开发顺序

推荐顺序：

1. 新增 registry 类型、内存实现和查询 API，不接入 UI。
2. 让 `shell_command background=true` 写入 registry。
3. 让 `waitForPort` 写回端口事实。
4. 让 run cancel 调用 registry cleanup。
5. 增加 runtime record 只读摘要。
6. 再考虑持久化 registry 或跨重启恢复。

每一步都必须保持命令工具仍是通用执行环境。守护层只处理事实、生命周期和清理，不替模型选择命令，也不把普通 shell 场景拆成微工具。
