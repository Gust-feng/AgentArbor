# 智能通道契约

智能通道是 AgentArbor 调用模型的统一契约。它不是新的事实源，也不是产品节点；它让模型能力以可审计、可替换、可失败和可观测的方式服务各层。

所有真实模型调用必须通过智能通道或 `AgentTurnRuntime`。领域模块、应用编排、CLI、Desktop Shell 和测试入口都不能直接绑定 provider SDK 或 provider adapter；应用组合根只能负责装配 provider adapter 和智能通道，不能把 provider-specific 字段泄漏给业务流程。

AgentArbor 的智能通道是内部契约，不是 provider SDK 的透传层。当前真实协议只做 OpenAI 格式：`openai_compatible_chat_completions` 和 `openai_responses`。OpenAI 格式 adapter 应优先使用 OpenAI 官方 TypeScript SDK 处理请求、工具 schema、stream、usage 和 provider 错误归一化；不得让 SDK 的对象结构反向污染 `ModelRequest`、`ModelResponse`、ToolCenter 或业务流程。其他 provider 协议后续再扩展。

## 核心对象

### ModelRequest

`ModelRequest` 描述一次模型调用的内部请求。它必须说明调用目的、调用方、输出契约、约束和预算。

```ts
interface ModelRequest {
  requestId: string;
  traceId: string;
  callerRef: string;
  purpose:
    | "desktop_agent"
    | "desktop_chat"
    | "intent_profile"
    | "rootlet_candidate"
    | "counterfactual"
    | "parent_synthesis"
    | "convergence_decision"
    | "plan_draft"
    | "execution_draft"
    | "verification_advice"
    | "governance_advice";
  inputRefs: string[];
  sanitizedMessages: ModelMessage[];
  outputContract: ModelOutputContract;
  constraintRefs: ConstraintRef[];
  budget: ModelBudget;
  sensitivity: "public" | "internal" | "restricted";
  requestedAt: string;
}
```

`sanitizedMessages` 只保存已清洗、已授权进入模型上下文的内容。未授权 Global Soil 内容、密钥、完整运行私密材料和平台凭证不能进入请求。

### ModelResponse

`ModelResponse` 描述 provider 返回后经过智能通道归一化的结果。

```ts
interface ModelResponse {
  responseId: string;
  requestId: string;
  providerId: string;
  model: string;
  status: "completed" | "failed" | "cancelled";
  outputKind: "candidate" | "draft" | "explanation" | "evidence_suggestion";
  structuredOutput?: unknown;
  textOutputRef?: ArtifactRef;
  usage?: ModelUsage;
  finishReason?: "stop" | "length" | "tool_call" | "content_filter" | "error";
  validation: ModelOutputValidationResult;
  completedAt: string;
}
```

`structuredOutput` 仍然只是单次模型产出。它必须先进入调用方或父层 agent 的候选池、收束判断、Plan 草案或治理建议流程，再接受确定性边界守卫；不能由 provider response 直接写入 Plan、Workflow IR、Run Memory 或 Global Soil。

### ModelUsage

`ModelUsage` 归一化 provider 用量，供成本、审计和观测使用。

```ts
interface ModelUsage {
  inputTokens?: number;
  outputTokens?: number;
  totalTokens?: number;
  cachedInputTokens?: number;
  uncachedInputTokens?: number;
  reasoningOutputTokens?: number;
  estimatedCostUsd?: number;
  latencyMs?: number;
  firstTokenLatencyMs?: number;
  outputDurationMs?: number;
  outputTokensPerSecond?: number;
}
```

用量字段可以缺失，但不能伪造。provider 不返回的字段应保持空值，并在观测层显示为 unknown。
`inputTokens` 对应 provider 的总 prompt / input tokens，是整次模型请求上下文，不等同于用户这一条消息的新输入；系统提示、工具 schema、历史对话、附件投影和工作区上下文都可能包含在内。`cachedInputTokens`、`uncachedInputTokens` 和 `reasoningOutputTokens` 只能来自 provider usage 细分字段，例如 DeepSeek Chat Completions 的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 或 OpenAI usage details；不能由前端或字符数估算。OpenAI-compatible Chat Completions 在 provider profile 明确支持时，应在流式请求中启用 provider 原生 usage 选项，例如 DeepSeek / OpenAI 的 `stream_options.include_usage`，并读取尾部 usage chunk。用户界面展示输入侧 token 时，应采用主流的“总输入 tokens（cached 子集）”表达，例如 `7.2K tokens (2.7K cached)`；不能把总 prompt tokens 表达成单条消息的新输入，也不能在 provider 未返回 cache split 时伪造 cached。
`firstTokenLatencyMs` 只能在真实流式响应中由 adapter 观测到首个用户可见输出 delta 时填写；`outputTokensPerSecond` 只能在可确认 output token 数与输出耗时同时存在时派生，不能把字符速度冒充为 token 速度。普通用户气泡若展示 token 信息，应保持为回答下方的紧凑元信息，不替代或改写模型正文；展示形态优先使用低对比度的输入 token（含 cached）、输出 token、速度和耗时，不做调试面板。

上下文窗口管理不能使用字符数粗估作为最终裁剪依据。输入 token 统计必须来自模型能力目录、OpenAI SDK / provider 返回的 usage、专用 tokenizer 或 provider 计量能力；无法精确计量时只能保守触发 AI 压缩，不能用估算结果直接丢弃关键上下文。

达到模型上下文阈值时，智能通道或 Context Pack 应调用模型执行安全压缩，压缩目标是让普通 agent loop 继续运行，而不是决定任务完成。压缩输出只能保留目标、最近对话、工具证据、失败边界、未完成事项和必要引用；raw prompt、raw provider response、raw tool output、secret、token 和 hidden reasoning 不得进入压缩结果。

### ModelCallRef

`ModelCallRef` 是正式材料引用模型调用的方式。

```ts
interface ModelCallRef {
  requestId: string;
  responseId?: string;
  providerId?: string;
  model?: string;
  outputKind: "candidate" | "draft" | "explanation" | "evidence_suggestion";
  eventRefs: string[];
  validationStatus: "pending" | "passed" | "failed";
}
```

Plan、ExecutionPlan、Verification Result 或 Governance Review 可以引用 `ModelCallRef`，但不能把未验证模型正文当成事实复制进去。

## 接口边界

### ModelProvider

`ModelProvider` 是 provider adapter 的最小接口。它只处理供应商协议差异。

```ts
interface ModelProvider {
  providerId: string;
  complete(request: ModelRequest): Promise<ModelResponse>;
}
```

Provider adapter 不能读取或写入 Global Soil、Plan Package、Fruits、Governance Registry 或任务状态机。

Provider adapter 必须把供应商响应归一化为 `ModelResponse`，不能把原始 provider response 结构泄漏到 Underground、Aboveground、Verification、Governance 或 Observation Panel。

### IntelligenceChannel

`IntelligenceChannel` 是业务层唯一能调用的模型入口。

```ts
interface IntelligenceChannel {
  request(request: ModelRequest): Promise<ModelResponse>;
  validateResponse(request: ModelRequest, response: ModelResponse): ModelOutputValidationResult;
}
```

智能通道负责：

- 校验请求是否带有目的、预算、输出契约和授权上下文。
- 发布模型调用事件。
- 调用合适的 provider adapter。
- 归一化 provider 响应。
- 执行输出契约校验。
- 返回可失败结果，而不是抛给业务层自行猜测。

普通 Desktop Agent 的模型调用目的必须使用 `desktop_agent`。历史 `desktop_chat` 只能用于读取和兼容旧记录，不能作为新的默认 AgentDefinition purpose。

Provider 网络错误、provider 返回失败、输出契约失败和请求校验失败，都必须被智能通道归一化为 `ModelResponse.status="failed"` 与 `model.failed` 事件。普通 Agent、Panel route 和前端 read-model 只消费这些归一化失败事实，不能直接解析 provider SDK 私有错误对象、raw response 或网络异常正文来决定产品状态。

## 事件契约

智能通道最低必须发布以下事件：

| 事件 | 触发时机 | 最低字段 |
| --- | --- | --- |
| `model.requested` | 请求通过通道校验并准备调用 provider | `requestId`、`traceId`、`purpose`、`callerRef`、`providerId`、`model`、`budget`、`inputRefs` |
| `model.completed` | provider 返回且响应归一化完成 | `requestId`、`responseId`、`usage`、`finishReason`、`outputKind`、`validationStatus` |
| `model.failed` | provider 失败、超时、输出不合约或预算越界 | `requestId`、`failureKind`、`retryable`、`fallback`、`sanitizedErrorRef` |

事件不得包含：

- API key、access token 或 provider 凭证。
- 未清洗完整 prompt。
- 未授权 Global Soil 内容。
- 用户隐私正文。
- provider 原始错误中的敏感字段。

## 配置边界

首个真实 provider 接入可以使用环境变量：

```text
AGENTARBOR_MODEL_API_KEY
AGENTARBOR_MODEL_NAME
AGENTARBOR_MODEL_BASE_URL
```

规则：

- `AGENTARBOR_MODEL_API_KEY` 只由 provider adapter 读取。
- `AGENTARBOR_MODEL_NAME` 是运行配置，不是代码常量。
- `AGENTARBOR_MODEL_BASE_URL` 仅用于兼容网关或自托管 OpenAI-compatible endpoint。
- 环境变量不得写入 EventLog、Snapshot、Plan Package、Run Memory、Experience Candidate 或 Global Soil。

### 模型市场与模型列表

模型市场属于模型运行时的配置入口，不属于工具市场、MCP 市场或普通 Agent loop。它只负责帮助用户选择 provider profile、保存本地配置、同步模型列表，并把最终运行配置交给智能通道。

当前模型市场只实现 OpenAI-compatible provider profile：

- 常驻厂商以 preset 形式提供，至少包含 DeepSeek、月之暗面、GLM 和 MiniMax。
- 用户可以创建自定义 provider profile，配置 `providerKind`、`protocolKind`、`baseUrl`、`model`、`defaultAiMode` 和本地 API Key。
- API Key 只进入本地 secret store；`/api/config`、模型市场、模型列表、capability 投影和面板可见状态都不得返回原始密钥。
- 模型列表通过 provider profile 的 OpenAI-compatible 模型列表接口获取，默认是 SDK base URL 下的 `/models`。只有 OpenAI 官方裸域 `https://api.openai.com` 可以在 SDK base URL 层补 `/v1`；其他厂商的 `baseUrl` 必须按用户或 preset 配置原样使用，不能统一追加 `/v1`。
- 模型列表获取失败只能返回安全错误，不能泄漏 API Key、请求头、raw provider response 或 provider 原始错误正文。

模型市场不得替普通 Agent 选择工具、决定停止、改写任务目标或判断模型能力是否足以完成任务。模型能力目录只影响请求装配、工具 schema、stream 能力和上下文窗口边界。

### 流式输出

面板的流式体验必须从真实模型请求开始，而不是在 provider 完成后再把完整文本切片伪装成实时生成。

规则：

- OpenAI-compatible Chat Completions 与 OpenAI Responses adapter 在运行时提供 `onOutputDelta` 时必须启用 provider stream。
- provider adapter 只能把安全的输出 delta 投影为 `ModelOutputDelta`；工具调用参数、hidden reasoning、raw provider response 和密钥不得作为可见 delta 输出。
- Panel / Basic Agent 只展示用户可见目的的 delta，例如普通桌面 Agent 回答、桌面对话和直接回答；内部规划、验证、压缩或结构化调用的 delta 不进入助手气泡。
- `model.output.delta` 事件必须携带安全 `delta` 字段，前端可以在 run 仍处于 active 状态时聚合最新 model call 的 delta 并展示正在生成的助手回复。
- 模型最终完成后，最终可见回答仍以归一化 `ModelResponse.textOutput` / visible output 为准；流式 delta 是进行中体验，不是新的事实源。

## 验证规则

- 模型输出必须匹配 `outputContract`；不匹配时返回 failed 或 validation failed。
- 单次 AI 输出只能进入候选池、草案或建议层；进入正式材料前必须通过父层 agent 收束，并通过调用方的确定性边界验证。
- OpenAI 格式 adapter 只能在显式配置 provider 时发起网络请求；默认 demo 和测试必须使用 fake/stub runtime，不触发真实网络。
- OpenAI 格式 adapter 应通过官方 SDK 或明确的测试注入 transport 发起请求；如果 SDK 初始化、transport 或 provider 配置不可用，必须返回清晰的 provider configuration failure。
- hard constraint 不能被模型输出覆盖。
- Path Bias 只能影响模型请求的偏好和排序提示，不能覆盖约束。
- LLM-as-judge 只能作为 Verification / Governance 的建议输入，不能单独决定通过。

## 首个接入范围

首个真实模型接入应围绕 Underground Cognitive Runtime 的 AI 驱动主线推进：

- Intent Core 可以请求目标结构化建议，并把结果作为 GoalIntentProfile 候选进入后续守卫。
- Rootlet 可以请求候选方向、风险、证据建议或反例。
- Parent Synthesis 和 Convergence 可以通过统一 AgentTurnRuntime 请求收束判断，但推荐、合并、淘汰、用户澄清或停止决策必须回到正式 convergence 结果，并接受 hard constraint、预算、状态机和引用一致性验证。
- Handoff / Plan Steward 可以使用上层 agent 叙事组织 Plan，但只能打包已收束、已验证的候选。

工程边界不得替 agent 思考：`outputContract`、parser、visibleOutput、validation、budget 和 permission 只负责结构裁剪、校验、失败归一和引用边界；不得把这些机制写成目标理解、候选排序、工具选择或收束裁决的主逻辑，也不得以脱敏或安全投影改写普通模型输出。

Aboveground、Verification、Governance 的真实模型调用应在智能通道和 AgentTurnRuntime 稳定后逐步接入。
