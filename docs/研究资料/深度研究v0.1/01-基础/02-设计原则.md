# AgentArbor 设计原则

## 原则 1：目标高于工作流

AgentArbor 可以使用工作流，但不能被工作流定义。真正的核心是目标、状态、反馈与演化决策。

固定工作流只能保证系统有秩序，却不能保证系统聪明。AgentArbor 需要的是有边界的自主性：在目标不变的前提下，允许路径不断变化。

## 原则 2：计划是当前假设，不是真理

所有计划都必须被视为“当前最优假设”。执行过程中，如果测试、用户反馈、架构压力或技术债证明计划不再可靠，系统必须允许重规划。

计划可以被冻结，但冻结不是永恒。冻结的意义是防止偷偷偏航，而不是禁止进化。

## 原则 3：Agent 不能只会执行，还要会怀疑

多 Agent 系统最大的问题不是不会做事，而是太容易一起同意错误方案。

AgentArbor 必须内置反对者角色：Critic、Review、Risk、Debt、Security。它们不负责让系统更快，而是负责让系统少长歪。

## 原则 4：每次行动必须留下解释

自主性若没有解释，就会变成黑箱。

AgentArbor 的每次行动都应当能回答：

- 为什么做？
- 依据是什么？
- 修改了什么？
- 验证了什么？
- 是否影响未来？

这些解释进入事件日志、文档和 Git commit。

## 原则 5：验证决定保留，生成不等于完成

AI 生成的代码、文档、任务图、能力配置都只是候选物。它们必须经过验证，才能成为系统的一部分。

验证包括：测试、构建、类型检查、代码审查、架构一致性、目标一致性、能力验证、安全检查。

## 原则 6：历史不可抹除，只能被覆盖、标记或分化

后续迭代可以改变之前的结论，但不能假装之前没有发生过。

AgentArbor 应当使用 supersede 机制：旧决策可以被新决策覆盖，但需要记录原因、影响范围和迁移路径。

## 原则 7：用户是园丁，不是流水线操作员

用户不应该被迫一步步指挥 Agent 写文件。用户负责给出目标、边界、方向变化和关键确认点。

AgentArbor 负责在边界内寻找路径。

## 原则 8：能力必须可扩展、可审查、可调配

AgentArbor 的能力不应硬编码在少数 Agent 内。能力应通过 MCP、skills、`.agent`、plugins、built-in tools 和 capability routing 统一组织。

用户可以添加能力，系统也可以建议、组合、验证能力。

## 原则 9：不要追求“永不失败”，要追求“失败后知道怎么处理”

真正自主的系统不是不失败，而是能识别失败类型：修复、重构、转向、分化、重生、暂停、人工确认。

## 原则 10：灵魂来自世界观

AgentArbor 的灵魂不是 UI，也不是大模型，而是它看待软件的方式：软件可以被孕育，可以长歪，可以修剪，可以分化，也可以重生。
