# ADR-0032：路径记忆与长期记忆回流架构

日期：2026-07-26

状态：Accepted

关系：本 ADR 补充 [ADR-0028](ADR-0028-AgentArbor统一Workbench与功能模块化单体架构.md) 的按功能闭环模块化边界，细化 [ADR-0014](ADR-0014-Agent集群与运行即沉淀.md) 的“运行即沉淀”原则，并以 `PathMemory` 取代其中依赖 Direction Handoff、Growth Plan 和 Agent 集群的旧 `RunMemory` 当前实现口径。它不改变 [ADR-0030](ADR-0030-AgentArbor-Pi原生底层架构.md) 中 Pi Session 与 Ordinary 业务事实的所有权。

## 背景

AgentArbor 需要从真实任务中积累经验，但“把对话存下来”“把工具输出放进向量库”都不能直接回答什么是记忆。若没有明确边界，记忆系统容易出现四类问题：

- 把会话历史、运行日志、长期事实和可复用经验混成一个数据池。
- 每次运行结束后让模型自由总结，并把总结直接注入后续任务，形成不可追溯的自我强化。
- 用相似度搜索替代写入治理、适用范围和失败证据。
- 为未来 Governance、Global Soil 和 Multi-Agent 提前建设统一 runtime、图数据库或全局状态。

当前生产主线只有 Ordinary Agent。Pi Session 是模型实际消费的会话树事实源；Ordinary 是 run 状态、工具事实、终态和结果的 owner。现有 `src/domain/fruits/contracts.ts` 中的 `RunMemory` 强制要求 Direction Handoff、Growth Plan、Nutrient Patch 等字段，不能描述当前线性 Ordinary run，也不能作为本期实现基础。

外部开源方案提供了两类有价值的经验：Mem0 把长期记忆做成从输入中提取、可更新、可检索的离散事实；LangGraph 把短期 thread state 与 namespace/key/JSON 形式的长期 Store 分开。它们共同说明“持久化”和“召回”是两个边界。但 AgentArbor 当前没有必要复制其向量基础设施、自动事实提取或工作流 runtime；第一阶段首先需要建立可信的本地运行事实层。

### 外部方案取舍

| 项目 | 已验证的核心做法 | 对 AgentArbor 的启发 | 第一阶段取舍 |
| --- | --- | --- | --- |
| Mem0 | 从消息中提取离散事实，通过 API/SDK 写入并用向量检索，支持作用域、更新和历史 | 语义事实应与原始会话分开，检索不是事实源 | 不引入自动提取和向量后端；以后用于 ExperienceCandidate 设计参考 |
| Letta | 小量 Memory Blocks 可常驻上下文并由 memory tool 编辑；大量 Archival Memory 通过插入/搜索工具按需使用 | Agent 主动写入适合可审查的语义记忆，常驻与检索记忆应分层 | 不让 Agent 自行决定是否保存运行路径，也不在第一阶段常驻 prompt |
| LangGraph | thread/checkpointer 保存短期状态；长期 Store 使用 namespace、key 和 JSON 文档，由应用节点显式读写 | 会话状态与跨 run 记忆必须拥有不同生命周期和存储边界 | 借鉴分层，不引入 graph runtime 或通用 Store 抽象 |
| Graphiti | 以 episode 为输入增量构建带双时间语义的实体/关系图，并结合语义、关键词和图检索 | 动态事实冲突和历史关系需要来源时间与有效时间 | 当前没有实体关系查询需求；不引入图数据库和 LLM 实体抽取 |

因此，本 ADR 采用“先可靠采集客观 PathMemory，再生成候选，再治理召回”的顺序。外部框架可以在后续作为 adapter 或算法参考，但不替代 AgentArbor 的 feature owner。

## 决策

### 1. 记忆的定义

AgentArbor 中的记忆是：**为了影响未来任务而被持久化，并具有明确来源、作用域、类型、版本和生命周期的事实或经验。**

满足以下条件的数据才能称为记忆：

1. 有稳定身份，不依赖当前进程中的对象地址或 live handle。
2. 有来源和证据，能够回答“从哪个运行、用户决定或治理动作产生”。
3. 有作用域，能够回答“属于哪个用户、工作区、项目或目标范围”。
4. 有明确类型，能够区分客观路径事实、候选经验、稳定偏好和路径倾向。
5. 有版本或不可变语义，后续修订不能静默覆盖历史含义。
6. 有读取和删除边界，不能因为写入过就永久、无条件进入模型上下文。

以下数据本身不是长期记忆：

- Pi Session 中的完整对话历史。
- Ordinary snapshot、EventLog 或原始工具结果。
- 当前 Task Soil、附件字节、live activity 和进程 handle。
- 模型临时推理、未经证据支持的总结或 UI 展示摘要。

这些数据可以成为记忆的来源，但不能被换名后直接当作长期记忆。

### 2. 路径记忆是自动形成的运行事实

`PathMemory` 是一次真实 Ordinary run 结束后形成的、只读的结构化路径档案。它记录：

- 用户本轮请求和上下文引用。
- 冻结的工作区作用域。
- 实际发生的工具事实顺序和父子关系。
- run 的真实终态、错误或取消原因。
- 当前系统确实拥有的验证状态和证据引用。

每个进入稳定终态的 Ordinary run 都应自动形成一条 `PathMemory`，包括 `completed`、`failed`、`blocked` 和 `cancelled`。失败和阻塞路径同样有长期分析价值；工程层不得用关键词、工具数量或回答文案猜测哪些才是“真实任务”。

当前 Ordinary 是会话轮次驱动，不维护独立任务生命周期。因此第一阶段的一条 `PathMemory` 对应一个 Ordinary run，而不是人为拼接出的“任务”。未来若出生显式 Task/Plan 能力，可以通过来源引用聚合多条 PathMemory，但不能反向改写原记录。

自动采集不等于自动复用。PathMemory 在第一阶段默认不进入模型上下文，也不直接成为 Global Soil 或 Path Bias。

### 3. 三种写入机制必须分开

长期记忆不是全部由 Agent 主动写入。AgentArbor 区分三种写入机制：

| 机制 | 触发者 | 写入对象 | 当前状态 |
| --- | --- | --- | --- |
| 生命周期采集 | 确定性的 feature 生命周期 | `PathMemory` 客观运行事实 | 第一阶段实现 |
| 显式记忆写入 | 用户指令或 Agent 在授权工具中提出 | 偏好、事实或经验候选 | 后续实现 |
| 后台归纳 | 受管分析任务 | `ExperienceCandidate`、冲突或去重建议 | 后续实现 |

Agent 主动写入只适合语义对象，因为“用户偏好是什么”“哪些经验可复用”需要理解与判断。运行是否结束、调用了哪些工具、工具结果是什么，则必须从 Ordinary 权威事实确定性采集，不能要求 Agent 记得调用一个 memory tool 才留下记录。

显式写入和后台归纳未来也只能生成候选，不能绕过来源、作用域、冲突处理和 Governance 直接成为全局真相。

### 4. 记忆分层与回流链路

长期方向采用以下单向链路：

```text
Pi Session                         Ordinary run facts
（会话上下文事实）                  （状态、工具、结果事实）
        |                                   |
        +--------- 仅作为来源引用 ----------+
                                            |
                                   PathMemory
                                   （自动、客观、只读）
                                            |
                            Agent / 后台分析（后续）
                                            |
                               ExperienceCandidate
                                            |
                                  Governance（后续）
                                            |
                         PathBias / 长期偏好 / 稳定事实
                                            |
                              按任务检索并作为材料提供
```

各层职责如下：

- `PathMemory`：回答“上次实际发生了什么”。
- `ExperienceCandidate`：回答“其中什么可能值得复用，以及适用前提是什么”。
- `PathBias`：回答“遇到相似任务时，可以优先考虑什么路径”。
- 稳定偏好或长期事实：回答“用户或工作区长期成立的事实是什么”。
- Governance：决定候选是否晋升、冲突如何处理、何时过期或退役。

PathMemory 不应包含事后生成的“成功模式”“偏离原因”或“复用建议”，除非来源 feature 已经拥有这些事实。语义解释属于 ExperienceCandidate，不得在采集阶段伪造。

### 5. 所有权和依赖方向

新增独立 `PathMemoryFeature`，完整拥有：

- PathMemory command、query 和 event facade。
- PathMemory schema、校验和文件系统 repository。
- 幂等采集、启动对账、删除和资源释放。
- PathMemory read-model 与行为测试。

Ordinary 继续拥有源 run。它只通过公开 query/event facade 提供已经稳定的终态事实，不导入 PathMemory 实现、不写 PathMemory repository，也不因为记忆失败改写 run 终态。

两者通过精确端口协作：

```text
createPanelRuntime()
  -> OrdinaryAgentFeature
  -> PathMemoryFeature
  -> OrdinaryPathMemoryConnector
       -> 订阅 Ordinary 稳定终态通知
       -> 调用 PathMemory command
       -> 启动时执行缺失记录对账
```

`OrdinaryPathMemoryConnector` 是跨 feature 接线 adapter，不拥有状态、不解释任务成败、不形成第二事实源。唯一生产 Composition Root 负责创建和释放它。不得建设 universal MemoryManager、全局 event bus、统一 Run repository 或第二个 Composition Root。

### 6. 采集时机是“终态事实稳定”，不是刚看到终态字段

Ordinary 的 `completed` 表示 provider 正常结束且模型不再调用工具，不表示任务已经通过验收。用户取消后，已经执行的工具仍可能在后台形成最终事实。因此 PathMemory 的实时触发点必须满足：

1. Ordinary 已提交 `completed / failed / blocked / cancelled` 终态。
2. 本 run 已接受的工具调用已经完成结果收口，或被明确记为 outcome unknown。
3. 终态 snapshot 和工具事实已经持久化。
4. Ordinary 对该 run 的执行资源已经进入可释放状态。

Ordinary 应公开“稳定终态事实可读取”的通知和 query，而不是让 PathMemory 监听 UI、SSE 文案或直接读取 Ordinary store。

进程可能在终态与记忆写入之间退出，因此实时触发只负责低延迟，启动对账负责完整性。对账从 Ordinary 公开 query 列出终态 run，与 PathMemory 的 `sourceRunId` 唯一索引比较，补写缺失记录。两条路径使用同一幂等 command。

### 7. PathMemory 必须保留事实，不复制大正文

PathMemory 保存用户本轮请求、上下文引用、工作区作用域、工具事实索引、终态和必要错误信息。它不复制：

- 完整 Pi transcript。
- 工具 input/output 正文和附件字节。
- assistant 完整回答。
- stdout/stderr、文件正文或 ToolOutputStore 内容。

这些内容继续由原 owner 保存，PathMemory 使用稳定 source ref、tool fact ref 和 answer ref 指向它们。若来源会话或证据被删除，PathMemory 的路径元数据仍可读，但对应引用可以诚实变为 unavailable；不得用缓存摘要冒充原证据。

自动采集在本地 runtime 内保存原始用户请求，不做关键词脱敏或摘要替换。PathMemoryFeature 必须提供按 id 和来源删除的 command，为后续记忆管理 UI 保留正式删除边界；第一阶段不做云同步或导出。

### 8. 检索和注入必须晚于治理

第一阶段只提供确定性 query，不做模型召回。后续检索遵循：

1. 先按用户、工作区和显式任务作用域过滤。
2. 再使用关键词、结构字段或向量相似度召回候选。
3. 再按时效、证据、失败记录和治理状态排序。
4. 只把有限、可追溯的候选作为模型材料提供。
5. 模型可以采用、调整或拒绝，不得被 Path Bias 机械锁定。

向量索引是可重建的检索投影，不是 PathMemory 事实源。图数据库只有在出现真实实体关系查询需求后才考虑；第一阶段不引入。

### 9. 旧 RunMemory 口径的处理

自本 ADR 生效后：

- 当前和新增实现统一使用 `PathMemory`，不再设计第二个 `RunMemory v2`。
- 旧文档中的 Run Memory 在表达“单次运行沉淀”时，按本 ADR 的 PathMemory 理解。
- 旧 `RunMemory` 中 Direction Handoff、Growth Plan、Nutrient Patch、successPatterns 等字段不进入第一阶段 schema。
- `ExperienceCandidate.sourceRunMemoryId` 后续改为 `sourcePathMemoryId`，不保留双写或永久 alias。
- 配置与 Research 中未启用的 `run_memory` stub 不代表当前记忆能力；接入检索时应按新契约清理或替换，不能直接启用旧 adapter。

## 第一阶段边界

第一阶段只实现：

- Ordinary 稳定终态事实的公开查询与通知。
- PathMemory v1 schema、文件持久化和幂等采集。
- 实时采集、启动缺失对账和有序释放。
- 按 id、source run、conversation 和 workspace 的确定性查询。
- 删除 command、错误语义和聚焦行为测试。

第一阶段明确不实现：

- 向量数据库、embedding、rerank 或图数据库。
- Agent memory tool、自动偏好提取或用户事实抽取。
- ExperienceCandidate、PathBias、Governance 或 Global Soil 生产运行时。
- 后台 LLM 总结、聚类、去重、冲突合并或自动遗忘。
- 模型上下文注入、Research 工具接入或完整记忆管理 UI。
- Multi-Agent、Sub-Agent 独立记忆或跨 feature 统一 run memory。

## 后果

收益：

- 每次真实运行都会留下可追溯路径，不依赖 Agent 主动调用工具。
- 会话、运行事实、路径档案和治理后长期知识各有唯一 owner。
- 第一阶段不需要新增数据库或模型调用，成本和失败面可控。
- 后续可以从真实 PathMemory 演进 ExperienceCandidate 和 PathBias，而不需要迁移一批模型生成的伪事实。

代价：

- 第一阶段的 PathMemory 可查询但不会提升模型表现，价值主要是建立可靠数据基础。
- PathMemory 引用的原始证据可能随来源删除而不可用；若未来要求独立证据保留，需要单独定义保留和删除策略。
- 当前 Ordinary run 不是完整任务对象，多轮任务只能保留逐 run 路径，直到真实 Task/Plan 聚合能力出生。

## 不采用

- 不直接接入 Mem0、LangGraph Store 或其他记忆框架作为当前业务 owner。
- 不把 Pi Session、Ordinary snapshot 或 ToolOutputStore 改名为记忆库。
- 不让 Agent 是否调用 `memory_write` 决定一条运行路径是否被记录。
- 不把每次自动采集的 PathMemory 直接注入后续 prompt。
- 不用“completed”“执行过测试命令”或回答中的成功措辞推断 verification 通过。
- 不建设统一 MemoryManager、通用知识图谱或全局工作流。
