# 动态工作流与元循环

## 1. 为什么必须有工作流

没有工作流，AgentArbor 会散成一堆 Agent 的即兴表演。

系统必须有基本秩序：

- 先理解目标；
- 再形成当前计划；
- 再执行；
- 再验证；
- 再反思；
- 再决定继续还是改变。

## 2. 为什么不能被工作流固定

如果工作流被写死，AgentArbor 就会失去自主性。

固定流程无法处理：

- 用户主动改变方向；
- 当前计划被证明不可靠；
- 技术栈需要替换；
- AgentApp 需要分化；
- 当前架构需要重生；
- 能力不足，需要先获取能力。

## 3. Meta Loop

AgentArbor 固定的是元循环：

```text
Observe → Orient → Plan → Act → Verify → Reflect → Evolve
```

这不是模板，而是心跳。

## 4. Workflow Graph

具体工作流应被表达为动态任务图：

- 节点：任务、验证、能力获取、文档更新、用户确认、Git 提交；
- 边：依赖、触发、阻塞、替代；
- 状态：pending、running、blocked、failed、verified、superseded、completed。

## 5. 动态修改规则

任务图可以被修改，但必须满足：

1. 修改理由被记录。
2. 被覆盖节点标记为 superseded，而不是删除。
3. 影响范围被分析。
4. 关键方向变化进入用户确认。
5. Git 或文档中保留演化记录。

## 6. 工作流的三种状态

### Draft

计划草案，还未被冻结，可以大幅调整。

### Active

当前执行任务图。可以局部调整，但重大偏移需要 Reflection。

### Superseded

被后续迭代覆盖的旧任务图。保留历史，不再执行。

## 7. 如何避免模板化

不要把“需求 → 计划 → 开发 → 测试”作为唯一流程。

应该允许系统生成这样的流程：

```text
发现能力不足 → 安装插件 → 验证插件 → 重新计划 → 开发
```

也可以生成：

```text
用户改变方向 → 影响分析 → 开分支 → 新分支规划 → 执行
```

还可以生成：

```text
连续失败 → 技术债评估 → Rebirth Proposal → 用户确认 → 新一代架构
```

## 8. 关键结论

AgentArbor 的工作流应该像树枝，不像铁轨。

铁轨只能通向预设终点。树枝会绕过石头，寻找光。
