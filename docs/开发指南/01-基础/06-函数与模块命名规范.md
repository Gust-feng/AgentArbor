# 函数与模块命名规范

## 目的

命名必须表达稳定职责，而不是表达一次迁移、视觉版本或实现者当时的想法。名称是模块边界的一部分：调用方只看公开名称，也应该能判断它负责什么、是否有副作用以及返回什么。

这份规范约束新增代码和正在修改的代码。已有稳定 API 不做机械式全仓改名；只有在迁移边界、职责修正或消除歧义时才改名，并在同一提交内完成引用迁移和验证。

## 函数命名

| 职责 | 推荐形式 | 说明 |
| --- | --- | --- |
| 创建控制器、状态或领域对象 | `createX` | 必须确实创建对象或闭包，不用于普通数据转换 |
| 从服务或持久化来源读取 | `loadX` / `fetchX` / `readX` | `load` 表示应用启动或恢复，`fetch` 表示远端请求，`read` 表示本地读取 |
| 写入或修改事实 | `saveX` / `updateX` / `deleteX` / `setX` | 名称应直接说明写入动作和对象 |
| 纯数据转换或投影 | `xFrom` / `xFor` | 例如 `workbenchInputPropsFrom`，不要用含糊的 `buildX`、`makeX` |
| 布尔判断 | `isX` / `hasX` / `canX` / `shouldX` | 不使用 `getIsX`、`checkX` 表示布尔结果 |
| React Hook | `useX` | 只用于遵守 Hook 规则的函数 |
| React 回调属性 | `onX` | 只用于组件边界传入的事件回调 |
| 事件处理实现 | `handleX` | 组件内部把事件转换为业务动作时使用 |
| 格式化、解析和序列化 | `formatX` / `parseX` / `serializeX` | 不把格式转换写成 `getX` |

`getX` 仅用于无副作用的直接读取，例如从缓存取快照或从集合取一项。它不能掩盖网络请求、状态修改、缓存失效或其他可观察副作用。`processX`、`doX`、`makeX`、`helper` 和单独的 `data` 不是可接受的公开职责名称。

## 类型、文件和组件命名

- 类型名使用业务概念或稳定 UI 契约，不使用 `New`、`V2`、`Temp`、`Redesign` 等迁移标签。
- 文件名应和其主要公开职责一致。一个文件混合多个职责时，先拆分职责，再决定是否改名。
- 组件名表达用户可见职责，例如 `PersonalWorkbench`、`ConversationTranscript`、`SidebarInlineRenameField`；`Manager` 只有在确实管理一组生命周期或资源时才使用。
- 纯投影、排序、筛选等函数放在以 `projection`、`selectors` 或具体业务职责命名的模块中，不放入 `utils` 或 `helpers` 垃圾抽屉。
- 兼容导出必须标注 `@deprecated`，并说明替代名称和退役条件；兼容名称不能继续出现在新代码中。

## 变更规则

1. 新增函数先写出它的副作用、输入输出和所有权，再选择名称。
2. 修改旧函数时，优先在当前功能闭环内完成职责化命名；不得为了统一风格顺手改动无关模块。
3. 改名必须同时迁移生产引用、测试引用和文档引用，并通过相关类型检查或测试。
4. 名称不能越过模块边界暗示不存在的能力。普通 Agent 的 helper、adapter、状态更新和一次模型工具循环不能命名为 `agent`、`plan`、`handoff` 或 `atomic`。
5. 当名称和真实职责冲突时，先修正职责边界，再决定是否保留兼容别名；不能靠别名掩盖职责混乱。

## 当前迁移示例

工作台输入和设置弹窗的 props 是纯投影，因此使用 `workbenchInputPropsFrom` 和 `workbenchSettingsDialogPropsFrom`，而不是没有明确语义的 `build...`。后续新增同类转换应遵循相同形式；这不要求一次性重命名整个仓库。
