# 约束工程

## 定位

约束工程负责把目标、非目标、权限、成本、时间、技术边界、安全要求、人工确认、验收标准、资产治理和演化边界转化为可执行契约。

它不是治理系统的重复。治理系统回答“谁有权批准、阻断、豁免和沉淀”，约束工程回答“约束如何被提取、引用、分发、执行、验证和沉淀”。

## 生命周期

```text
Soil 提供长期治理约束和资产使用约束
  -> Underground Center 提取候选约束、冲突和未知项
  -> .agentarbor Direction Handoff 记录 ConstraintRef、证据和升级条件
  -> Aboveground Center 裁决冲突并写入 Growth Plan
  -> Workflow IR 分发到任务和工具执行门
  -> Aboveground Growth 按约束切片执行
  -> Verification 验证约束满足情况
  -> Run Memory 记录约束变化、失败和偏离
  -> Fruits 携带候选经验或能力
  -> Governance 决定能否入土
  -> Soil 只吸收稳定、可治理的长期约束
```


`Constraint` 是约束事实源。任务、计划、验证和资产记录不应复制完整约束，而应引用它。

## ConstraintRef

```ts
type ConstraintRef = {
  constraintId: string;
  requiredLevel: 'hard' | 'soft' | 'preference';
  enforcementGate: Constraint['enforcementGate'];
};
```

`ConstraintRef` 是约束在具体对象中的使用方式。Direction Handoff、Growth Plan、TaskSpec、Verification Result、Capability Asset 和 Fruit Detachment 都应通过 `constraintRefs` 引用约束。

## 约束等级

- `hard constraint`：硬约束。违反后必须阻断、请求用户决策、治理复核、发起 Nutrient Request 或触发 Growth Plan Revision。
- `soft constraint`：软约束。违反后不一定阻断，但必须记录原因、影响范围和验证证据。
- `preference`：偏好约束。用于方案排序、Path Bias 和默认选择，不能覆盖硬约束或用户确认门。

## 分发规则

Underground Center 可以提出候选约束，但不能把候选约束自动变成硬约束。硬约束必须来自用户确认、治理规则、Soil 中的稳定规则，或 Aboveground Center 基于证据作出的明确裁决。

Underground Center 负责发现约束，不负责最终执行裁决。Direction Handoff 应列出约束证据、冲突和未知项，让 Aboveground Center 判断如何进入 Growth Plan。

Aboveground Center 负责把约束分发到 Growth Plan、Workflow IR 和任务切片。Aboveground Growth 只能接收与自己任务相关的约束切片，但这些切片必须保留回溯到完整 `Constraint` 的引用。

Verification 负责验证约束是否满足。验证结果必须能说明：

- 哪些硬约束已满足。
- 哪些软约束被偏离以及偏离理由。
- 哪些偏好约束被 Path Bias 采用或拒绝。
- 哪些约束需要 Nutrient Request、Growth Plan Revision、用户确认或治理复核。

## 冲突与养料请求

约束冲突不能由执行个体自行解决。

当出现以下情况时，应触发 Nutrient Request 或 Growth Plan Revision：

- 硬约束之间冲突。
- Path Bias 推荐路径与当前硬约束冲突。
- Soil 中的长期规则与用户当前确认目标冲突。
- Aboveground Growth 执行时发现约束前提不成立。
- Verification 发现约束证据不足或违反。

如果冲突涉及用户目标、权限、成本、安全或长期资产治理，Aboveground Center 必须根据 `conflictPolicy` 请求用户确认或 Governance Review。

## 沉淀规则

Run Memory 应记录本次运行中新增、修改、违反、豁免或退役的约束。Experience Candidate 可以携带约束使用经验，但不能自动进入 Soil。

只有满足以下条件的约束才可以沉淀为 Soil 的长期治理规则或 Capability Asset 元数据：

- 已在至少一次运行中被验证。
- 有明确适用范围和不适用条件。
- 有证据引用和责任归属。
- 经过 Governance 或用户确认。

临时任务约束不能自动成为长期资产约束。
