# ADR-0020: 智能通道与模型接入边界

日期：2026-05-02

状态：Accepted

取代说明：关于 Ordinary 主循环、会话历史、上下文压缩和 provider binding 的具体实现，已由 [ADR-0030-AgentArbor Pi 原生底层架构](ADR-0030-AgentArbor-Pi原生底层架构.md) 取代。本 ADR 仍定义中性 `AgentLoop` / `IntelligenceChannel` 端口以及 Multi-Agent 的业务隔离边界。

## 决策

模型能力是中性基础设施，不是某个 feature 的内部 adapter，也不是产品工作流节点。AgentArbor 用两个窄端口承接不同调用形态：

```text
Ordinary Agent
  -> AgentLoop
  -> Agent Session adapter（Pi AgentHarness/Session）

Deep manager / child / synthesis 与其他单轮模型消费者
  -> IntelligenceChannel / AgentTurnRuntime
  -> OpenAI protocol adapter
```

两条端口共享冻结模型配置、连接解析、协议能力、用量、流式输出、失败归一化和 provider adapter 边界，但不共享业务状态。`AgentLoop` 负责机械性的模型-工具-模型循环；`IntelligenceChannel` 负责单次归一化模型请求；`AgentTurnRuntime` 在其上提供 Deep 所需的工具循环。调用 feature 自己解释完成、暂停、失败和业务输出。

任何 feature、route、Panel controller 或领域模块都不能直接绑定外部 SDK、provider adapter、provider 私有字段或原始流式协议。外部 SDK 只能存在于模型 adapter；`model-runtime` 是创建 `AgentLoop` 与 `IntelligenceChannel` 的唯一中性工厂，后端 Composition Root 负责装配。

## 当前协议范围

生产只支持两种 OpenAI 格式：

- `openai_responses`
- `openai_compatible_chat_completions`

Ordinary 的模型-工具循环使用 Pi AgentHarness/Session；单轮模型消费者继续通过 `IntelligenceChannel` 使用各自的中性 provider adapter。当前支持的模型协议仍是 OpenAI Responses 与 OpenAI-compatible Chat Completions，但 Ordinary 的 provider/auth binding 已由 `pi-ai` 承担。fake 只能由测试显式注入，不能成为生产配置或 UI 选项。Multi-Agent 与模型式 Skills 的共享 transport 暂保留旧 adapter，直到 pi-ai 能无损表达现有 refusal、continuation、附件和错误事实。

## 端口职责

### AgentLoop

`AgentLoop` 接受系统指令、canonical 模型消息、冻结工具边界、可选 AgentTool、`AbortSignal` 和流式回调，返回互斥的 `completed / approval_required / cancelled / failed`。它必须保留模型实际消费的消息、工具结果、usage 与确认请求，并在 release 时释放 SDK 资源。

`AgentLoop` 不拥有 conversation、run、事件、仓储、read-model 或业务完成语义。live confirmation continuation 只能在拥有它的 feature 内使用，不能伪装成可跨进程恢复的 durable token。

### IntelligenceChannel 与 AgentTurnRuntime

`IntelligenceChannel` 处理 `ModelRequest / ModelResponse`、流式 delta、用量和 provider 失败归一化。`AgentTurnRuntime` 在其上执行 Deep manager、child 与 synthesis 所需的模型-工具循环。它们不读取 Ordinary 状态，也不承担 Ordinary 业务完成。

### Provider adapter

Provider adapter 只处理：

- 鉴权、base URL、模型和协议字段映射。
- 工具 schema、消息、附件和流式事件映射。
- usage、缓存命中、finish reason 和错误归一化。
- provider 明确支持的协议 continuation。

Provider adapter 不能定义工具权限、Agent 目标、feature 状态、完成语义、仓储或 read-model；不能把 SDK 对象和 provider 私有字段泄漏到 core。

## 上下文与缓存

- Ordinary 从 Pi Session 的活动 branch 恢复上下文；`ordinary-run/v5` 只保存 Session 引用，不从 UI 文案、活动事件或摘要重建第二份历史。
- 未触发模型上下文压缩时，系统提示、工具定义和既有消息顺序保持稳定；不能静默改写历史来“优化”展示。
- 上下文压缩只能在模型调用前由 loop-level context maintenance 执行，必须保持工具调用与结果配对；失败明确返回 context overflow。
- OpenAI 官方请求可以发送官方专有缓存与 reasoning continuation 字段；OpenAI-compatible endpoint 不发送未经声明的官方私有字段。
- cached、uncached 和 reasoning token 只能使用 provider 返回值，不能由字符数估算。

## 失败与取消

模型配置错误、网络错误、请求校验失败、上下文溢出、输出不合约、取消和资源释放失败必须保留真实状态，不能变成成功或固定 fallback 回答。一个 feature 只处理自己的业务决策，不解析 SDK 私有错误对象来猜测状态。

## 配置与数据

本地模型设置只接受 settings schema version 3。旧设置、旧 provider 协议和旧本地运行数据直接失效，不迁移、不双读。API key 只进入本地 secret/config 边界和 adapter 初始化，不进入 HTTP read-model、事件、snapshot 或日志。

## 后果

- Ordinary 后续能力围绕中性 `AgentLoop` 演进，不回退到自研 Ordinary tool-use loop。
- Deep 可以继续使用 `AgentTurnRuntime`，但不得把它提升为 universal Run runtime。
- 新 provider 只有在形成独立 adapter 并满足两条中性端口契约后才能接入；不能把 provider 差异扩散到 feature。
- 模型调用的状态、用量和错误只形成调用 feature 的事实或展示投影，不建设跨 feature 的统一业务事件库。
